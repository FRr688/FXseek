# FXseek 手机版（iOS / Android）规划与设计

> 状态：**规划稿**（v0.2）· 2026-10-08
> 桌面版当前版本：1.0.6
> 本文只谈手机端，不改桌面端既有行为。
>
> **v0.2 变更**：`eg2` 查实为 Google **EmbeddingGemma 2**（2026-10-06 发布）——
> 手机端本地跑得动一个**原生多模态**嵌入模型了。据此重写定位（轻度检索）、
> 检索策略（三级自动降级二级）、LLM/ASR 可选项、以及手机↔电脑联动。

---

## 0. 一句话定位

> **桌面 FXseek 是「库」，手机 FXseek 是「眼睛和耳朵」。**
>
> 一句补充：**手机端只做轻度检索任务。**

桌面端解决「我硬盘里这几万个素材怎么找」，手机端解决「我**现在**想找点什么，而且我手上只有手机」。

**什么叫「轻度」**：手机端不追求把库里的每个角落都翻出来。它要的是
**秒开、秒出、结果八成够用**。真正的重活（全库深度语义、大模型重排、
跨模态融合）该交给电脑 —— 如果电脑在的话。

| | 桌面版 | 手机版 |
|---|---|---|
| 任务性质 | 重度检索 / 建索引 / 全库管理 | **轻度检索** |
| 模型 | WeMM-Embedding-2B（约 2 GB，本机） | **EG2**（本地，见 §2） |
| 打标 / 转写 | 本机 oMLX 或官方 API | **可选项**，且只能接官方 API |
| 检索层级 | 三级 | **三级，可自动降级为二级** |
| 重活 | 自己扛 | **外派给电脑**（§5） |

## 1. 为什么值得做（场景）

| 场景 | 桌面版 | 手机版该有的样子 |
|---|---|---|
| 在沙发上想到一首歌，想确认库里有没有 | 得回电脑 | 掏手机，哼一句 / 说个歌名，直接出 |
| 看到一样东西，想知道自己拍过没 | 不可能 | **举手机拍一张 → 以图搜图** |
| 微信群收到的音频，想找库里同款 | 得先存到电脑 | 分享面板 → 「存进 FXseek」→ 自动入库 |
| 出差在外想翻自己的素材 | 没法 | 局域网连回家里的机器 |
| **没网、电脑也没开** | 没法 | **手机本地 EG2 照样搜**（v0.2 新增） |

**手机端最大的机会不是「把桌面版缩小」，而是四件桌面版永远做不到的事：**

1. **拍照即搜**（相机是手机独有的输入设备）
2. **录音即搜**（麦克风同理）
3. **分享面板接入**（任何 App 里「分享到 FXseek」）
4. **离线可搜**（EG2 在手机本地，不依赖电脑在线）

## 2. 核心矛盾：那个 2 GB 的模型放哪？

这是整个手机版**唯一真正难的决策**，先把它想清楚，后面全是体力活。

桌面端的检索能力来自 **WeMM-Embedding-2B**（约 1.8~2 GB，MLX 跑在 Apple Silicon 上）。手机上跑不跑得动？

| 平台 | 现实 | 结论 |
|---|---|---|
| iOS | A17/M 系芯片算力够，MLX 也有 iOS 版；但**模型文件 2 GB**，App Store 首包限制、下载等待、后台被系统杀 | 技术上可行，**产品上不可接受** |
| Android | 骁龙/天玑 NPU 生态碎片，2B 多模态模型基本跑不动；全国产 App 市场对包体更敏感 | **不可行** |

### 但 EG2 改变了这个前提 ★

**EG2 = EmbeddingGemma 2**，Google 于 **2026-10-06** 发布，Apache 2.0：

| 指标 | 数值 |
|---|---|
| 总参数 | **740M**（文本核心 **270M** + 视觉 **170M** + 音频 **300M**，按需组合） |
| 架构 | Gemma 4 |
| 模态 | **原生多模态**：文本 / 图片 / 音频 / 视频 / 代码 → 同一个向量空间 |
| 上下文 | **8K token** = 5.5 分钟音频 / 29 张图 / 58 帧视频 |
| 输出维度 | **768**，用 MRL 可裁到 **512 / 256 / 128**（最多省 6 倍存储） |
| 内存占用 | Pixel 11 Pro 量化后：**仅文本 ~191 MB**，**全模态 ~567 MB** |
| 许可 | Apache 2.0（可商用） |

**这意味着什么**：那个「15 亿参数起步、2 GB 打底」的门槛**消失了**。
手机现在可以本地跑一个**真正多模态**的嵌入模型，代价是 191~567 MB 内存。

**但要说清楚 EG2 不是 WeMM 的替代品**：

| | WeMM-Embedding-2B（桌面） | EG2（手机） |
|---|---|---|
| 体积 | ~2 GB | 191~567 MB |
| 质量 | 更高 | 次一档，但「够用」 |
| 定位 | 全库精度、深度检索 | **轻度、快速、离线** |

两者**不是同一个向量空间**，这一条后面 §5 会展开讲 —— 它决定了联动怎么做。

### 结论：三档策略（v0.2 重排）

```
┌─────────────────────────────────────────────────────────────┐
│ Tier 1  瘦客户端（先做这个）                                  │
│   手机 = 遥控器 + 播放器 + 相机                              │
│   重活（建索引 / 嵌向量 / 转写 / 打标）全在桌面端            │
│   靠局域网 HTTP 通信，零模型下载，包体 < 20 MB               │
├─────────────────────────────────────────────────────────────┤
│ Tier 2  移动端独有能力（紧接着做）                            │
│   拍照即搜 / 录音即搜 / 相册自动入库 / 分享面板 / 后台备份     │
│   这些桌面版做不到，且不依赖手机本地模型                       │
├─────────────────────────────────────────────────────────────┤
│ Tier 3  本地 EG2 检索（v0.2 从「远期」提到主线 ★）            │
│   手机本地跑 EG2（文本 191MB / 全模态 567MB，按需下载）        │
│   离线也能做语义检索，不再依赖电脑在线                        │
│   没配 LLM/ASR 时，它就是手机端检索的全部（配合文件名）        │
└─────────────────────────────────────────────────────────────┘
```

**Tier 3 从「可砍的 2.0 功能」变成主线的原因**：原来它被排在最后，是因为
「150~300 MB 的小模型质量存疑，收益只在没连上桌面时体现」。EG2 把这个
判断推翻了 —— 它是**原生多模态**的，文本 / 图 / 音 / 视频**同一个空间**，
意味着「拍一张照搜库」和「哼一段旋律搜库」在本地就能做，而且 191 MB 的
纯文本档位轻到可以默认装上。

│                  │                              │  (127.0.0.1:8231)  │
│  · 浏览 / 搜索    │   发现：_fxseek._tcp.local   │                    │
│  · 播放器         │   配对：6 位数字码 / 二维码   │  WeMM 2GB 模型      │
│  · 相机 / 麦克风  │   鉴权：Bearer Token         │  索引 / 转写 / 打标 │
│  · 本地缓存       │                              │  Chromaprint        │
│  · EG2 本地模型 ★ │                              │  EG2 向量同步 ★     │
└──────────────────┘                              └────────────────────┘
        │
        │ 无桌面可连时（v0.2：不再降级为纯浏览）
        ▼
┌──────────────────────────────────────────┐
│ EG2 本地索引（文本 191MB / 全模态 567MB） │

└──────────────────────────────────────────┘
```

**关键设计：手机端不持有素材原文件**，只持有缩略图、流式播放地址和
**EG2 向量**（后者极小，见 §5.2）。原文件永远在桌面。这样：
- 手机存储零压力
- 桌面的索引是权威，手机是副本
- 桌面端一改，手机端立刻看到

## 3.5 检索策略：三级自动降级为二级 ★

桌面端 `fastsearch.py` 是三级检索（L0 文件名 → L1 向量 → L2 深度）。
**手机端沿用同一套三级策略**，但多了一条自动降级规则。

### 三级各自的依赖

| 层级 | 干什么 | 依赖 | 手机端能否独立完成 |
|---|---|---|---|
| **L0 文件名 / 元数据** | 文件名、扩展名、类型词、格式词、时间、大小 | 无 | ✅ 永远可用 |
| **L1 向量语义** | 「用大白话搜画面内容」 | **EG2**（本地，191~567 MB） | ✅ 手机本地 |
| **L2 深度检索** | 跨模态召回 + AI 描述 / 转写文本参与排序 | **LLM 打标 + ASR 转写** | ⚠️ 取决于是否配置 |

**为什么 L2 卡在 LLM/ASR 上**：L2 之所以「深」，靠的是**语料** ——
AI 生成的画面描述、AI 打的标签、ASR 转出来的文字。这些文本进了索引，
用户搜「那个谁唱的关于月亮的歌」才可能命中歌词。

**没有 LLM/ASR，就没有这些语料**，L2 无从谈起 —— 它不是在算力上跑不动，
而是**没有东西可搜**。

### 自动降级规则

```
                   ┌─────────────────────────────┐
                   │ 手机端启动 / 进入搜索        │
                   └──────────────┬──────────────┘
                                  ▼
                   ┌─────────────────────────────┐
                   │ 能不能连上桌面？             │
                   └──────┬───────────────┬──────┘
                      能  │               │ 不能
                          ▼               ▼
        ┌───────────────────────┐  ┌──────────────────────────┐
        │ 用桌面索引             │  │ 用手机本地索引            │
        │ 桌面已含 AI 描述+转写  │  │ 配了官方 LLM/ASR？        │
        │ → 【三级】L0+L1+L2     │  └───┬──────────────┬───────┘
        └───────────────────────┘   配了│              │没配
                                        ▼              ▼
                          ┌──────────────────┐ ┌──────────────────┐
                          │ 【三级】L0+L1+L2 │ │ 【二级】L0+L1 ★  │
                          │ 本地索引已富化   │ │ 文件名 + EG2     │
                          └──────────────────┘ └──────────────────┘
```

**一句话规则**：

> **没配 LLM / ASR，检索策略自动降为二级 —— 只有文件名检索 + EG2 模型检索。**

### 三种状态的对照

| 状态 | 数据源 | 层级 | 能搜到什么 |
|---|---|---|---|
| **连上桌面** | 桌面索引 | **三级** | 全部（含桌面已打好的描述和转写） |
| **离线 · 配了 LLM/ASR** | 手机本地索引（已富化） | **三级** | 全部（含手机上自己打的描述和转写） |
| **离线 · 没配** | 手机本地索引（原始） | **二级** | 文件名 + EG2 语义（画面/声音相似度） |

**界面必须明说当前是哪一级**，不能让用户以为自己搜了个假库：

```
┌────────────────────────────────────────────┐
│  检索能力                       二级 ⓘ     │
│  ────────────────────────────────────────  │
│  ✓ 文件名检索            始终可用           │
│  ✓ EG2 语义检索          本地模型           │
│  ✗ 深度检索（AI 描述/转写）  未配置         │
│                                            │
│  配置官方 LLM 与 ASR 后即可解锁 →  [去配置] │
└────────────────────────────────────────────┘
```

## 3.6 LLM 打标 / ASR 转写：可选，且只能接官方 API ★

在桌面端，打标和转写是**索引的标配**（本机 oMLX 或官方 API 都行）。
在手机端，它们是**可选项**，而且规则更严：

### 规则

| 规则 | 说明 |
|---|---|
| **默认关闭** | 不配也能正常用（退化成二级检索），不弹窗骚扰 |
| **只能接官方 API** | 手机不跑本地 LLM/ASR 模型（跑不动、耗电、包体炸） |
| **只白名单供应商** | 内置若干官方端点，用户只填 API Key，不填任意 URL |
| **密钥存 Keychain / Keystore** | 不进明文配置文件，不进日志 |
| **走用户自己的额度** | FXseek 不经手中转，不代付 |

**为什么「只能接官方 API」是好事**：如果允许填任意 base_url，等于把手机
变成一个「谁都能骗它去发请求」的代理；而且用户在手机上填一个自建地址，
大概率填错、连不上、然后来问为什么不行。**白名单 = 少一类客服问题。**

### 这两个开关影响什么

| | 开启后 | 不开 |
|---|---|---|
| **LLM 打标** | 新素材自动生成中文描述 + 标签 → 可被文字搜到 | 只有文件名和 EG2 画面语义 |
| **ASR 转写** | 音视频出文字稿 → 可被歌词/台词搜到，播放面板有文字 | 播放面板无文字，搜不到内容 |

### 界面（设置 → 智能服务）

```
┌────────────────────────────────────────────┐
│  智能服务                                   │
│  ────────────────────────────────────────  │
│  视觉打标 / 语音转写              [ 关 ] →  │
│  未配置时检索为「二级」：文件名 + EG2 语义  │
│                                            │
│  AI 描述与标签                    [ 配置 ]  │
│  官方 API · 未配置                          │
│                                            │
│  语音转写                         [ 配置 ]  │
│  官方 API · 未配置                          │
└────────────────────────────────────────────┘
```

## 3.7 手机 ↔ 电脑 联动 ★

用户提出的方向：**检索任务很重时，交给电脑端更强的 WeMM 模型处理。**

这个方向是对的，但**有一个必须先说清的技术事实**，否则会做成一个跑不通的功能。

### ⚠️ 向量不能跨模型搬运

WeMM-Embedding-2B 和 EG2 是**两个不同的模型、两个不同的向量空间**。
「128 维的 EG2 向量」和「WeMM 的向量」维度不同、语义坐标系也不同，
**余弦相似度算出来是噪声**。

所以 **「把手机的向量缓存传给电脑，让 WeMM 处理」在字面上做不到** ——
WeMM 无法消费外来向量，它只能编码**原始内容**（文字 / 图片 / 音频）。

### 能做的是三件事（都成立）

#### A. 深度外派（query offload）—— 「帮你算」

手机把**原始查询**（关键词 / 拍的照片 / 录的音）发给电脑，电脑用 WeMM
编码并搜自己的库，把结果发回来。

```
手机                          电脑
 │  ① 本地 EG2 先搜（立刻出结果，不等网络）
 │
 │  ② POST /v1/mobile/search  { query: "..." | 图片 | 音频 }
 ├─────────────────────────────►  ③ WeMM 编码 + 全库深度检索
 │                                  （AI 描述 / 转写 全部参与）
 │  ④ { items: [...] }
 ◄─────────────────────────────┤
 │  ⑤ 两路结果按排名融合（RRF），本地结果标「本机」
 │     桌面结果标「电脑」
```

**关键：融合的是「结果列表」不是「向量」** —— 用 RRF（Reciprocal Rank
Fusion）按排名合并，两边各出各的分，不需要向量可比。

#### B. 向量同步（vector sync）—— 「带着走」

电脑用 **EG2** 把全库算一遍向量，同步给手机。因为**两边同一个模型**，
手机离线也能拿同一套向量做检索。

存储代价**极小**（这也是 MRL 的价值）：

| 维度 | 每条 | 1 万条 | 10 万条 |
|---|---|---|---|
| 768 | 768 B | 7.7 MB | 77 MB |
| 256 | 256 B | 2.6 MB | 26 MB |
| **128** | **128 B** | **1.3 MB** | **13 MB** |

> 当前库 **263 个素材 / 723 条向量**：768 维只要 **约 555 KB**。
> 就算 10 万素材，256 维也只有 26 MB —— **手机存储毫无压力。**

#### C. 内容上行（content upload）—— 「帮你收」

手机上的新素材（自己拍的照片、录的音）传给电脑入库，电脑用 WeMM 建
索引，再通过 B 把 EG2 向量同步回来。这样**手机本地没有的东西，电脑也能搜到**。

### 那「重活外派」到底派什么

| 重活 | 手机能做吗 | 外派给电脑 |
|---|---|---|
| EG2 编码 | ✅ 能做（191 MB） | 可选（省电） |
| **WeMM 编码（高质量）** | ❌ | ✅ **这就是外派的核心** |
| LLM 打标 | ❌（只能调官方 API） | ✅ 电脑本机 oMLX 免费 |
| ASR 转写 | ❌（只能调官方 API） | ✅ 同上 |
| 全库深度重排 | ❌ | ✅ |

**所以「把向量缓存传给电脑」的正确形态是 A + C**：传**内容**（原始查询、
新素材），不是传向量；向量只做桌面→手机的单向同步（B）。

### 三种联动模式（用户可选）

| 模式 | 行为 | 适合 |
|---|---|---|
| **本地优先**（默认） | 只用手机 EG2，不发网络请求 | 省电、隐私、只想快速翻 |
| **智能外派** | 本地先出结果，同时发电脑；两路 RRF 融合 | 日常，想让结果更准 |
| **全交给电脑** | 只发电脑，等结果 | 明确要「搜全库深度」时 |

## 4. 信息架构 / 导航

**主导航用底部 Tab（5 个），不用汉堡菜单。** 理由：这是浏览型应用，主路径是「看 → 点 → 播」，Tab 切换成本最低。

```
┌──────────────────────────────────────────┐
│                                          │
│              内容区                       │
│                                          │
├──────────────────────────────────────────┤
│  全部素材   视频   图片   音频   文档      │
│    ▦        ▶      ▣      ♪      ☰      │
└──────────────────────────────────────────┘
```

| Tab | 对应桌面端侧栏 | 备注 |
|---|---|---|
| 全部素材 | `STATE.kind = ''` | 默认 Tab |
| 视频 | `video` | |
| 图片 | `image` | 手机端**这里是重点**（相册联动） |
| 音频 | `audio` | |
| 文档 | `document` | 手机上优先级最低，但保留 |

**二级页面**（push 进入，不占 Tab）：

- 搜索（点搜索框进入）
- 以图搜图 / 以音搜素材 / 语音搜索
- 播放器（音频 / 视频共用壳）
- 素材详情
- 漫步时光（Memory Lane）
- 设置 → 连接 / 外观 / 智能服务 / 关于

```

│ FXseek                          │  ← 大标题

| 措施 | 说明 |

| 首次配对需 6 位码 | 桌面端显示，30 分钟内有效，防止陌生人连上 |

## 6. 手机端独有的能力清单（Tier 2）

| 能力 | 实现 | 依赖的后端 API |
|---|---|---|
| **拍照即搜** | 相机 → 压缩 → POST | `POST /v1/search-image` |
| **录音即搜** | 录音 → 指纹 → POST | `POST /v1/audio-search` |
| **语音搜索** | 系统语音识别 → 文本 | `POST /v1/voice-search` |
| **相册自动入库** | 后台读相册 → 上传新增 → 索引 | `POST /v1/import` + `/v1/sources/index` |
| **分享到 FXseek** | iOS Share Extension / Android Share Target | `POST /v1/import` |
| **后台备份** | 充电 + Wi-Fi 时把新照片送过去 | 同上 |
| **锁屏播放控制** | Now Playing / MediaSession | 纯客户端 |
| **离线收藏** | 下载原文件到本地 | `GET /v1/file?path=` |

**「相册自动入库」要特别谨慎**：手机相册动辄几万张，全传上去建索引会让桌面端卡住很久。设计上必须：

1. **只传缩略图 + 元数据**建「轻索引」（足够搜到）
2. 用户点开才拉原图
3. 默认**关闭**，开启时明确告诉他「会占用约 X GB 和 Y 分钟」
4. 分批 + 可暂停 + 只在充电时跑

## 7. 技术选型

| 方案 | 优点 | 缺点 | 评价 |
|---|---|---|---|
| **SwiftUI (iOS) + Compose (Android) 双原生** | 体验最好；相机/相册/分享面板/后台播放全是一等公民；包体小 | 两套代码，工作量 × 1.7 | ⭐ **推荐** |
| Flutter | 一套代码；UI 一致性好 | 相机/后台播放/分享面板都要靠插件，踩坑多；包体 +10MB | 次选 |
| React Native | 生态大 | 同上，且性能调优麻烦 | 不推荐 |
| Tauri Mobile | 能复用桌面端的 Web UI | 移动端 WebView 性能差，瀑布流滚动会掉帧；相机插件不成熟 | ❌ |
| PWA | 零成本 | iOS 上无后台、无相册、无分享面板、无推送 | ❌ 只能当 demo |

### 为什么推荐双原生

手机版的**核心价值全在原生能力上**（拍照、录音、相册、分享面板、后台播放、锁屏控件）。这些在跨平台框架里恰恰是最容易出问题的地方 —— 用 Flutter 省下的那 40% 工作量，会在调试相机和后台播放时全部还回去。

而且这个 App 的 UI 复杂度不高（瀑布流 + 播放器 + 设置），双原生的 UI 工作量没有想象中大。

**如果只做一个平台：先做 iOS。** 理由：桌面版用户 = Mac 用户，他们的手机大概率也是 iPhone。

### 需要新加的（v0.2 扩到六样）

```
1. mDNS 服务广播
   _fxseek._tcp.local  →  携带 name / version / item_count / port
   桌面端 app.py 启动时挂上（纯增量，不影响现有行为）

2. 配对与鉴权
   POST /v1/pair/request   { code: "482913" }  → { token: "..." }
   POST /v1/pair/revoke
   GET  /v1/pair/devices
   所有 /v1/* 在「局域网模式」下校验 Authorization: Bearer <token>
   （127.0.0.1 回环请求永远放行，桌面端自己的 UI 不受影响）

3. 缩略图尺寸参数
   GET /v1/thumb?path=...&w=320
   手机按屏幕密度要合适尺寸，避免拉 2000px 的大图浪费流量

4. 手机检索能力自述  ★ 新增（§3.5）
   GET  /v1/mobile/caps
     → { levels: ["L0","L1","L2"], has_ai_desc: true, has_asr: true,
         index_version: 42 }
   手机据此决定自己是三级还是二级，不用自己猜

5. 深度外派检索  ★ 新增（§3.7-A）
   POST /v1/mobile/search
     { q: "关键词" }           或
     { image: "<base64>" }     或
     { audio: "<base64>" }
     → { items: [ {path, score, kind, why} ], took_ms }
   与现有 /v1/search 的区别：这是给手机用的稳定契约，返回体只含
   手机渲染需要的字段，且强制带 `why`（命中原因，用于解释排序）

6. EG2 向量同步  ★ 新增（§3.7-B）
   GET  /v1/mobile/vectors?since=<rev>&dim=256
     → { model: "eg2-300m", dim: 256, rev: 43,
         vectors: [ {path, vec: "<base64 int8>", mtime} ],
         deleted: ["<path>", ...] }
   桌面端用 EG2（不是 WeMM）给全库算向量；手机按 rev 增量拉取。
   删掉的素材用 deleted 列表告知，手机据此清理本地缓存。
```

**注意**：这套改动是**纯增量**的 —— 桌面端不加任何新依赖，不加配对也能继续用，开了局域网才走鉴权。

**桌面端还要多做一件事**：装 EG2 并建一份 EG2 向量表（`eg2_vectors`），
和 WeMM 向量**并存**。理由见 §3.7 —— 手机要的是**同一模型**算出来的向量，
而桌面自己的 WeMM 向量给不了手机。这份表只服务同步，不影响桌面检索。

| **M7 增量索引** | 手机本地给「只存在于手机」的素材建 EG2 索引 | 3 周 | 1.1 |

**M1~M3 是主干（约 6.5 周）**，做完就已经是一个「能用的手机客户端」。
**M3.5 是 v0.2 新增的主线**（原 Tier 3 从「4 周+ 的 2.0 功能」提前到这里），
因为它现在是**离线可用**的唯一途径，不再是锦上添花。
M4 才是真正的差异化，M5.5 让手机和电脑真正成为一个整体。

## 10. 明确不做的事

| 不做 | 原因 |
|---|---|
| ❌ **手机端跑 WeMM** | 2 GB 放不进手机（EG2 是替代方案，不是同一件事） |
| ❌ **手机端跑本地 LLM / ASR 模型** | 跑不动、耗电、包体炸；**只允许接官方 API**（§3.6） |
| ❌ **把向量当通用货币跨模型传** | EG2 向量喂不了 WeMM，两个空间（§3.7） |
| ❌ 手机端做第二个库 | 两个库 = 两份索引 = 「为什么手机搜得到电脑搜不到」的无穷 bug |
| ❌ 云同步 / 云账号 | 这个产品的**全部卖点就是不上传**，加云等于自杀 |
| ❌ 手机端删文件 | 误触成本太高，删除一律回桌面操作 |
| ❌ Android 首发 | 先把 iOS 做对，Android 复用协议和设计 |
| ❌ 平板适配（1.0） | 手机版优先；iPad 版等 2.0（那时可以用桌面端的分栏布局） |

**关于「不做手机端建索引」的修订**：v0.1 写的是「绝对不做」，v0.2 改成
「**1.0 不做，1.1 做增量**」—— 因为 EG2 让它变得可行，而且**只给手机独有的
素材建索引**是合理需求（自己拍的照片 / 录的音）。但**全库索引永远在电脑**。

## 11. 分类型需求分析 ★ v0.3

手机端的第一原则是**轻量**。这一节按「照片 / 视频 / 文档 / 音频」四类，
逐个算清需求、算力和内存，最后汇总成一份要设计的功能清单，外加一个看板。

### 11.0 先钉死一个前提：最低支持设备 = iPhone X

这个决定后面所有的数字，所以放在最前面。

| 项目 | iPhone X |
| --- | --- |
| 芯片 | A11 Bionic（2017） |
| 神经引擎 | 第 1 代，约 600 GFLOPS，2 核 |
| 内存 | **3 GB** |
| **最高系统** | **iOS 16.7.x** —— iOS 17 起就不再支持（iPhone 8 / 8 Plus / X 三款同时被砍） |

**iOS 16 这条是硬约束**：任何「iOS 17 才有」的 API 都不能用，
最低部署目标必须定 **iOS 16.0**。（Apple 至今仍在给 16.7.x 发安全更新，
所以定 iOS 16 不是一个短命的选择。）

---

### 11.1 照片：手机端占比最高的一类

#### 桌面端现在怎么做

读完代码，桌面的照片链路是：

```
读文件 → PIL 打开 → convert("RGB") → 长边缩到 420px（IMAGE_MAX_SIDE 默认值）
      → 对齐到 28 的倍数（Qwen-VL 的 patch_size × merge = 14 × 2）
      → WeMM 编码 → 2048 维向量
```

注意 **420px 是桌面默认值**，而且设置页允许用户在 128~2048 之间调
（`app.py:160` 的 `image_max_side`）。这是一个「用户可调」的参数。

#### 手机端要不要也先缩一遍？—— 要，但方式不一样

**结论：要缩，而且缩得比桌面更狠；但不要落盘。**

三个理由：

1. **EG2 有视 token 预算这个概念，而且 Google 自己的基准就是 70 个视觉 token/图。**
   官方那篇博客的延迟表写得很清楚：*"evaluated with a maximum budget of 70
   vision tokens per image"*。70 个 token 折算成像素大约就是 **224~256px 的量级**。
   也就是说 **缩到 256px 不是我们抠出来的，是模型本来的设计点**。
   再往上喂像素，模型也用不上，只是白烧算力。

2. **手机没那个余量。** 420px 长边（420×315）对 256px（256×192）是 **2.6 倍像素**。
   在 iPhone X 上，这就是 2.6 倍的等待和 2.6 倍的发热。

3. **不用落盘，这是和桌面的关键差别。** 桌面从磁盘读文件、走 PIL；
   手机上应该**直接从 Photos 框架拿 `CVPixelBuffer` 喂给 MediaPipe
   Universal Embedder** —— 官方文档明说这个 Task「自动处理图像缩放、张量归一化和
   多模态 token 化，直接把原始图像或文本传进去就能拿到 768 维（或 128~512 维截断）的
   归一化向量」。**中间不产生任何临时文件**，省 IO、省内存、省一次解码。

#### 建议的分档

| 设备档 | 长边 | 依据 |
| --- | --- | --- |
| A15+ / 6 GB+ | **256 px** | 贴着 EG2 的 70-token 设计点 |
| A12–A14 / 4 GB | **224 px** | 略降一档换速度 |
| **iPhone X / A11 / 3 GB** | **192 px** | 最低档，优先保证「能用」 |

**为什么不给用户调**：桌面版把这个参数开放给用户，是因为桌面有 40 倍的余量。
手机端把它做成**自动档位**就行 —— 用户既不知道 420 和 256 的差别，
也不应该为「搜不出来」负责。**留给用户的是「省电优先 / 平衡 / 效果优先」三个字**，
不是像素数。

#### 内存需求（算清楚）

EG2 是**模块化**的，官方博客原话是可以按需只加载需要的编码器：

> Load only the encoders you need (e.g., Text + Vision for photo and video search,
> or dynamically activate the audio encoder when voice memos are added).

按 740M = 文本 270M + 视觉 170M + 音频 300M 拆，INT4 量化下：

| 加载的模块 | 权重 | 估计常驻内存 | iPhone X（3 GB）能不能扛 |
| --- | --- | --- | --- |
| 纯文本（270M） | ~135 MB | **~191 MB**（官方参考值） | ✅ 轻松 |
| **文本 + 视觉（440M）** | ~220 MB | **~280–320 MB** | ✅ 舒服 —— **照片/视频搜索要的就是这档** |
| 文本+视觉+音频（740M） | ~370 MB | **~500–567 MB**（官方参考值） | ⚠️ 紧张，必须按需加载 |

**单张照片的临时开销**：256×256×3 ≈ **190 KB** 输入，加上中间激活，
峰值大概再多 10~30 MB，且是瞬时分配、用完即还。
相比常驻的 300 MB，这部分可以忽略 —— **手机端的内存瓶颈是模型常驻，不是图片本身**。

#### 向量存储（用真实数据算）

拿现在这台机器上的真实库当样本（1,494 个内容条目）：EG2 是 768 维、支持 MRL 截断。

| 维度 | 类型 | 1 万张照片 | 5 万张照片 | 真实库 1,494 条 |
| --- | --- | --- | --- | --- |
| 768 | float32 | 29.3 MB | 146 MB | 4.38 MB |
| 512 | float32 | 19.5 MB | 98 MB | 2.92 MB |
| **256** | **int8** | **2.4 MB** | **12.2 MB** | **0.36 MB** |
| 128 | int8 | 1.2 MB | 6.1 MB | 0.18 MB |

> 对照：桌面端 WeMM 是 **2048 维**（`index.db` 实测），这就是为什么
> 「把向量在两端之间搬」在纸面上就不成立 —— 维度都对不上。

**结论：手机端用 256 维 + int8 存储。**
5 万张照片才 12 MB —— 存储完全不是问题，**算力才是**。

#### iPhone X 的吞吐，以及由此推出的限流策略

Google 公布的参考点是 **M5 Pro GPU 上 37.3 ms/图**（26.9 张/秒，70 token 预算）。
我没有 A11 的实测数据，**所以这里必须诚实**：A11 的神经网络引擎是第一代、
只有 2 核约 600 GFLOPS，而且 LiteRT 在 iOS 上的 NPU 委托走 CoreML，
A11 对不少算子的支持有限，很可能退化到 CPU/GPU 路径。

按数量级推，A11 上大概是 **0.8~2 秒/张**（这是一个待实测的估计值，
**M1 阶段第一件事就是在真机上跑一遍标定**）。

按 1.5 秒/张算：

| 照片数 | iPhone X 预估耗时 |
| --- | --- |
| 1,000 张 | ~25 分钟 |
| 10,000 张 | ~4 小时 |
| 30,000 张 | ~12.5 小时 |

**所以照片索引绝不能「装好就开始猛跑」。** 必须：

1. **增量**：只处理没算过的，装完先算最近 500 张，让用户马上能搜到东西
2. **限流**：一批 200 张，批之间歇一下，让出 CPU
3. **看状态暂停**：息屏、低电量（< 20%）、发烫（`ProcessInfo.thermalState` 到 `.serious`）就停
4. **进度可见**：设置页和看板都要能看到「已索引 1,240 / 共 3,800」
5. **内存告警就卸模型**：监听 `didReceiveMemoryWarning`，卸掉视觉编码器，
   下次用再懒加载

### 11.2 视频：抽帧搜视频可行，但必须拆成两件事

#### 可行吗？—— 可行，而且这正是 EG2 官方演示在做的事

Google 在 AI Edge Gallery 里放的 **Video Moments Finder** 就是干这个的，
而且官方描述里有一句很关键：

> On-device video keyframe indexing and natural language search: After users select a
> local video, the on-device engine indexes vision with audio chunks and generates
> embeddings for them.

用户输入 *"kids laughing"*、*"dog catching a frisbee"*，引擎当场算出 query 向量，
跟视频帧向量比，**直接把命中的时间点标出来** —— 不需要转写、不需要先生成文字描述。

**这就是「抽帧做文字搜视频」的完整答案：不需要大模型，纯向量就能做到。**

#### 但必须把两件事分开

很多人会把这两件事混成一件，它们的成本和依赖完全不同：

| | **(a) 向量抽帧检索** | **(b) LLM 打标** |
| --- | --- | --- |
| 干什么 | 每帧算一个向量，按帧检索 + 定位时间点 | 抽帧拼成九宫格，让 LLM 写一段描述和标签 |
| 需要什么 | **只需要 EG2**（视觉编码器） | 需要一个**已配置的 LLM**（官方 API，可选） |
| 成本 | N 帧 × 一次小模型推理 | **1 次**大模型调用（不管视频多长） |
| 依赖用户配置吗 | **不依赖** | 依赖 |
| 优先级 | **必做** —— 这是视频搜索的核心价值 | 可选增强 |

> (b) 用九宫格拼图是这个项目已经验证过的省法：桌面端 `_video_contact_sheet()`
> 就是 9 格 × 320px，**一次调用**搞定整段视频，代价与视频长度无关。
> 逐帧打标＝一分钟视频几十次调用，绝对不能那么干。

#### 抽帧密度：由最低设备决定，不给用户调

范老板这个判断是对的，而且理由比「省事」更硬：

> **抽帧密度是一个「索引格式」参数，不是一个「偏好」参数。**

桌面端 `video_max_frames` 默认 32 且用户可调 —— 在桌面上这没问题，因为
一台 M 系列 Mac 跑 32 帧还是 8 帧，用户感知不到差别。

**但在手机上不行**，因为一旦开放：

1. **同一个库在不同设备上会产出不同的索引**，将来做联动/同步时对不齐
2. **iPhone X 用户「手滑调高」= 一次彻底的卡死体验**，而且他不知道为什么
3. 用户根本没有判断依据 —— 他不知道自己的 A11 和别人的 A17 差多少

所以定死一张表，**所有设备同一套**：

| 视频时长 | 抽帧间隔 | 上限 |
| --- | --- | --- |
| < 30 秒 | 3 帧（首/中/尾） | 3 |
| 30 秒 ~ 3 分钟 | 每 **8 秒** 1 帧 | **12** |
| 3 分钟 ~ 30 分钟 | 每 **20 秒** 1 帧 | **12** |
| > 30 分钟 | 每 **60 秒** 1 帧 | **12** |

**硬上限 12 帧**（桌面是 32），帧长边 **256px**（iPhone X 档 192px）。

算一下比桌面轻多少：

```
手机 / 桌面 = (12 / 32) × (256 / 420)²  ≈  0.375 × 0.371  ≈  13.9%
```

**大约只有桌面端单视频算力的 1/7。** 这个余量是留给 iPhone X 的。

代价是什么？长视频的定位精度会变粗 —— 一段 30 分钟的视频只能定位到 ±60 秒。
**这是可以接受的**：手机上看长视频、还要精确定位到某一秒，本来就是极低频的需求；
真需要精确定位时，用户会去电脑上，那时候用的是桌面的 32 帧索引。

#### iPhone X 的耗时估算

按 1.5 秒/帧（同上一节的估计）＋ 解码开销：

| 场景 | 帧数 | iPhone X 预估 |
| --- | --- | --- |
| 15 秒短视频 | 3 | ~6 秒 |
| 3 分钟 | 12 | ~25 秒 |
| 30 分钟 | 12 | ~25 秒（帧数封顶，但解码更慢） |

**注意最后一行**：帧数封顶之后，长视频的主要成本变成了 **解码**（要 seek 到 12 个位置）。
所以抽帧要走 `AVAssetImageGenerator` 的 `requestedTimeToleranceBefore/After`，
**容忍模糊定位**，不要为了精确 seek 去逐帧解码。

#### 视频的音轨怎么办

官方 Video Moments Finder 是「vision with audio chunks」——
视觉和音频**都**索引。但在我们这儿：

- **v1：视频只索引视觉帧**，音轨不碰。
- 理由：音频编码器是最重的模块（300M），iPhone X 上不该为视频再拉一个编码器起来。
- **不损失功能的场景**：视频里的对白/歌词，走「用官方 API 转写」这条路更实用
  （转成文字后是 L2 语料，能参与深度检索，也能显示字幕）。
- v1.1 再考虑给 A15+ 设备加音轨嵌入。

### 11.3 文档：需求频次最低，格式必须砍到极致

#### 现状对比

桌面端 `DOC_EXT` 有 **23 个扩展名**：

```
.txt .md .log .csv .json .xml .yaml .yml .py .js .ts .html .htm   ← 纯文本类
.pdf
.doc .docx .rtf .wps
.xlsx .xlsm .et
.pptx .dps
```

为了让这些都能读，桌面端装了 `openpyxl` / `xlrd` / `olefile` / `python-pptx`，
还调系统 `textutil`，另外写了 OLE2 复合文档解析（`.wps` / `.et` / `.dps` 都是 OLE2，
不是 zip）。

**这套东西一个都不该搬到手机上。**

#### 手机端砍到「三条抽取路径」

**关键发现：iOS 自带的能力，已经能覆盖绝大部分常见格式，且零依赖。**

| 档 | 格式 | 手机上怎么读 | 代价 |
| --- | --- | --- | --- |
| **A 档**<br>（手机能抽正文） | `.pdf` | **PDFKit**（系统框架，`PDFDocument.string`） | 0 |
| | `.txt .md .log .csv .json .xml .yml .yaml .py .js .ts` | 纯文本直读 + 编码嗅探 | 0 |
| | `.docx .rtf .html .htm` | **`NSAttributedString`**（iOS 原生就认 docx / rtf / html） | 0 |
| **B 档**<br>（只有文件名+元数据） | `.xlsx .xls .xlsm .et` | 手机不抽正文；连上电脑才有 | — |
| | `.pptx .ppt .dps` | 同上 | — |
| | `.doc .wps` | 同上（老二进制，手机没有解析器） | — |

**所以手机端真正要写的代码只有三条路：PDFKit / 纯文本 / NSAttributedString。**
23 个格式 → 3 条路径，而且**全是系统自带的，不增加一个字节的包体**。

#### 为什么 `.xlsx` 和 `.pptx` 也划到 B 档

严格说 `.xlsx` / `.pptx` 是 zip + XML，抽里面的 `sharedStrings.xml` / `slide*.xml`
并不难。但：

1. **手机上看表格、看幻灯片、再在手机上搜表格内容 —— 这个需求本身就不成立**。
   表格真正的使用场景是在电脑上打开的。
2. 一旦开了这个口子，就要处理样式、合并单元格、多工作表、公式缓存、
   日期序列号……桌面端 `_xlsx_text` 已经踩过 `.et` 要改名成 `.xlsx` 才能读的坑。
3. **B 档不是「搜不到」，是「搜文件名和元数据」** —— 这已经覆盖了
   99% 的「我记得有这么个文件」场景。

#### 和桌面联动的落差要说清楚

文档是**最需要「连上电脑」的一类**。所以界面要明说：

- 本机：能搜到**文件名**（所有格式）+ **内容**（A 档那 16 个格式）
- 连上电脑：能搜到**全部格式的内容**（桌面端已经全部索引过了）

**这句话必须写在界面上**，否则用户拿一个 `.pptx` 搜不到内容，
会认为是 bug 而不是设计。

### 11.4 音频：音乐为主 —— 声音指纹砍掉，语义搜索按设备分档

#### 先说结论

| 能力 | 手机端要不要 | 理由 |
| --- | --- | --- |
| 元数据搜索（歌手/专辑/歌名/流派） | **必做** | 零算力、秒出、命中率最高 |
| EG2 音频**语义**搜索（"很安静的钢琴曲"） | **可选，按设备分档，默认关** | 唯一能做「按感觉找」的手段，但音频编码器最重 |
| Chromaprint **声音指纹** | **v1 不做** | 见下 |
| ASR 转写（会议录音） | **可选，走官方 API** | 真正需要转写的场景 |

#### 为什么砍掉声音指纹

桌面端的 `fingerprint.py` 用 Chromaprint，解决的是「同一段录音的不同文件」。
**这个需求在手机上不成立**，四条理由：

1. **音乐的身份，元数据就够了。** 手机上音乐为主，而音乐的歌手/歌名/专辑
   就写在 ID3 标签和文件名里 —— 桌面版界面现在显示的
   `A-Lin · 以前，以后` 这种，**不需要任何模型就能拿到**。
   为「找一首歌」上指纹，是拿大炮打蚊子。

2. **指纹解决的场景，在手机上几乎不会遇到。** 指纹的价值是
   「我这份是 320kbps，你那份是 FLAC，其实是同一首」——
   这在**整理别人的库**时有用。用户自己的手机上不会有这种重复。

3. **「听一首找一首」这个场景，看着像 Shazam，其实不是。**
   Shazam 能成功是因为它**比的是全世界的曲库**；我们只能比自己的库，
   而自己库里有什么，用户本来就知道。**这个功能的价值被高估了。**

4. **成本不低。** 要引 chromaprint C 库 + 音频解码（FFmpeg 或 AVFoundation 的
   重采样），跨平台编译、包体、以及和桌面端指纹库对不齐的风险。

#### EG2 的音频能力：它解决的是另一个问题

**语义相似 ≠ 精确同一首。** 这两件事不能互相替代：

| | EG2 音频嵌入 | Chromaprint |
| --- | --- | --- |
| 回答的问题 | 「这首**听起来像**什么」 | 「这**就是**那一首吗」 |
| 换个编曲/现场版 | 还能命中 | 完全失配 |
| 对「找安静的钢琴曲」 | ✅ 有用 | ❌ 没用 |

#### 音频编码器是最大的一块，所以要按设备分档

300M 参数的音频编码器，比视觉（170M）还重。加进来常驻内存从 ~300 MB 跳到 ~567 MB。

**分档策略（复用桌面版 model reaper 的思路）：**

| 设备档 | 策略 |
| --- | --- |
| **iPhone X / A11–A12 / 3–4 GB** | **默认不装音频编码器**。用户在音频页主动点「按感觉搜」时才临时加载，**用完就卸**（并在界面上明说「正在加载音频模型…」） |
| A13–A14 / 4–6 GB | 默认装，但只在充电 + 息屏时后台编码 |
| A15+ / 6 GB+ | 默认装，音乐库 < 500 首时闲时编码完 |

**音乐的编码量其实很小**：一首歌截 **30 秒**（副歌附近）就够体现风格，
不用整首编。210 首歌 × 30 秒 ≈ 1.75 小时音频 —— 一次性后台任务。

#### 音乐 vs 会议录音，两条完全不同的路

| | 音乐 | 会议录音 |
| --- | --- | --- |
| 主要怎么找 | **元数据**（ID3：歌手/专辑/歌名/年份/流派） | **转写文字** |
| 语义嵌入有用吗 | 有用（按情绪/风格） | 用处小 |
| 需要 ASR 吗 | 不需要 | **需要**（可选，走官方 API） |
| 时长 | 3~5 分钟 | 30 分钟 ~ 2 小时 |

**所以手机端音频 = 元数据搜索（必做）+ 可选语义搜索（默认关，按设备档）+ 可选 ASR。**

顺便说，**这个分类也解释了 ASR 该放在哪**：会议录音是唯一真正需要 ASR 的音频类型，
而它恰好是频率最低、也最值得等的那一类。

### 11.6 看板（Dashboard）★ 新加

范老板要的「一眼看到手机端和电脑端各有多少、都是些什么」。
定位是 **只读的可观测面板**，不是控制台 —— **轻量原则同样适用**。

#### 四块内容

**① 双库对照（顶部大卡）**

```
┌──────────────────┬──────────────────┐
│  本机             │  电脑             │
│  1,240 项         │  149,382 项       │
│  图片  890        │  图片  118,004    │
│  视频   12        │  视频    1,204    │
│  音频  320        │  音频   28,900    │
│  文档   18        │  文档    1,274    │
│                   │  ⟳ 3 分钟前同步   │
└──────────────────┴──────────────────┘
         [ 连上电脑可用深度检索 ]
```

**离线时电脑那半张卡不显示旧数字**，而是显示「未连接」。
如果一定要显示上次快照，必须**明确标注「上次同步于 X」** ——
绝不能让用户对着一个过期数字以为是实时的。

**② 类型分布**

一条**堆叠条**（比四个环形图省地方，也更符合「占比」的阅读习惯）：
图片 / 视频 / 音频 / 文档 四段，本机和电脑各一条，上下对齐 ——
**一眼就能看出「电脑上全是图片，我手机上倒是音频多」这类结论**。

**③ 索引健康度**

| 指标 | 说明 |
| --- | --- |
| 已索引 / 待索引 / 失败 | 三个数字，失败可点开看原因 |
| 上次索引时间 | 相对时间（「2 小时前」） |
| **当前检索级别** | **二级 / 三级** —— 直接复用 ⑧ 屏那张卡 |
| 模型状态 | 文本档 / 全模态 · **已加载 / 未加载**（让用户知道内存里有没有东西） |
| 存储占用 | 向量库 / 缩略图缓存 / 模型缓存，三项分开 |

**「模型已加载 / 未加载」这一项值得单独说** ——
它是唯一能让用户理解「为什么刚才快、现在慢」的指标，
也是排查「是不是一直占着我 300MB 内存」的唯一入口。

**④ 最近动态**

- 最近 7 天索引了多少（小柱状图，不写具体数字也行）
- 最近搜索过的词 —— **默认关，可在设置里打开**（搜索词是隐私，不能默认采集展示）

#### 数据从哪来

**本机**：本地 SQLite 聚合查询，**不联网、不发请求**，打开即出。

**电脑**：
- `GET /v1/stats` —— **桌面端已有这个接口**，直接用
- `GET /v1/mobile/caps` —— 计划新增（见 §8），提供检索级别和能力自述

**缓存策略**：电脑侧数据本地缓存一份，**断网时明确标灰并显示快照时间**。

#### 明确不做

- ❌ 看板上不放任何**写操作**（不能在这里删文件、改设置、触发索引）
- ❌ 不做**实时轮询**（打开时拉一次 + 下拉刷新就够，省电）
- ❌ 不做**搜索词统计上报**（本地都不默认开，更不会上传）

## 12. 外观与语言：与桌面端统一 ★ v0.3

范老板的要求：**外观和桌面端统一，两套主题；同样支持中英文切换。**

好消息是这两件事在桌面端都已经做完了，手机端**不是从零设计，而是把已有的那套搬过去**。

### 12.1 主题：两套，令牌逐值对齐

桌面端的机制很简单：`ui.html` 的 `:root` 定义亮色令牌，
`body[data-theme="dark"]` 覆盖同名令牌，**组件全部走 `var()`** ——
所以换主题不用动结构，只换一套值。

**★ 关键：桌面端的亮色不是纯白。** 源码注释写得很直白：

> 亮色已整体降亮度：大面积纯白长时间看刺眼，
> 改为「页面浅灰 + 卡片近白」两级，保留层次但不晃眼

手机端必须照搬这个灰阶关系，**不能自作主张用 `#fff` / `#000`**。

#### 完整令牌表（两侧逐值一致）

| 用途 | 亮色 | 暗色 |
| --- | --- | --- |
| 页面底 | `#eef1f5` | `#16181d` |
| 卡片 / 面板底 | `#f7f9fb` | `#1f232a` |
| 侧栏 / 控件浅底 | `#eaedf2` | `#242931` |
| 悬停 / 选中 | `#e3e7ed` / `#e0e9f9` | `#262b33` / `#2b313a` |
| 边框 / 强边框 | `#d9dde4` / `#c6ccd5` | `#2e333c` / `#3a4048` |
| 正文 / 次要 / 弱化 | `#1a1d21` / `#636a77` / `#8f96a2` | `#e8eaed` / `#b6bcc8` / `#8b93a1` |
| 主按钮 | `#37465b` | `#4a5d78` |
| 强调蓝 / 浅蓝底 | `#3d7eff` / `#e4ecfd` | `#3d7eff` / `#22314a` |
| 成功 / 警告 / 错误 | `#3fb950` / `#d29922` / `#e5534b` | 同左 |
| 缩略图占位底 | `#e8ebf0` | `#23272f` |
| 品牌渐变 | `#6366f1 → #a855f7 → #ec4899` | 同左 |

**品牌渐变两套主题都不变** —— 它本身就是中间亮度的紫粉，在两种底色上都立得住。

#### 手机上多一个数据源：跟随系统

桌面的「自动」只有一种含义：按本地时间 07:00–19:00 切。
但 iOS 用户的预期是**跟随系统外观**（`UITraitCollection.userInterfaceStyle`）。

所以**主题从三档变四档**：

| 档 | 行为 |
| --- | --- |
| **跟随系统**（默认） | 系统切深色我就切 —— iOS 用户的预期 |
| 按时间 | 本地时间 07:00–19:00 白天主题，其余夜晚 —— 保留，给固定作息的人 |
| 白天 | 恒定亮色 |
| 夜晚 | 恒定暗色 |

**这是一处有意的不一致**，因为平台惯例不同。理由要写进「与桌面端的刻意差异」表，
而不是让用户以为我们忘了。

### 12.2 令牌能照抄，但有两处必须换算

**颜色一个字节都不改**，但尺寸不能照抄：

1. **触控目标 ≥ 44pt**（Apple HIG）。
   桌面端的行高、按钮、开关都是按鼠标设计的。手机端要按比例放大 ——
   但**放大的是尺寸，不是颜色**。
2. **字号走 Dynamic Type，别写死。**
   桌面端用 `html{font-size}` 三档 + 全站 rem（基准 16px → 14.5 / 16 / 17.5）。
   但手机用户在**系统设置里就能调字号**。所以手机端：
   - 用语义字号（`.body` / `.headline` / `.caption`），**不写死 px**
   - 「小 / 中 / 大」三档变成**相对系统的偏移**，不是绝对值

### 12.3 语言：直接复用桌面端那份词典 ★★

桌面端的 `i18n.js` 分三层，**其中两层是纯数据，与 DOM 无关**：

| 层 | 是什么 | 手机端能不能用 |
| --- | --- | --- |
| `ZH2EN` 词典 | 365+ 条 `"中文": "English"` | ✅ **纯数据，直接导出** |
| `RULES` 正则 | 处理插值/动态文案（带变量的句子） | ✅ **纯逻辑，移植成一个小函数** |
| DOM walker `applyNode()` | 遍历 DOM 换文本 | ❌ 原生端用不上 |

**导出的做法**：

```
i18n.js 的 ZH2EN
   ├─► iOS:     zh-Hans.lproj/Localizable.strings
   │            en.lproj/Localizable.strings
   └─► Android: values/strings.xml
                values-en/strings.xml

i18n.js 的 RULES
   └─► 各平台一个小运行时：Swift 一个 tr(_:) 函数 / Kotlin 一个 tr() 函数
```

**这一步应该写个脚本自动化**，而不是手工抄 365 条 ——
因为桌面端以后还会加词条，**手工抄一定会漂移**。

#### 手机上其实有两条翻译路径

| 翻什么 | 走哪条 |
| --- | --- |
| 原生 UI（导航栏、设置项、按钮、空态） | **系统本地化**（`.strings` / `strings.xml`） |
| 系统画的界面（权限弹窗、Share Sheet、日期选择器） | **系统自动翻**，只要在 `Info.plist` 声明 `CFBundleLocalizations = [zh-Hans, en]` |

#### 必须保留的两条规矩

1. **不翻译用户自己的元数据** —— 歌手名、专辑名、文件名。
   桌面端是**刻意**跳过这些的（`i18n.js` 的 `SKIP_SEL` 里就有 `.card .nm`）。
   手机端同样：截图里的 `a lin - 四季.flac`、`风景(示例).png` 在英文界面下**原样显示**。
2. **切换立即生效，不重启** —— 桌面端切换是即时的，手机端也要。
   设置项存本地，首次启动跟随系统语言。

### 12.4 验收标准

- [ ] 两套主题的**每一个颜色值**都与桌面端令牌表一致（可用脚本逐值比对）
- [ ] 品牌渐变两套主题都不变
- [ ] 切主题**不影响任何布局**，只换颜色
- [ ] 字号跟随系统 Dynamic Type，且「小/中/大」是相对偏移
- [ ] 触控目标 ≥ 44pt
- [ ] 中英文切换**立即生效**，无需重启
- [ ] 英文界面下**用户元数据保持原文**
- [ ] 系统权限弹窗跟随语言设置


## 13. 早期分发：走 IPA 安装 ★ v0.3

范老板拍板：**早期以 IPA 安装**。这一节把这条路的坑一次性列清。

### 13.1 三条路对比，以及为什么 Ad Hoc 最合适

| 路径 | 年费 | 装机有效期 | 装机数 | 用户怎么装 |
| --- | --- | --- | --- | --- |
| 免费 Apple ID 侧载 | 0 | **7 天** | **3 个 App** | 自己插数据线用 AltStore / Sideloadly，**每 7 天重签** |
| **$99 开发者 + Ad Hoc IPA** | **$99** | **1 年** | **100 台 / 设备类型** | 登记 UDID 后可 OTA 一点安装 |
| TestFlight | $99 | 90 天 / 构建 | 10,000 | 装 TestFlight，输邀请码 |

**结论：$99 + Ad Hoc IPA 是早期最合适的** —— 一年有效期、100 台够用、装完不用管。

**❌ 免费 Apple ID 那条路要明确排除**：7 天过期意味着测试者**第 8 天一定来问你
「怎么打不开了」**。数据还在，但 App 起不来。早期测试最怕的就是「装完就失效」。

**❌ 企业证书（$299）也不要考虑**：要求公司主体 + D-U-N-S 编号，
而且 Apple 对企业证书滥用是**直接吊销**的，个人开发者做消费类应用走这条路
等于随时可能全量失效。

### 13.2 IPA 怎么给到用户手上

**方式 A：数据线 + 工具**（最土，零依赖）

AltStore / Sideloadly / Apple Configurator 2 / Xcode 都行。
缺点是**每个测试者都要会折腾**，Windows 用户还要装额外工具。

**方式 B：OTA 一点就装**（体验最好，推荐）

iOS 支持用 `itms-services://` 从网页直接安装：

```
itms-services://?action=download-manifest&url=https://<域名>/manifest.plist
```

**硬要求（Apple 官方原文）**：

> Be sure that the .ipa file is accessible over HTTPS and that your site is signed
> with a certificate that's trusted by iOS and iPadOS. **Installation fails if a
> self-signed certificate doesn't have a trusted anchor** and can't be validated
> by the device.

也就是说 **必须真 HTTPS + 受信任证书**，自签不行。

**★ 零成本可行方案**：

| 放什么 | 放哪 | 为什么可行 |
| --- | --- | --- |
| `manifest.plist` | **GitHub Pages** | HTTPS + 受信任证书，免费 |
| `FXseek-1.0.x.ipa` | **GitHub Releases** | HTTPS + 受信任证书，**单个附件上限 2 GB**，够 |

然后给测试者一个网页，上面一个按钮指向 `itms-services://` 链接。
**这套和现在桌面端的 Release 流程是同一套基础设施**，不用新建任何东西。

> ⚠️ 国内访问 GitHub 慢。桌面端已经在用 `ghfast.top` 镜像，
> 但 **OTA 安装不能走镜像** —— `itms-services` 的 URL 必须是原始 HTTPS 地址。
> 所以 IPA 本体可能下得慢，这点要提前跟测试者说清。

**方式 C：TestFlight** —— 要过一次 App Store Connect 审核（比正式上架轻），
优点是 10,000 人、用户零门槛。**早期测试者超过 100 人就该切到这条。**

### 13.3 UDID：Ad Hoc 绕不过去的一步

Ad Hoc 的 provisioning profile 里**必须列出每一台设备的 UDID**，否则装不上。
上限 **100 台 / 设备类型 / 会员年**（每年续费时重置）。

收集方式：

1. **让测试者插电脑**，Finder / iTunes 里点设备名 → 看到 UDID → 复制发你（最笨最可靠）
2. **一个 HTTPS 页面挂 `.mobileconfig` 描述文件**，装上就显示 UDID（体验好，但 Apple 收紧了，要实测）
3. **Apple Configurator / 第三方服务**（Appcircle 之类）代管设备登记

**这是流程摩擦，不是技术问题。早期建议人工收**，20 人以内完全够用。

**⚠️ 一个容易踩的坑**：设备一旦登记进 profile，**当年移除的额度不返还**。
别用「先随便加几台试试」的心态做设备登记。

### 13.4 ★ 三个 Info.plist 权限，漏一个就静默失败

这是 IPA 路径上**技术含量最高、也最容易翻车**的地方。
iOS 和 macOS 最大的差别：**权限没声明，功能不是报错，是静默不工作。**

| 键 | 少了会怎样 | 什么时候弹 |
| --- | --- | --- |
| `NSLocalNetworkUsageDescription`<br>+ `NSBonjourServices`（含 `_fxseek._tcp`） | **局域网发现永远失败，且不报错** —— 用户只看到「找不到电脑」 | **第一次真正访问局域网时** |
| `NSPhotoLibraryUsageDescription` | 相册读不了 —— 照片索引整个功能没了 | 第一次读相册 |
| `NSMicrophoneUsageDescription` | 录音搜、语音搜用不了 | 第一次开麦 |
| `BGTaskSchedulerPermittedIdentifiers` | 后台增量索引不会跑 | 不弹，但任务永远不被调度 |

**★★ 局域网权限是最大的坑**：弹窗只在**第一次真正访问局域网时**出现，
用户手滑点了「不允许」，**之后不会再弹**，mDNS 会**静默失败**。

必须做两件事：

1. 连接配对页上，发现失败时明确提示
   「可能是「本地网络」权限没开 → 去 设置 › FXseek › 本地网络」，并给跳转按钮
2. 首次进配对页**先解释再触发**，别让用户在不知情下点掉那个弹窗

### 13.5 EG2 模型不要打进 IPA

| 装法 | IPA 体积 | 问题 |
| --- | --- | --- |
| 文本档打包进去 | ~250 MB | 每次改代码重新出包，用户都要重下 250 MB |
| 全模态打包进去 | ~650 MB | 同上，而且 100 台设备每次都要传这么大 |
| **只装壳，首次启动下载** | **< 30 MB** | ✅ 和桌面端 WeMM（1.8 GB）同一个思路 |

**模型从哪下**：GitHub Releases，或之后放对象存储。**不要走 GitHub Pages**
（有 1 GB 仓库上限）。

**要处理的四件事**：

1. **下载中断能续**（`URLSession` 后台下载 + 断点续传）
2. **下载完校验**（SHA-256 比对，防止半截文件）
3. **没网时的空态**（明说「模型未下载，拍照即搜暂不可用」+ 重试）
4. **界面要说清**：下载的是**本地模型**，不是上传你的照片 ——
   否则「全程本地、不上传」的承诺会被用户误解

### 13.6 iOS 不允许 App 自我更新

**这是一条 iOS 硬规则**：沙盒里没有「下载并替换自己」的能力
（除非走 App Store / TestFlight）。

所以「检查更新」在手机端只能做到：

> **检查 → 发现有新版本 → 提示 + 一个按钮跳 Safari 打开 OTA 链接**

**不能像桌面端那样一键下载安装。** 这个差异要写进「与桌面端的刻意差异」表。

好在小：`/v1/update/check` 的后端逻辑**可以完全复用**，
只是手机端比对的是 IPA 的 `CFBundleShortVersionString`。

### 13.7 早期就要定死的三件事（改起来很贵）

| 项目 | 建议 | 为什么定死 |
| --- | --- | --- |
| **Bundle ID** | `com.frr688.fxseek` | 一旦发布**不能改** —— 改了等于新 App，用户要重装、数据可能丢 |
| **最低 iOS 版本** | **16.0** | 定了才能保 iPhone X（见 §11.0） |
| **签名证书** | 一个 Apple Developer 账号，别换 | 换证书 = 所有已装机器的 profile 失效 |

**版本号机制直接复用桌面端**：`CFBundleShortVersionString` 与 `app.py` 的 `"version"`
保持同一个号 —— 这样「电脑 1.0.6 / 手机 1.0.6」是同一个概念，
用户不会被两个版本号搞晕。

## 14. 待确认的问题

需要范老板拍板的几件事（v0.3 更新）：

1. **先做 iOS 还是双端一起？** 建议 iOS 先行（桌面用户 = Mac 用户）
2. **局域网模式默认开还是默认关？** 建议默认**关**，由用户在桌面端「设置 → 连接」里主动打开（安全第一）
3. **相册自动入库要不要做进 1.0？** 建议**不做进 1.0**，它风险最高、收益最不确定，放到 1.1
4. **Apple 开发者账号**（$99/年）—— iOS 上架必须有；没有的话只能走 TestFlight 内测
5. **Android 要不要上架国内应用商店？** 各家的隐私合规（尤其「读取相册」权限说明）是额外工作量
6. **★ EG2 默认装哪一档？** 建议**默认只装文本档（191 MB）**，全模态档（567 MB）
   按需下载 —— 但这样「拍照即搜」就得等下载完才能用，要不要首装就带全模态？
7. **★ 联动默认哪种模式？** 建议默认**本地优先**（省电、不 surprise），
   连上电脑时提示「可用深度检索，点一下开启」
8. **★ 手机自己的 LLM/ASR 要内置哪些官方供应商？** 建议先做
   OpenAI / Anthropic / Gemini / 通义 / 智谱 五家，够覆盖绝大多数人

v0.3 新增（分类型分析之后）：

9. **★ 最低部署目标定为 iOS 16.0？** iPhone X 最高只能到 16.7.x，
   要支持它就得放弃所有 iOS 17 的新 API。建议**接受**（Apple 仍在给 16.7.x 发安全更新）
10. **★ 照片缩到 192px 会不会太糊？** 这是 iPhone X 档的取值。
    建议**先按 192 做、M1 阶段真机标定后再定**（若质量掉得厉害就宁可慢一点）
11. **★ 音频语义搜索在 iPhone X 上默认开还是关？** 建议**默认关**
    （音频编码器 300M 会把常驻从 300MB 拉到 567MB），用户主动点才加载
12. **★ 看板的「最近搜索词」要不要做？** 建议**做，但默认关** ——
    搜索词是隐私，不能默认采集展示
13. **★ 视频抽帧 12 帧封顶够用吗？** 30 分钟视频只能定位到 ±60 秒。
    建议**接受**（手机上看长视频还要精确定位是极低频需求，真要精确定位去电脑上）

v0.3（外观/语言统一）新增：

14. **★ 主题默认跟随系统，还是保持桌面端的三档？** 建议**默认跟随系统**
    （iOS 用户预期），并把「按时间」保留成第四档
15. **★ 要不要写个「从 i18n.js 导出 .strings / strings.xml」的脚本？**
    建议**要** —— 365+ 条手工抄一定会漂移，而且桌面端以后还会加词条
16. **★ 「小/中/大」字号在手机上怎么定义？** 建议做成**相对系统的偏移**
    （如系统字号 × 0.9 / 1.0 / 1.1），而不是绝对值

v0.3（早期分发：IPA）新增：

17. **★ Bundle ID 用 `com.frr688.fxseek` 行吗？** 建议**现在定死** ——
    发布后不能改，改了等于新 App
18. **★ 有没有 $99 的 Apple Developer 账号？** 没有的话早期只能走 7 天免费侧载，
    强烈不建议（见 §13.1）
19. **★ OTA 安装页放 GitHub Pages 吗？** 建议**放** —— 零成本、证书受信任，
    和桌面端 Release 是同一套基础设施
20. **★ 早期测试者大概多少人？** 20 人以内人工收 UDID 就够；
    接近 100 人时该提前切 TestFlight

## 附：与桌面端的设计一致性检查表

手机版无论在哪个平台，都必须守住这些桌面端已经定下的规矩：

- [ ] 品牌色：`#6366f1 → #a855f7 → #ec4899` 渐变
- [ ] 优化操作**只在播放面板**，详情页不出现（1.0.5 的决策）
- [ ] 视频和音频**共用同一个文字面板**（1.0.5 的决策）
- [ ] 英文/中文双语，且**不翻译用户自己的元数据**（歌手名、文件名）
- [ ] 用户体验设置里必须有**动效三档开关**，并尊重系统「减弱动态效果」
- [ ] 两套主题的**每个颜色值**与桌面端 `ui.html` 的 `:root` / `body[data-theme="dark"]` **逐值一致**（可脚本比对）
- [ ] 切主题**只换颜色不改布局**；品牌渐变两套主题都不变
- [ ] 语言切换**立即生效不重启**；英文下用户元数据（歌手名、文件名）保持原文
- [ ] iOS 版 `Info.plist` 里 **`NSLocalNetworkUsageDescription` + `NSBonjourServices` 必须在**
      （漏了局域网发现会静默失败，且权限弹窗不会再出现）
- [ ] 首次使用要说清**「全程本地、不上传」**——这是产品的核心承诺
