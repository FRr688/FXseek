# FXseek 手机版（iOS / Android）规划与设计

> 状态：**规划稿**（v0.1）· 2026-10-08
> 桌面版当前版本：1.0.5
> 本文只谈手机端，不改桌面端既有行为。

---

## 0. 一句话定位

> **桌面 FXseek 是「库」，手机 FXseek 是「眼睛和耳朵」。**

桌面端解决「我硬盘里这几万个素材怎么找」，手机端解决「我**现在**想找点什么，而且我手上只有手机」。

---

## 1. 为什么值得做（场景）

| 场景 | 桌面版 | 手机版该有的样子 |
|---|---|---|
| 在沙发上想到一首歌，想确认库里有没有 | 得回电脑 | 掏手机，哼一句 / 说个歌名，直接出 |
| 看到一样东西，想知道自己拍过没 | 不可能 | **举手机拍一张 → 以图搜图** |
| 微信群收到的音频，想找库里同款 | 得先存到电脑 | 分享面板 → 「存进 FXseek」→ 自动入库 |
| 出差在外想翻自己的素材 | 没法 | 局域网连回家里的机器 |

**手机端最大的机会不是「把桌面版缩小」，而是三件桌面版永远做不到的事：**

1. **拍照即搜**（相机是手机独有的输入设备）
2. **录音即搜**（麦克风同理）
3. **分享面板接入**（任何 App 里「分享到 FXseek」）

---

## 2. 核心矛盾：那个 2 GB 的模型放哪？

这是整个手机版**唯一真正难的决策**，先把它想清楚，后面全是体力活。

桌面端的检索能力来自 **WeMM-Embedding-2B**（约 1.8~2 GB，MLX 跑在 Apple Silicon 上）。手机上跑不跑得动？

| 平台 | 现实 | 结论 |
|---|---|---|
| iOS | A17/M 系芯片算力够，MLX 也有 iOS 版；但**模型文件 2 GB**，App Store 首包限制、下载等待、后台被系统杀 | 技术上可行，**产品上不可接受** |
| Android | 骁龙/天玑 NPU 生态碎片，2B 多模态模型基本跑不动；全国产 App 市场对包体更敏感 | **不可行** |

### 结论：三档策略

```
┌─────────────────────────────────────────────────────────────┐
│ Tier 1  瘦客户端（先做这个）                                  │
│   手机 = 遥控器 + 播放器 + 相机                              │
│   重活（建索引 / 嵌向量 / 转写 / 打标）全在桌面端            │
│   靠局域网 HTTP 通信，零模型下载，包体 < 20 MB               │
├─────────────────────────────────────────────────────────────┤
│ Tier 2  移动端独有能力（紧接着做）                            │
│   拍照即搜 / 录音即搜 / 相册自动入库 / 分享面板 / 后台备份     │
│   这些桌面版做不到，且不依赖手机本地模型                       │
├─────────────────────────────────────────────────────────────┤
│ Tier 3  离线轻量索引（远期）                                  │
│   手机本地跑一个量化到 150~300 MB 的图文检索小模型            │
│   只覆盖「找自己拍的照片」这一件事，离线可用                   │
│   跑不动就退化成「文件名 + 相册时间线」                       │
└─────────────────────────────────────────────────────────────┘
```

**为什么 Tier 1 是正确起点**：桌面端已经有完整的 HTTP API（见 §8），手机端几乎不用后端改动就能跑起来。而且它立刻解决「沙发上想找东西」这个真实痛点。

**为什么 Tier 3 放到最后**：它会显著拖慢一切，而且收益只在「没连上桌面」时才体现 —— 而没连上的时候，用户通常也不着急找素材。

## 3. 系统架构

```
┌──────────────────┐        局域网 (Wi-Fi)        ┌────────────────────┐
│  手机 App         │  ◄──── HTTP + mDNS ────►   │  桌面 FXseek        │
│                  │                              │  (127.0.0.1:8231)  │
│  · 浏览 / 搜索    │   发现：_fxseek._tcp.local   │                    │
│  · 播放器         │   配对：6 位数字码 / 二维码   │  WeMM 2GB 模型      │
│  · 相机 / 麦克风  │   鉴权：Bearer Token         │  索引 / 转写 / 打标 │
│  · 本地缓存       │                              │  Chromaprint        │
└──────────────────┘                              └────────────────────┘
        │
        │ 无桌面可连时
        ▼
┌──────────────────┐
│ Tier 3 本地小模型 │  （远期，可降级为纯文件浏览）
└──────────────────┘
```

**关键设计：手机端不持有素材文件**，只持有缩略图和流式播放地址。原文件永远在桌面。这样：
- 手机存储零压力
- 索引只有一份（不会出现「手机和电脑搜出来的结果不一样」）
- 桌面端一改，手机端立刻看到

## 4. 信息架构 / 导航

**主导航用底部 Tab（5 个），不用汉堡菜单。** 理由：这是浏览型应用，主路径是「看 → 点 → 播」，Tab 切换成本最低。

```
┌──────────────────────────────────────────┐
│                                          │
│              内容区                       │
│                                          │
├──────────────────────────────────────────┤
│  全部素材   视频   图片   音频   文档      │
│    ▦        ▶      ▣      ♪      ☰      │
└──────────────────────────────────────────┘
```

| Tab | 对应桌面端侧栏 | 备注 |
|---|---|---|
| 全部素材 | `STATE.kind = ''` | 默认 Tab |
| 视频 | `video` | |
| 图片 | `image` | 手机端**这里是重点**（相册联动） |
| 音频 | `audio` | |
| 文档 | `document` | 手机上优先级最低，但保留 |

**二级页面**（push 进入，不占 Tab）：

- 搜索（点搜索框进入）
- 以图搜图 / 以音搜素材 / 语音搜索
- 播放器（音频 / 视频共用壳）
- 素材详情
- 漫步时光（Memory Lane）
- 设置 → 连接 / 外观 / 智能服务 / 关于

### 5.2 搜索

沿用桌面端的**类型词 + 格式词**识别，但在手机上要额外处理**语音输入**：

- 搜索框右侧常驻麦克风 → 长按说话 → `POST /v1/voice-search`
- 识别结果直接填进搜索框并触发搜索，**用户可以再改**
- 识别错了能撤回（手机上语音识别错字很常见）

│  │                    连接 ›  │  │

**安全性**（重要，因为局域网 = 同 Wi-Fi 下任何人都能连）：

| 措施 | 说明 |
|---|---|
| 首次配对需 6 位码 | 桌面端显示，30 分钟内有效，防止陌生人连上 |
| 配对后发 Bearer Token | 存在手机 Keychain / Keystore |
| Token 可撤销 | 桌面端「设置 → 已连接设备」里踢掉 |
| 默认拒绝 | 桌面端设置里有个总开关，关掉就完全不响应局域网 |
| 只读默认 | 手机端默认只能**搜和看**，删除/索引等写操作需要在桌面端单独授权 |

**为什么默认只读**：手机丢了 = 库被删了，这个风险不能接受。

### 5.7 漫步时光（Memory Lane）

桌面端那个按年份漫游的场景，手机端**更适合**（手机是随手翻的姿势）：

- 竖屏全屏，上下滑动切年份
- 卡片用**视差 + 淡入**（手机 GPU 无压力）
- 支持「摇一摇随机」—— 手机独有交互
- 可以直接生成一张**分享图**发朋友圈（这个能传播）

## 6. 手机端独有的能力清单（Tier 2）

| 能力 | 实现 | 依赖的后端 API |
|---|---|---|
| **拍照即搜** | 相机 → 压缩 → POST | `POST /v1/search-image` |
| **录音即搜** | 录音 → 指纹 → POST | `POST /v1/audio-search` |
| **语音搜索** | 系统语音识别 → 文本 | `POST /v1/voice-search` |
| **相册自动入库** | 后台读相册 → 上传新增 → 索引 | `POST /v1/import` + `/v1/sources/index` |
| **分享到 FXseek** | iOS Share Extension / Android Share Target | `POST /v1/import` |
| **后台备份** | 充电 + Wi-Fi 时把新照片送过去 | 同上 |
| **锁屏播放控制** | Now Playing / MediaSession | 纯客户端 |
| **离线收藏** | 下载原文件到本地 | `GET /v1/file?path=` |

**「相册自动入库」要特别谨慎**：手机相册动辄几万张，全传上去建索引会让桌面端卡住很久。设计上必须：

1. **只传缩略图 + 元数据**建「轻索引」（足够搜到）
2. 用户点开才拉原图
3. 默认**关闭**，开启时明确告诉他「会占用约 X GB 和 Y 分钟」
4. 分批 + 可暂停 + 只在充电时跑

## 7. 技术选型

| 方案 | 优点 | 缺点 | 评价 |
|---|---|---|---|
| **SwiftUI (iOS) + Compose (Android) 双原生** | 体验最好；相机/相册/分享面板/后台播放全是一等公民；包体小 | 两套代码，工作量 × 1.7 | ⭐ **推荐** |
| Flutter | 一套代码；UI 一致性好 | 相机/后台播放/分享面板都要靠插件，踩坑多；包体 +10MB | 次选 |
| React Native | 生态大 | 同上，且性能调优麻烦 | 不推荐 |
| Tauri Mobile | 能复用桌面端的 Web UI | 移动端 WebView 性能差，瀑布流滚动会掉帧；相机插件不成熟 | ❌ |
| PWA | 零成本 | iOS 上无后台、无相册、无分享面板、无推送 | ❌ 只能当 demo |

### 为什么推荐双原生

手机版的**核心价值全在原生能力上**（拍照、录音、相册、分享面板、后台播放、锁屏控件）。这些在跨平台框架里恰恰是最容易出问题的地方 —— 用 Flutter 省下的那 40% 工作量，会在调试相机和后台播放时全部还回去。

而且这个 App 的 UI 复杂度不高（瀑布流 + 播放器 + 设置），双原生的 UI 工作量没有想象中大。

**如果只做一个平台：先做 iOS。** 理由：桌面版用户 = Mac 用户，他们的手机大概率也是 iPhone。

## 8. 后端协议（几乎不用改）

桌面端已有完整的 HTTP API，手机端**直接复用**：

| 手机端用途 | 现有 API | 是否需要改 |
|---|---|---|
| 连接测试 / 状态 | `GET /health`、`GET /v1/about` | 否 |
| 浏览列表 | `GET /v1/browse` | 否 |
| 搜索 | `POST /v1/search` | 否 |
| 以图搜图 | `POST /v1/search-image` | 否 |
| 以音搜素材 | `POST /v1/audio-search` | 否 |
| 语音搜索 | `POST /v1/voice-search` | 否 |
| 素材详情 | `GET /v1/detail` | 否 |
| 缩略图 | `GET /v1/thumb` | 否 |
| 原文件 / 流式播放 | `GET /v1/file?path=` | 需确认 **Range** 支持（拖动进度条） |
| 分类计数 | `GET /v1/stats` | 否 |
| 索引源 | `GET /v1/sources` | 否 |
| 转写 / 优化 | `POST /v1/asr/transcribe`、`/v1/asr/polish` | 否 |
| 打标 | `POST /v1/ai/tag` | 否 |
| 导入（分享进来的文件） | `POST /v1/import` | 否 |
| 设置读写 | `GET/POST /v1/settings` | 需加 `mobile_*` 键 |

### 需要新加的三样

```
1. mDNS 服务广播
   _fxseek._tcp.local  →  携带 name / version / item_count / port
   桌面端 app.py 启动时挂上（纯增量，不影响现有行为）

2. 配对与鉴权
   POST /v1/pair/request   { code: "482913" }  → { token: "..." }
   POST /v1/pair/revoke
   GET  /v1/pair/devices
   所有 /v1/* 在「局域网模式」下校验 Authorization: Bearer <token>
   （127.0.0.1 回环请求永远放行，桌面端自己的 UI 不受影响）

3. 缩略图尺寸参数
   GET /v1/thumb?path=...&w=320
   手机按屏幕密度要合适尺寸，避免拉 2000px 的大图浪费流量
```

**注意**：这套改动是**纯增量**的 —— 桌面端不加任何新依赖，不加配对也能继续用，开了局域网才走鉴权。

## 10. 明确不做的事

| 不做 | 原因 |
|---|---|
| ❌ 手机端建索引 | 2 GB 模型放不进手机，放进去也没人愿意等下载 |
| ❌ 手机端做第二个库 | 两个库 = 两份索引 = 「为什么手机搜得到电脑搜不到」的无穷 bug |
| ❌ 云同步 / 云账号 | 这个产品的**全部卖点就是不上传**，加云等于自杀 |
| ❌ 手机端删文件 | 误触成本太高，删除一律回桌面操作 |
| ❌ Android 首发 | 先把 iOS 做对，Android 复用协议和设计 |
| ❌ 平板适配（1.0） | 手机版优先；iPad 版等 2.0（那时可以用桌面端的分栏布局） |

## 11. 待确认的问题

需要范老板拍板的几件事：

1. **先做 iOS 还是双端一起？** 建议 iOS 先行（桌面用户 = Mac 用户）
2. **局域网模式默认开还是默认关？** 建议默认**关**，由用户在桌面端「设置 → 连接」里主动打开（安全第一）
3. **相册自动入库要不要做进 1.0？** 建议**不做进 1.0**，它风险最高、收益最不确定，放到 1.1
4. **Apple 开发者账号**（$99/年）—— iOS 上架必须有；没有的话只能走 TestFlight 内测
5. **Android 要不要上架国内应用商店？** 各家的隐私合规（尤其「读取相册」权限说明）是额外工作量

## 附：与桌面端的设计一致性检查表

手机版无论在哪个平台，都必须守住这些桌面端已经定下的规矩：

- [ ] 品牌色：`#6366f1 → #a855f7 → #ec4899` 渐变
- [ ] 优化操作**只在播放面板**，详情页不出现（1.0.5 的决策）
- [ ] 视频和音频**共用同一个文字面板**（1.0.5 的决策）
- [ ] 英文/中文双语，且**不翻译用户自己的元数据**（歌手名、文件名）
- [ ] 用户体验设置里必须有**动效三档开关**，并尊重系统「减弱动态效果」
- [ ] 首次使用要说清**「全程本地、不上传」**——这是产品的核心承诺
