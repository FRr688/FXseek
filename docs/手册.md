## 分发与依赖

本目录是**自包含**的：`venv/cpython-3.11/` 内已含 Python 运行时与全部依赖，
**整包拷贝即可运行，无需联网、无需 pip install**。

`requirements.txt` 仅用于记录版本、便于重建环境。已内置的依赖：

| 用途 | 包 |
|---|---|
| 模型推理 | `mlx` 0.32.2、`mlx-vlm` 0.7.1 |
| 图像 | `pillow` 12.3.0、`numpy` 2.3.5 |
| 文档解析 | `pdfplumber` 0.11.10、`openpyxl` 3.1.5、`xlrd` 2.0.2、`python-pptx` 1.0.2、`olefile` 0.47 |

> 注意：`venv/` 不是标准 venv（无 `pyvenv.cfg`），而是可重定位的独立运行时，
> 搬到任意路径都能正常工作。它原本不带 `pip`，如需重建依赖可先 `ensurepip`。

### 外部命令：一律走绝对路径，别写裸名字

`bin/` 里那份 `ffmpeg` / `ffprobe` / `fpcalc` 是随包分发的（`@loader_path/lib/*`
指到旁边的 `lib/`，所以搬走也能跑），`indexer._find_bin()` 按
**自带 > `$FFMPEG` 环境变量 > 系统 PATH 与常见位置** 的顺序解析，解析好的路径就是
`indexer.FFMPEG` / `FFPROBE`。项目自己的代码全部用它，只有一处例外踩过坑：

> 设置页「音频转写 → 测试连接」原本写的是 `subprocess.run(["ffmpeg", …])`。
> 终端里跑没问题 —— 开发机的 PATH 有 `/opt/homebrew/bin`；但**双击图标启动的
> 打包版走 LaunchServices，进程 PATH 只有 `/usr/bin:/bin:/usr/sbin:/sbin`**，
> 于是报 `[Errno 2] No such file or directory: 'ffmpeg'`：明明应用自己带了一份，
> 却因为写的是裸名字而找不到。修法两道：
> 1. `asr_desc._ffmpeg_bin()` 拿 `indexer.FFMPEG`（绝对路径），顺带把
>    `FileNotFoundError` 翻译成人话（「本机找不到 ffmpeg（试过 …）」）；
> 2. `paths.py` 在导入时 `_enrich_path()`：把**自带 `bin/`** 和
>    `~/bin`、`/opt/homebrew/bin`、`/usr/local/bin`、`/opt/local/bin`
>    补进 `PATH` 最前面（已有的不重复加）。这一条是为了**第三方库**：
>    `mlx_vlm` / `transformers` 里那些 `shutil.which("ffmpeg")`（解 m4a、aac
>    要走它，而本机录音正好产出 m4a）自己不会用 `indexer.FFMPEG`，
>    只能靠 PATH 找得到。

自检：`app.py` 启动时会打一行 `ffmpeg: …` —— `[内置 ✅]` 说明用的是随包那份，
`[系统 ⚠️]` 说明蹭的本机 ffmpeg，`[不可用 ❌]` 是两边都没找到（此时视频抽帧、
音频缩略图会受限）。想验证「干净 PATH」下的解析结果，可以
`env -i HOME="$HOME" PATH=/usr/bin:/bin ./venv/cpython-3.11/bin/python3.11 -c "import indexer; print(indexer.FFMPEG)"`。

## 支持的索引格式

| 类型 | 扩展名 | 说明 |
|---|---|---|
| 图片 | jpg/jpeg/png/gif/bmp/webp/tiff/heic | 可选 AI 描述生成（提升语义泛化） |
| 视频 | mp4/mov/avi/mkv/m4v/webm/flv/wmv | ffmpeg 自适应抽帧后编码 |
| 音频 | mp3/wav/m4a/aac/flac/ogg/opus/aiff | 文件名 + 可选 ASR 转写文本 |
| 文档 | txt/md/pdf/doc/docx/rtf/wps/csv/json/py/js/ts/html/htm/xml/yaml/yml/log | 文本切块（800 字/块，重叠 100）；`.doc/.docx/.rtf/.wps` 走系统 `textutil` |
| 表格 | xlsx/xlsm/et | openpyxl 读单元格；**`.et` 兼容 WPS 老式 OLE2/BIFF 格式**（走 xlrd） |
| 演示 | pptx/dps | python-pptx 读文本框与表格 |

**已知限制**：老式二进制 `.dps`（WPS 演示的 OLE2 格式）无开源解析器，
正文提取不出，仅按文件名收录；扫描版 PDF 同样提取不到文字（需 OCR 才能解决）。

**文档里内嵌的图片不会被编码**。索引文档时只抽取**文字**（pdfplumber / textutil /
openpyxl / python-pptx），文档内部的插图、扫描页图片都不会送进 WeMM 的图像编码器，
因此「以图搜图」搜不到「某个文档里的那张图」。对照实测：同一张图单独存成 `.png`
时相似度 **0.955**，把它塞进 PDF 后该 PDF 只有 **0.199**（远低于平衡门槛 0.40），
等于完全搜不到。如果扫描件本身需要被图片检索命中，得把页面导成独立图片再索引。

> 顺便修掉一个老 bug：以前后端文本预览有 `latin-1` 兜底，而 latin-1 能映射全部
> 256 个字节值、永不报解码错误，导致 PDF / WPS 等二进制文件被「成功」解成一屏乱码。
> 现在先按扩展名黑名单拦截，再对内容做嗅探（含 `\x00` 或非 utf-8/gbk/big5 则拒绝）。

## 文字检索的排序：为什么「空文档」曾经霸榜

**症状**：搜「太空」「美女」「小女生」，前三名永远是 `6.wps`、`未命名.et`、
`未命名.wps`、`未命名.dps`、`2.dps` —— 同一批文件，且与查询内容毫无关系。

**根因不是模型能力不足，是「没有正文的文档」在向量空间里成了万金油。**

这个库里 14 个文档有 7 个根本没有正文：

| 文件 | 能抽出的正文字数 | 内容 |
|---|---|---|
| `6.wps` | 2 | 「测试」 |
| `未命名.md` | 4 | 「你好吗啊」 |
| `2.dps` | 14 | 空模板 |
| `未命名.dps` / `.et` / `.wps` | 各 16 | 空模板 |
| `未命名-1.wps` | 18 | 空模板 |
| `未命名.html` | 5 | 去标签后只剩 `<title>Title</title>` |

这些文件（以及抽不出正文时的兜底占位文本）算出来的向量就是「一个空文档」的向量，
落在向量空间中心附近，**对任何查询都有 0.5~0.75 的余弦相似度**：

```
搜「唱歌」：未命名.html 0.754 | 6.wps 0.677 | 未命名.md 0.627   ← 全是空文档
          真正的答案 告白_FR.mp3 只有 0.503
```

模型本身没问题——它把「个人简历」和「比较.txt（模型对话记录）」在不同查询下排出了
不同顺序；出问题的是**三层策略里没有任何一条按正文长度降权**：`_is_meaningless()`
只认文件名关键词、体积 < 8KB 和纯色图，完全不看正文。

### 修法（三层各一处）

1. **索引期标注**（`indexer.py` 的 `iter_units`）：文档的 `meta` 里写入
   `text_len`（整篇正文字数）与 `no_text`（是否根本没抽出来）。老索引没有这两个
   字段，`_low_info_doc()` 就返回 `False`，不会误伤。
2. **HTML 去标签**（`indexer.py` 的 `_strip_html`）：`.html`/`.htm` 入库前先剥掉
   标签——空模板的标签本身就是「低信息但通用」的文本。
3. **排序降权**（`indexer.py` 的 `EMPTY_DOC_PENALTY = 0.35`）：
   - L2 深度语义：`total = sim * 0.35 + lex_b` —— 只罚语义分；
   - L1 向量检索：`_demote_low_info()` 对纯向量分乘 0.35（**注意 `search_vector`
     必须传 `with_chunk=True` 才会回填 meta**，否则拿不到 `text_len`，降权静默失效）；
   - **文件名命中的词法加成（`lex_b`）不罚**：搜「6」仍要能找到 `6.wps`。

### 顺带把「匹配门槛」重新标定

空文档被压下去后，本库的分数区间才露出来：**真正相关的素材 0.50~1.15，无关内容的
背景天花板只到 0.45**。所以（`ui.html` 的 `smartFilter`）：

- `balanced` 的绝对下限从 `0.40` 提到 `0.46`；
- 空页兜底加一道「及格线」`MIN_RELEVANT = 0.46`：若过滤后一条不剩、**且最高分本身
  连及格线都不到**，说明库里根本没有相关素材 —— 这时宁可给「没有找到相关素材」的
  空页，也不硬凑 3 条不相关的东西摆在最前面（旧行为就是硬凑，正是「不相关的还出现
  在前面」的直接原因）。

### 效果

| 查询 | 修复前 | 修复后 |
|---|---|---|
| 太空 / 宇宙 / 旅行 | `6.wps 64%`、`未命名.et 55%` … | **没有找到相关素材**（空页） |
| 美女 | `6.wps 64%`、`女孩.mp4 55%` … | **女孩.mp4 55%** 第一 |
| 小女生 | `6.wps 59%`、`未命名.md 51%` … | **女孩.mp4 51%**（唯一） |
| 唱歌 | `6.wps`、`未命名.md` … | **告白_FR.mp3 50%** 第一 |
| 财报 | `6.wps`、`未命名-1.wps` … | **季度经营分析报告.docx 68%**（唯一） |
| 小狗 / 夕阳 / 简历 | 空文档在前 | **正确结果 95%**（唯一） |

副作用（刻意保留）：`6.wps` 的正文就是「测试」两个字，现在**搜「测试」不会再把它
排在前面** —— 这种文档本身没有可检索的信息量，代价可接受；用文件名（搜「6」）依然
能找到它。

## 检索变慢：两个随库增长的隐藏成本（1.0.7）

**症状**：库里攒到 1500 个文件之后，搜「女人照片」「鸡翅」这种词**卡着不动**，
一等就是几分钟；而用文件名搜（L0）却秒出。所以第一直觉会是「向量检索扛不住了」，
其实恰恰相反。

### 先把账算清楚

先量一下各段的真实成本（库 9661 行、2048 维）：

| 环节 | 实测耗时 |
|---|---|
| 读全库 BLOB 进内存 | 0.51 s |
| **numpy 全库矩阵乘** | **0.087 s** |
| 纯 Python 逐行点积（1000 行折算全库） | **1.9 s / 查询向量** |
| `_is_meaningless()` 全库图片（1190 张） | **223 s** |

**向量检索本身只占 0.087 秒。** 慢的是它旁边那两个东西。

### 成本一：`_is_meaningless()` 在检索时开全库的图

这个函数的作用是给「纯色图 / 测试图」降权（分数 ×0.55），判断依据是
**把图缩成 64×64 灰度后算标准差**。问题在于，它被放在了对**全库每个候选**都调一次
的位置上。而这批图里有 **1167 张在外置卷上**，单张要 **187 ms**（几乎全是 I/O）——
1190 × 187 ms ≈ **223 秒**。比向量检索本身慢三个数量级。

**两道修复，缺一不可：**

1. **把判定移到 `probe_media_meta()` 里顺手做完，然后跟着落盘。**
   这个函数本来就要 `Image.open` 取 width/height/dpi，此时图已经开着，
   多算一次 64×64 标准差几乎免费。算出来的 `flat` 字段会跟着
   `media_meta_cache.json` 一起持久化 —— 之后检索**一次磁盘都不用碰**，
   纯字典读取。实测 `探测 200 次 0.00s`。
   > ⚠️ **改探测字段必须同时把 `_probe_key()` 的前缀 +1**（`v2|` → `v3|`）。
   > 老缓存里没有 `flat` 键，留着它会让每次都静默退回「现场开图」的老路 ——
   > 而且**看起来一切正常，只是慢**，这种 bug 最难查。

2. **第一趟只排序、不算分，用推导把候选砍到远小于全库。**
   降权是 **单向下调**（只会把分数乘 0.55，不会上调），所以：
   ```
   cutoff = hi_after × 0.42
   hi_after ≥ hi_before × 0.55      ← 最高的那个最多也才被罚 ×0.55
   ⇒ cutoff ≥ hi_before × 0.231
   ```
   于是「乘完 0.55 之后仍进得了结果集」的候选，分数必然 ≥ `hi_before × 0.231` ——
   低于这条线的**不管罚不罚都出局**，根本不需要开图。
   再补一道硬上限 `cap = max(top_k × 2, 200)`：
   > 光靠按比例的 floor 不够 —— 余弦分数在大库里会「挤在一起」，实测随机向量的
   > max 只有 0.05，按比例算出的 floor 低到几乎拦不住谁。所以必须封顶。

### 成本二：L2 深度检索的向量循环是纯 Python

```python
# 每行 × 每个查询向量 × 2048 次乘加
sim_main = max(sum(a * b for a, b in zip(q, v)) for q in qvecs)
```

9661 行 × 2048 维 ×（扩展词 × 两种指令）→ 单查询十几秒。
`fastsearch.search_vector`（L1）**早就用 numpy 了，L2 没有** —— 纯粹的历史遗留。

改成一次性堆成矩阵：

```python
_mat = np.vstack([np.frombuffer(b, dtype="<f4") for b in vecs])
sim_main_all = (_mat @ _Q.T).max(axis=1)      # 一次算完所有查询向量
```

AI 标签行（`chunk_idx >= AI_TAG_BASE`）单独做映射，也是整列向量化：

```python
_mapped = np.clip(fs.TAG_MAP_A * sim_main_all + fs.TAG_MAP_B, 0.0, 0.99)
sim_main_all = np.where(_is_tag, _mapped, sim_main_all)
```

> `map_tag_score(s)` 是「线性 + 夹到 [0, 0.99]」，所以能整列替换。
> **必须验证等价** —— 用一组边界值（负数、0、跨越 0.99 的大值）逐值比对，
> 确认向量化结果与标量版完全一致再换。

### 附带修掉的一个 400

空查询（或全标点、`expand_query` 拆不出词）会让 `qvecs` 为空，
而打分块直接取 `len(qvecs[0])` → `IndexError` → HTTP 400
`{"error": "list index out of range"}`。

```python
if not qvecs:
    return []
```

空查询本来就无从检索，返回空结果比抛异常合理。**注意**：这个 bug 在重写打分时
只是**换了个位置崩**，不是新引入的 —— 遇到这种「一改就崩」的现象，先确认
是你改坏的还是本来就坏的。

### 结果

| 场景 | 修前 | 修后 |
|---|---|---|
| 文字检索（缓存已热） | 223 s 起 | **0.1 ~ 5.5 s** |
| `探测 200 次` 耗时 | — | **0.00 s**（纯读缓存） |
| 首次 `POST /v1/browse`（冷） | 70 s | 一次性成本，之后 0.24 s |
| 重启后首次 browse | — | **0.35 s**（磁盘缓存持久） |

**结果完全没变** —— top1 和分数逐条一致（`女人照片` → `05_人物_839.jpg` 0.823；
`鸡翅` → ` (216).jpg` 1.015；`狗` → `小狗'(示例).png` 0.974）。这是这类优化唯一
可信的验收标准：**只许变快，不许变样**。

> **为什么全新安装的第一次检索还是慢一次**：`flat` 是**持久化**的，不是预先算好的。
> 冷缓存下第一次扫外置卷仍要付一次探测成本（`warm_meta_cache` 就是干这个的，
> 浏览器滚动时也在顺手预热）。**之后包括重启都是毫秒级。**

## 文字搜图片：为什么「有气球的画面」曾经搜不到

### 症状

库里有 `文件12.png`（一张彩色的宝宝照，画面里有红黄蓝绿一堆气球）。搜「气球」、
「有气球的画面」，结果里**根本没有这张图**，直接显示「没有找到相关素材」。

### 原因不在排序，在分数尺度

先说结论：**模型的排序其实是对的**，`文件12.png` 在三张图片里一直排第一。问题出在
「文字 → 图片」的原始余弦天生就低：

| 查询 | 正确图片的原始余弦 | 无关内容的背景分 |
|---|---|---|
| 有气球的画面 → 文件12.png | **0.382** | 0.38 ~ 0.45（比较.txt、元宵喜乐…） |
| 气球 → 文件12.png | **0.376** | 同上 |
| 海边的日落 → 夕阳图 | **0.374** | 同上 |
| 小狗 → 小狗在操场奔跑.png | 0.984（文件名命中） | — |

也就是说，**「文字→文档」的相关分是 0.50 ~ 1.15，而「文字→图片」只有 0.37 ~ 0.51，
两者跟「无关内容」的背景分完全重叠**。上一节为了把空文档挡掉而设的绝对门槛
（`MIN_RELEVANT = 0.46`）顺手把正确的图片也一起挡掉了 —— 任何**绝对分数线**都不可能
同时满足「太空给空页」和「有气球的画面要出文件12」。

### 修法：索引期给图片做视觉描述，把 text→image 变成 text→text

WeMM 是检索模型，对「短查询 vs 长文本」的区分度本来就弱（见上一节）。真正有效的做法
是**不要拿文字去撞图片向量，而是先把图片变成文字**。

设置页「AI 描述生成配置」就是这个能力。要注意两点：

1. **模型得有视觉能力**。填一个纯文本模型（只做代码/对话那种）给它图片，要么超时、
   要么胡编。本机 oMLX 上实测可用的是 `mlx-works:gemma-4-26B-A4B-it-oQ3e-mtp`（单张 50 秒）
   与 `Jackrong:Qwopus3.5-4B-Coder-oQ4-mtp`（名字里带 Coder，但确实能看图）。

   官方服务商不用自己记这些 —— 见下面「[服务商下拉](#服务商下拉只填-api-key-那种用法)」。

2. **打标不再在索引期自动跑**（2026-10 起）。索引只负责编码，标签由详情页的
   「立即打标签」按钮或设置里的「闲置时打标签」补上 —— 见
   「[打标签与转写太贵](#打标签与转写太贵可以手动补和闲着的时候慢慢补)」。
   老库里如果 `meta` 全是空的 `{}`，是因为当时那版还带着抽样开关，重建一次索引、
   再让它闲时补标即可。

配置改完（`data/settings.json`）**不需要重启**，`load_settings()` 每请求读盘。之后
重建图片索引即可：

```bash
# 必须先停服务：journal_mode 是 delete，边跑边写会锁库
pgrep -f "app.py --port 8231" | xargs -r kill -9; sleep 1
./venv/cpython-3.11/bin/python3.11 -c "
import indexer as ix, json
cfg = json.load(open('data/settings.json'))
ix.build_index(['<图片路径>'], force=True, ai_config={...})"
```

### 服务商下拉：只填 API Key 那种用法

「AI 描述生成」和「音频转写（ASR）」两张卡的第一行都是**服务商**下拉。选一个官方服务商，
接口地址与推荐模型自动带出，**用户只需要粘一个 API Key**；只有选「自定义 / 本地」时
才会露出「API 地址」那一行。

| 卡片 | 内置服务商 |
| --- | --- |
| AI 描述生成 | OpenAI · Google Gemini · 阿里云百炼（通义千问）· 智谱 GLM · 月之暗面 Kimi · 硅基流动 · xAI Grok · 自定义 / 本地 |
| 音频转写 | OpenAI · Groq · 硅基流动 · 自定义 / 本地 |

几个设计上的决定：

- **服务商本身不存盘。**每次加载拿已经存着的 `base_url` 反查预设表，对得上就是那个服务商，
  对不上（含空）就是「自定义」。好处是**老配置不会被改写** —— 本机 oMLX 那种
  `http://127.0.0.1:9977/v1` 打开就是「自定义」，地址原样躺在那儿。
- **切到「自定义」时不清空地址**，只把那一行露出来，方便在现有地址上改。
- **「获取列表」按钮就贴在模型下拉右边**，拉到的模型全部填进下拉，点开就能挑，
  不用手打。合成选项由 `setModelOptions(selId, current, models)` 负责，规则是
  **已存的那个模型名永远排第一并保持选中** —— 拉取失败、模型下架、换回别的服务商，
  原来存的名字都不会凭空消失（只会多出候选）。
- 占位符会跟着服务商变：官方服务商的 Key 框提示 `sk-…`，自定义的提示「本地服务可留空」。

留个心：**官方服务商里也有不带视觉的模型**（比如只做文本的）。选完服务商后模型名仍然可以改，
拿不准就点「获取模型列表」，挑名字里带 `vl` / `vision` / `4v` / `omni` 的那种。

### API Key 那个小眼睛

两个 Key 框右边都有一个眼睛按钮（`toggleKey(id, btn)` + `paintEye(btn, shown)`）：

- **只切 `input.type`**（`password` ↔ `text`），取值逻辑一个字没动 —— `saveAI()` / `saveASR()`
  读到的还是同一个 `$('#aiKey').value`。
- 开着的状态图标换成 `eyeOff`（带斜杠），颜色用 `var(--blue)`；
  关着用 `var(--text-3)` 的淡灰。两个色在深浅主题下都够对比度。
- 按钮**浮在输入框右内侧**（`.keywrap` + 绝对定位），不占额外宽度、也不推挤左边的说明文字；
  输入框留 `padding-right:38px` 给图标让位。
- 写的是 `type="button"`，放在表单里不会误触提交；带 `title` 与 `aria-pressed`，键盘可达。

⚠️ 顺手修了个**潜伏的暗色主题 bug**：`--accent` 只在 `:root`（亮色）里定义，
`body[data-theme="dark"]` 里没有覆盖 —— 于是暗色下 `.btn.primary` 是「近黑底 + 白字」，
糊在卡片上几乎看不见。现在暗色块里补了 `--accent:#3c4453; --accent-hover:#4a5262`。
（`--accent` 是当**背景**用的，不能简单换成浅色；这也是眼睛按钮改用 `--blue` 而不是 `--accent` 的原因。）

### 卡片为什么这么短：`details.fold`

这两张卡原来一眼望不到头（十好几行）。现在每张卡只留**一行必需项** + 动作行，
其余按性质收进折叠块：

| 卡片 | 默认露出 | 折进去的 |
| --- | --- | --- |
| AI 描述生成 | **一行四格**：服务商 · API 地址 · API Key · 模型+获取列表；下面 保存/测试；再下面 **待处理素材**（打标 N/M · 转写 N/M + 刷新）与 **等不及空闲**（补全标签 / 补全转写，蓝色） | **打标偏好**（提示词、标签上限）、**后台补全**（闲置开关、门槛、每轮上限） |
| 音频转写 | 同上 | **高级**（语言、时长上限） |

### 字段横排：`.fgrid`

「四行必需项」最初是四行（每行「标签在左、控件在右」），卡就竖着很长。
现在改成**一行四格**：同一个 `.fgrid` 网格里放四个 `.fgroup`，每格**标签在上、控件在下**。

```css
.fgrid{display:grid;gap:14px 16px;align-items:start;
  grid-template-columns:minmax(150px,1.15fr) minmax(150px,1.1fr) minmax(130px,.95fr) minmax(205px,1.5fr)}
.fgrid > .fgroup{display:flex;flex-direction:column;gap:8px;min-width:0}
.fgrid > .fgroup > .k{flex:none;font-size:0.8125rem;line-height:1.45;min-height:56px}
```

三个踩过的点：

- **列宽要显式给比例，别用 `auto-fit`。** 内容区 `.wrap` 恒为 880px（卡片内宽 838px），
  `repeat(auto-fit,minmax(210px,1fr))` 算出 3 列（268px × 3），四个字段就掉成 3+1 两行。
  改成显式四列比例后是 193 / 185 / 160 / 252px，最后一列（模型 + 「获取列表」按钮）
  手动给多一点，否则下拉框被按钮挤到只剩几十像素。
- **断点要按「视口 − 侧栏 230 − `.main` 内边距 80」折算。** 内容区本身封顶 880px，
  直接用 `max-width:1180px` 判断会把「窗口还宽、但内容区已经窄了」的情况漏掉。
  现在两处断点：`1140px` 落成两列，`760px` 落成一列。
- **标签区给 `min-height:56px`。** 服务商那行的说明文字有两种（长的那句会折成两行），
  不给下限高度的话，四格的控件会各自上下错位，一行看过去参差不齐。

折叠块的两个细节：

- **`summary` 右侧的徽标（`.fbadge`）**由空 `<span>` 占一个 flex 位，把状态文字和箭头一起顶到右边；
  内容为空时仍然占位，所以展开/收起不会左右跳。
- **「后台补全」的徽标会报数**（`renderIdleBadge()`）：有待处理的显示「N 个待补」并高亮，
  没有就写「全部就绪」，正在跑写「正在补全…」并变蓝。
  **但它故意不自动摊开折叠块** —— 一开始写了 `det.open = true`，用户点了「补全标签」发现
  自己刚收好的面板又被弹出来，当场说「不要去展开已经折叠的」。进度改在「等不及空闲」下面
  那行 `#bfHint` 里显示，跑着的时候给它加 `.hintline.hot`（品牌蓝），收着也能一眼看到。
- 「启用」开关从单独一行搬到了卡片标题右侧（`.seg` + `margin-left:auto`），
  一眼就能看到这张卡是开是关。

### 「待处理素材」和「等不及空闲」为什么不折进去

这两块一开始是和「闲置门槛 / 每轮上限」一起塞在「后台补全」折叠块里的，用户看了一眼就说
**「把等不及空闲单拎出来，不要折叠在里面」**、接着又说 **「把待处理这栏也拎出来，顾客可以观察
来决定是不是立马按等不及空闲的按钮」** —— 有道理，折叠块里放的是**配置**（改了下次才生效），
而这两块是**看状态 → 立刻动手**，藏在两层里等于多点一次、还容易找不到。

现在它们都在卡片正文里、**两个折叠块下面**（`<details>` 之外），顺序是「先观察、后动作」：

```html
</details>

<!-- 「待处理素材」与「等不及空闲」故意都留在折叠块**外面**：
     先看还剩多少（观察）→ 再决定要不要立刻动手（动作），这两步都不该藏在两层里。 -->
<div class="row" style="padding-top:4px">
  <div class="k">待处理素材<span class="sub">还没有描述/标签的图片视频，与还没转写的音频</span></div>
  <div class="acts" style="margin-top:0">
    <span id="idleStat" …>—</span>
    <button class="btn" onclick="loadIdleStatus()">…刷新</button>
  </div>
</div>
<div class="row">
  <div class="k">等不及空闲<span class="sub">立刻逐个补完，不用等上面那个门槛</span></div>
  <div class="acts" style="margin-top:0">
    <button class="btn accent" id="bfTagBtn" onclick="aiBackfill('start','tag')">…补全标签</button>
    <button class="btn accent" id="bfAsrBtn" onclick="aiBackfill('start','asr')">…补全转写</button>
    <button class="btn" id="bfStopBtn" onclick="aiBackfill('stop')" style="display:none">…停止</button>
  </div>
</div>
<div id="bfHint" class="hintline"></div>
```

配套地：`#bfHint`（「正在补标签 · 已完成 N…」/「上次补全：…」）也跟着搬到了折叠块外面，
而 `#idleHint`（「开着的时候：后台每 20 秒看一眼…」）留在折叠块里 —— 那句话是在解释闲置机制。

`#bfHint` 在跑着的时候会挂上 `.hintline.hot`（品牌蓝），所以**折叠块全程收着也能看到进度**：

```js
if(hint) hint.className = 'hintline' + (active ? ' hot' : '');
```

（这条是用户反馈后加的：最初 `renderIdleBadge()` 里写了 `if(active){ det.open = true }`，
点一下按钮就把用户手动收好的「后台补全」弹了出来 —— **「不要去展开已经折叠的」**，已删掉。）

放在折叠块**下面**而不是上面，是因为那行说明写的是「不用等**上面**那个门槛」，
门槛就在它正上方的折叠块里；摆上面这句话就说不通了。

**两个按钮用了 `.btn.accent`（品牌蓝）**，和旁边灰按钮区分开 —— 这是高频动作，得一眼能找到：

```css
.btn.accent{background:var(--blue);border-color:var(--blue);color:#ffffff;font-weight:600}
.btn.accent:hover{background:#3a68c4;border-color:#3a68c4}
/* 禁用态（正在跑）压暗但保持同色，不会突然变成灰按钮让人以为找错了 */
.btn.accent:disabled{background:var(--blue);border-color:var(--blue);opacity:.45;cursor:default}
```

（点击后两个按钮禁用 + `停止` 出现；跑完由 `loadIdleStatus()` 的 8 秒轮询复位 —— 实测
`backfill.active` 由 true 转 false、提示变成「上次补全：完成 0 个，全部成功。」、按钮重新可点。
注意闲置循环本身是 **20 秒一轮**，所以「待处理 0 个」时点下去也可能要等最多 20 秒才收工。）

**一句话：服务卡不并排。** 试过把 AI 和 ASR 摆成左右两列（`grid-template-columns:repeat(2,1fr)`），
结果每张卡只有 432px 宽，四格字段塞不下、又退回竖排，比原来还难看 —— 用户当场否掉了。
现在所有服务卡（AI / ASR / MCP 那三张）都是**同样 880px、上下堆叠**，
「并排」指的是**卡片内部的字段**排成一行。

外观那一屏同理：界面主题 / 字体大小 / 界面动效三行合并成一个 `.row.grid3`
（`repeat(3,minmax(0,1fr))`，900px 以下落成一列）。

**那三组按钮要让「组等宽 + 组内按钮等宽」。** `.seg` 天生是 `display:inline-flex`
（宽度随内容），所以「自动/白天/夜晚」「T小/T中/T大」「跟随系统/完整/关闭」三块的总宽各不相同，
右边缘参差不齐，选中态一亮更明显。用户的原话是**「按钮文字居中整齐摆放」**：

```css
/* 三段撑满各自的栏 + 组内按钮等宽：等宽之后文字天然居中，一行看过去才齐。 */
.row.grid3 .seg{display:flex;width:100%}
.row.grid3 .seg button{flex:1 1 0;justify-content:center;min-width:0;padding:6px 8px}
```

实测三块都是 **267px**、每块里三个按钮都是 **86px**、`justify-content:center`。
**注意别全局改 `.seg`** —— 卡片标题右侧那个「关闭/开启」开关、折叠块里的
「闲置时打标签」开关都靠 `inline-flex` 贴内容宽度，撑满会顶到不该去的地方。

另外，折叠体最后一行去掉了 `border-bottom`（`details.fold > .foldbody > .row:last-child`），
否则折叠加卡片本身就是双层边框，看着很脏。

### 关键：必须「逐标签存向量」+「去掉通用方向」

这两条是实测出来的，缺一个都不行。

**① 一个标签一条向量。** 把标签串 `"小女孩、绿色连衣裙、气球、…"` 整体编码成一条向量
时，查「气球」只有 **0.388**，而一段毫不相干的标签串「日落时分、太阳、鸟、湖泊、山峦」
也有 **0.339** —— 长文本把单个词稀释掉了，等于没有区分度。改成**每个标签单独编码**后，
「气球」对「气球」是 **0.9097**。

**② 减去「通用方向」。** 单个短词向量是 hub：32 个标签两两之间的「最佳错误匹配」中位数
高达 **0.725**，通用查询（太空/旅行/财务/会议…）对全部标签的最高余弦有 **0.600 ~ 0.717**。
所以直接用原始余弦，搜「太空」也会命中图片。

修法是取一组「通用词」的平均向量当基准方向，把它减掉（`indexer.TAG_CENTER_TERMS`，
22 个词：人物/自然/户外/场景/物体/内容/图片/照片/天空/建筑/食物/动物/植物/室内/室外/
颜色/装饰/背景/风景/日常/生活/环境），存 `normalize(v_tag − μ)`。居中后的点积：

| 类别 | 居中后点积 | 举例 |
|---|---|---|
| 真匹配（查询=标签本身） | **0.454 ~ 0.522** | 气球 0.494、泰迪熊 0.522、小狗 0.482 |
| 句子式查询（应该命中） | **0.286 ~ 0.478** | 有气球的画面 0.478、一张狗的图片 0.286 |
| 无关查询（应该落空） | **0.000 ~ 0.097** | 太空 0.041、财务 0.021、会议 0.037、旅行 0.055 |

空档在 0.097 与 0.286 之间，阈值取 0.20 就能干净分开。

### 映射回「文档分数」尺度

分隔线定完还要让标签分跟文档分可比，否则界面上的门槛（0.46）没有意义。
`fastsearch.map_tag_score()` 把它线性映射：

```
TAG_RAW_FLOOR = 0.20            # 居中点积低于此值＝无关
TAG_MAP_A = 1.15
TAG_MAP_B = 0.45 - 1.15*0.20 = 0.22
映射后 = clamp(1.15 * raw + 0.22, 0, 0.99)
```

映射后：真匹配 0.74 ~ 0.82，句子式查询 0.55 ~ 0.77，**无关查询 ≤ 0.33（稳稳落在 0.46
门槛之下）**。

### 实现位置

| 位置 | 作用 |
|---|---|
| `indexer.py` `AI_TAG_BASE = 9000` / `AI_DESC_IDX = 9500` | 标签向量占用的 chunk_idx 区段 |
| `indexer.py` `tag_center_vec()` | 懒加载并缓存那 22 个通用词的平均向量 μ |
| `indexer.py` `_center_text_vec()` | `v = embed(DOC_INSTRUCTION)` → `normalize(v − μ)` |
| `indexer.py` 图片分支 | 每个标签一条记录，描述另占一条 |
| `fastsearch.py` `map_tag_score()` | 居中点积 → 可比分数 |
| `fastsearch.load_matrix()` | 多取一列 `chunk_idx`，`_MAT["chunks"]` |
| `fastsearch.search_vector()` | `chunk_idx >= 9000` 的行套用映射 |
| `indexer.py` L2 聚合 | `idx >= AI_TAG_BASE` 时 `sim_main = map_tag_score(sim_main)`，`sim_ext = 0` |

> `sim_ext` 必须清零：映射常数是按 `QUERY_INSTRUCTION` 那一份标定的，无指令那一份
> 尺度不同，混进来会把无关查询抬过门槛。

### 顺带修的一个「下沉」问题

`indexer.search` 里 L1（向量层）判断「结果够好、不用再跑深度模型」用的是
`score_quality(res, min_count=2, min_top=0.30)`。0.30 比界面的 0.46 低 —— 于是会出现
**L1 拿到 0.362 就认为够好、直接返回，前端再按 0.46 全部隐藏，页面空白** 的情况
（「一张狗的图片」就是这样：L1 给 0.362 空页，L2 深度语义能给 0.937）。

修法：把 L1 的接受下限抬到跟界面一致。

```python
# indexer.py L1 —— 跟 ui.html 的 MIN_RELEVANT = 0.46 对齐
if fs.score_quality(res, min_count=2, min_top=0.46):
```

### 效果

| 查询 | 修之前 | 修之后 |
|---|---|---|
| 有气球的画面 | 空页 | **文件12.png 77%**（唯一） |
| 气球 | 空页 | 文件12.png 79% |
| 泰迪熊 | 空页 | 文件12.png 82% |
| 海边的日落 | 空页 | 夕阳西下唯美风景图.png 65% |
| 一张狗的图片 | 空页 | 小狗在操场奔跑.png 94% |
| 小女生 | 空页 | 文件12.png 60% |
| 太空 / 财务 / 会议 / 旅行 | 空页 | **仍然空页**（标签分 ≤ 0.33） |
| 美女 | 女孩.mp4 55% | 女孩.mp4 55%（不变） |
| 财报 | 季度经营分析报告.docx 68% | 不变 |
| 小狗 / 简历 / 夕阳 | 95% | 不变 |

### 代价与前提

* 每张图片多出 10 ~ 13 条向量（11~12 个标签 + 1 条描述），索引耗时从「瞬间」变成
  **单张 12 ~ 34 秒**（要跑一次视觉模型）。库里图片多时这一步要花时间，可以只在
  `ai_sample_ratio < 1.0` 下给一部分图做。
* **没有配视觉模型时这套完全不起作用**：`meta` 里没有标签，就没有 9000+ 的向量，
  检索行为跟以前一模一样（不会报错，只是文字搜图片仍然弱）。
* 「以图搜图」是另一条路，它本来就很准（图片向量直接比对），不依赖这套。

## 视频也能用文字描述搜到

同一套 AI 描述机制也用在视频上，但**不是逐帧打标**——那样一个 10 分钟的视频要调几千次模型，
本机算力根本扛不住。做法是**把关键帧拼成一张九宫格，交给视觉模型看一次**：

```
视频 → 抽关键帧（沿用「视频抽帧」密度设置）
     → 取 9 张均匀分布的代表帧，缩放到 320×320，加 6px 白边拼成 984×984 的 3×3 拼图
     → 一次视觉调用（prompt 说明「这是同一段视频按时间顺序抽取的关键帧，从左到右、从上到下」）
     → 得到描述 + 标签 → 与图片一样，逐标签存 9000+ 号向量（做同样的通用方向居中）
```

**代价与视频长度无关**（永远只看 9 张图）：实测 `女孩.mp4` 14.3 秒、`元宵喜乐（FR).mp4` 7.7 秒、
`clip_95s.mp4` 5.7 秒。效果：

| 查询 | 结果 |
| --- | --- |
| 拍手 | 女孩.mp4 **0.847** |
| 彩色测试图 | clip_95s.mp4 **0.878** |
| 元宵节贺图 | 元宵喜乐（FR).mp4 0.593 |
| 有气球的画面 | 文件12.png 0.699 · 女孩.mp4 0.502 |

标签向量**只写一份**（`chunk_idx = 0` 的那一帧），否则视频每一帧都会把同一批标签重新写一遍、
白算几十倍。

两点说明：

* 「视频抽帧」的密度设置会影响九宫格取到哪些帧；`video_max_frames` 太小可能取不出 9 张，
  这时会用实际帧数拼（`cols = ceil(sqrt(n))`），一样只调一次模型。
* 素材详情面板里，图片和视频都会显示「AI 描述 + 标签胶囊」，视频那栏会额外标一句
  **（由关键帧拼图生成）**，提醒你这描述来自 9 张代表帧、而不是逐帧看过的。描述正文只取
  主句——`关键物体：/场景：/类别：` 这些行已经变成标签胶囊了，再贴在正文里等于重复一遍。

## 打标签与转写太贵？可以「手动补」和「闲着的时候慢慢补」

整条链路里只有两件事要花算力：**视觉模型打标签**（一张图/一条视频实测 **11 ~ 14 秒**）和
**语音识别转写**（一首 3 分半的歌实测 **18 ~ 34 秒**）。文件夹一多，「加进来就全量跑」会让人
不敢加目录。

所以从 2026-10 起，**索引期既不打标也不转写**（`indexer.py` 的 `build_index` 开头直接把
`ai` / `asr` 置成 `None`，签名里保留 `ai_config` / `asr_config` 只为兼容旧调用方）。一次模型调用
× 几千个文件会让索引无声地卡上几小时；改成由**详情页按钮**和**闲置守护线程**分摊。

同时**删掉了「智能抽样打标」**（原来的 `ai_strategy` / `ai_sample_ratio` / `ai_max_per_batch`）——
抽样会造成「同一批素材里有的能搜到、有的搜不到」，很难解释。现在的目标是**最终全部打标、全部转写**，
只是把时间从「集中一次」摊成「闲时 + 你点一下」。

### 一、详情页的「立即打标签」/「立即转写」

图片或视频没有 AI 描述时，详情面板的「AI 描述」位置不是空白，而是一张提示卡：

```
这张素材还没有生成描述与标签 ——
用文字是搜不到它的（只能靠以图搜图/文件名命中）。
[ 立即打标签 ]
用设置里的视觉模型给这一张生成，约 10~60 秒；生成后立刻可以用文字搜到它。
```

音频或视频没有转写时，「转写内容」位置同理：

```
还没有转写 —— 里面的歌词或说话内容现在还搜不到（只能靠文件名与指纹匹配）。
[ 立即转写 ]
用设置里的语音识别服务转写这一段，几秒到几十秒；转写后立刻可以按歌词/台词搜到它。
```

两个按钮分别走 `POST /v1/ai/tag` 与 `POST /v1/asr/transcribe`，都是**同步返回**
（靠 `ThreadingHTTPServer` 每请求一线程，不挡别的操作）。

`POST /v1/ai/tag` **只做三件事**（不会重抽视频帧、不会重新编码）：

1. 调一次 `ai_desc.describe_image`（图片＝原图；视频＝`_video_contact_sheet()` 那张九宫格）；
2. 把 `ai_description` / `ai_tags` / `ai_model` 一起 `UPDATE` 进该文件所有
   `chunk_idx < 9000` 的行（只改 meta，不动向量）；
3. `DELETE ... WHERE chunk_idx >= 9000` 后重建 9000+i 与 9500 号标签向量。

`POST /v1/asr/transcribe` 做的略有不同：

1. 先 `_has_audio_stream(path)` 探一下有没有音轨（ffprobe）——没有就直接写 `asr_none` 返回，
   比分不出音轨再让服务端报 500 快得多（实测 0.17 秒 vs 一次完整往返）；
2. 超过设置里的「单文件时长上限」写 `asr_skip: "too_long"`（默认 **0 = 不限**，见下）；
3. 调 `asr_desc.transcribe()`，把 `asr_text` / `asr_model` 并进所有 `chunk_idx < 9000` 的行；
4. **音频**还要重编码一次 0 号向量——因为音频的转写文本是拼进那条向量的（视频不用，视频帧走
   图像嵌入，转写文本只进 meta 供关键词检索用）。重编码失败只打印一行日志，文字照样入库。

没索引过的文件会被挡下来（提示「先刷新索引」）——因为标签向量和转写都要挂在已有的帧/分块上。

#### 「单文件时长上限」：默认改成不限，以及那个永远不重试的坑

这个设置本身很简单，但它踩过一个**看起来像「转写坏了」的坑**，值得记一笔。

**现象**：用户报「稍微长点的音视频，启动不了 ASR 模型进行转写」。实测一个 37.7 分钟
的 FLAC，4.1 秒就返回了：

```
{"ok": false, "message": "时长 2260 秒，超过设置的上限 600 秒"}
```

**根因有两层，第二层才是真麻烦**：

1. `asr_max_duration` 默认 **600 秒**，而这个判断在**发请求之前**。所以整张专辑 /
   演唱会现场的 FLAC（常见 35~65 分钟）一律被秒拒 —— **ASR 模型根本没被调用过**，
   用户看到的「启动不了」其实是「压根没让它启动」。本机实测：同一个文件把上限设成 0
   之后**一次就成功了**（373.7 秒、5074 字、文本干净）。

2. 拒掉之后写了一个 `asr_skip: "too_long"` 标记，而**判断「要不要重试」的两处代码
   都只问「这个标记在不在」，不问「当初是哪条上限挡的」**：

   * `_asr_pending()` —— 增量索引时决定跳不跳过（indexer.py）
   * `asr_status()` —— 界面上那份「待转写清单」，**它连 `max_duration` 都没接**

   于是用户就算把上限调到 0，那些长文件也**永远停在跳过状态**，一次都不会再试。
   这比第 1 层更糟：第 1 层至少改了设置能救，第 2 层是**改了也没用**。

**修法**：

| 改动 | 位置 |
| --- | --- |
| 默认从 600 改成 **0（不限）** | `app.py` 的 `DEFAULT_SETTINGS` |
| 一次性迁移：把盘上冻结的 `600` 搬成 `0`，并记进 `_migrations` | `app.py` 的 `_migrate_settings()`，由 `load_settings()` 调用 |
| 两处判断合成一个共用函数 `_asr_skip_lifted(m, max_duration)` | `indexer.py` |
| `asr_status(db_path=None, max_duration=None)` 新增参数；`app.py` 包一层 `_ix_asr_status()` 把当前上限传进去 | `indexer.py` / `app.py` |
| 跳过时多记一条 `asr_skip_dur`；转写成功时把 `asr_skip` / `asr_skip_dur` / `asr_none` 一起清掉 | `indexer.py` 的 `transcribe_file` 与 `do_index` 两处 |
| 报错文案指名道姓：「…超过「设置 → 智能服务 → 音频转写」里的时长上限 N 秒，把那个数字调大、或填 0 表示不限」 | `indexer.py` |

**为什么迁移要单独做**：`load_settings()` 是「代码默认值 ← 用户已存的值」，
用户那份 settings.json 里**冻结着老默认值 600**。只改 `DEFAULT_SETTINGS` 对他
**完全无效** —— 必须把冻结的那个 600 也搬走。迁移跑过一次就记进 `_migrations`，
所以**用户之后自己故意填 600 不会被再动**（实测已验证）。

**判据表**（`_asr_skip_lifted`，已实测）：

| meta 状态 | 上限 600 | 上限 0 | 上限 2400 |
| --- | --- | --- | --- |
| `asr_skip: too_long`，duration 2259.8 | 跳过 | **重试** | **重试** |
| `asr_skip: too_long`，duration 3903.6 | 跳过 | **重试** | 跳过（仍超） |
| `asr_skip: too_long`，没记 duration | 跳过 | **重试** | **重试** |
| `asr_none`（确认没语音） | 跳过 | 跳过 | 跳过 |
| `asr_skip: "其他原因"` | 跳过 | 跳过 | 跳过 |
| 已有 `asr_text` | 跳过 | 跳过 | 跳过 |

只有 `too_long` 这一种理由能被放宽救回来；`asr_none` 与时长无关，永远不该重试。


### 二、设置里的「闲置时处理」

`设置 → 智能服务` 上有四个值（默认 **开 / 开 / 5 分钟 / 10 个**）：

| 设置 | 含义 |
| --- | --- |
| 闲置时打标签 | AI 打标的总开关（还要 `ai_enabled` 也开着才生效） |
| 闲置时转写音频 | ASR 的总开关（还要 ASR 服务配置好） |
| 闲置多久后开始 | 这段时间内**没有任何 HTTP 请求**才动手（分钟） |
| 每轮上限 | 一段连续空闲里最多处理几个（0 = 不限） |

守护线程 `idle-worker` 每 20 秒醒一次，判定链是：
总开关 → 配了服务 → **没在建索引、没在打标、没在转写**（否则作废本轮窗口）→ 空闲够久 →
本轮还没到上限 → 取一个待处理的开工。失败退避 120 秒。

**打标签与转写轮流取**（`_IDLE["turn"]` 每完成一个就 +1，按奇偶决定这次先看哪个队列）。
不轮流的话，待打标的图片一多，转写会被一直饿着。

**一次只跑一个**，而且只要有人发起请求（`Handler.handle_one_request()` 每请求记一次
`_STATE["last_req"]`），下一轮就重新计时——所以在用的时候它不会来抢算力。一轮的计数按
`int(time.time() // max(needed, 60))` 的窗口号归零，不会「睡一晚上跑满全库」。

设置页那一行会实时显示 `打标 6 / 6 · 标签齐了 ｜ 转写 6 / 6 · 转写齐了`（并发读
`GET /v1/ai/status` 与 `GET /v1/asr/status`，只在「确实有活在干」时才 8 秒轮询一次——
写成 `setTimeout(fn, 0)` 会变成死循环猛刷接口）。

### 「打标了没 / 转写了没」的判据

- **打标**：看有没有 `chunk_idx >= 9000` 的向量行，**不看 meta**。手改过 meta 的老库不会被误判成
  「已打标」；反过来，删掉标签向量就等于「没打标」，重建一次即可。
- **转写**：看 meta 里有没有 `asr_text`（有内容）、`asr_none`（没识别到语音）或 `asr_skip`
  （超时长被跳过）三者之一——后两种也算「处理过了」，不会反复重试。

### 三、等不及空闲？点「立即补全」

上面两条路都有前提：详情页要你**一个个点**，闲置线程要你**真的闲够 N 分钟**。可默认
`idle_minutes = 30`，而你又一直在页面上操作——那个条件可能几天都凑不齐，新加进来的图片就
一直没标签、用文字搜不到它。

所以设置页「智能服务」里多了一行 **「等不及空闲？」**：

```
等不及空闲？
索引期不打标（几千张图会把索引卡住几小时），所以新加进来的图片
要等上面那个「闲置」条件。急着用就点这里，立刻逐个补完。
              [✨ 立即补全标签]  [🎤 立即补全转写]  [× 停止]
上次补全：完成 1 个，全部成功。
```

**它只是把「闲置」这个门槛去掉，活还是那个闲置线程干的**（`_ai_idle_loop()` 里的
`man = _IDLE.get("manual")` 分支）：

| | 闲置模式 | 立即补全 |
| --- | --- | --- |
| 空闲门槛 | `idle_minutes` 分钟 | **0**，立刻开始 |
| 每轮上限 | `idle_batch` | **0**，一直跑到没得跑 |
| 谁干活 | 同一个 `ai-idle-tagger` 守护线程 | 同一个 |

**为什么不新开一个线程**：两条路同时开工会抢 GPU，转写和打标互相拖慢，还可能同时往
`index.db` 里写。复用同一条循环，`_STATE["ai_tagging"]` 那个「一次只跑一个」的护栏自动生效。

实测（6 个待打标文件，其中 3 个是视频）：

```
tagged=1 pending=6  →  点「立即补全标签」
  [ 90s] tagged=4 pending=3 done=3 failed=0
  [212s] tagged=7 pending=0 done=6 failed=0   finished
日志：[立即补全] 完成 女孩.mp4 · 12 个标签 · 14.4s
      [立即补全] 完成（成功 6 个、失败 0 个）
```

没有待处理的素材时它会**立刻结束**并提示「没有待处理的素材」，不会空转。
完成数 `done`、失败数 `failed` 会一直留在 `_IDLE["manual"]` 里，所以按钮复位后那行提示
仍然写着「上次补全：完成 N 个」，你能确认它真的干完了。

**注意**：`last_path` 是上一次处理留下的，页面只在 `running == true` 时才显示
「正在处理「文件名」」——否则会把一个早就处理完的文件说成正在处理。

## 搜索结果里的视频，封面就是「命中的那一帧」

视频在索引期是**逐帧**编码的（`indexer.py` 的 `iter_units` 视频分支：
`for idx, (img, ts) in enumerate(_video_frames(path)): yield ("video", idx, {"timestamp": ts}, ...)`），
所以每一帧都是索引库里一条独立向量、`meta` 里带着自己的时间点。既然如此，
搜索结果里的视频就不该统一显示「中间那一帧」：

* **封面** → `/v1/thumb?path=…&t=<命中帧秒数>`，显示的就是检索命中的那一帧；
* **悬停预览** → `<video data-start="<命中帧秒数>">`，从命中帧开始播，而不是从片头；
* **双击预览** → 浮层播放器顶部标一句「从 00:04 开始播放（匹配帧定位）」。

以图搜图时这一条是精确的：拿第 4.2 秒的画面去搜，回来的 `女孩.mp4` 命中帧就是 **4.21s**
（换第 8.5 秒的画面去搜，命中帧跟着变成 **8.67s**）。文字检索因为命中的通常是
「整段视频的 AI 标签向量」，帧位置是**用同一个查询向量在该视频自己的帧向量里再排一次序**
得到的——它答的是「这段视频里，哪一帧最接近你搜的东西」，不是「这一帧一定能证明这条命中」。

### 踩过的三个坑

**① 「最匹配帧」曾经永远定位到第 0 帧。** `fastsearch.search_vector` 原本拿
`chunk_map` 的**列表下标**去对齐矩阵行号，可矩阵的行序是 `items` 的 rowid 顺序、
而那条 SQL 的返回顺序是另一回事——AI 打标时 chunk 0 被 `INSERT OR REPLACE` 重写过，
两者就此错位。实测 `女孩.mp4` 的矩阵行 chunk 顺序是
`[0, 9000…9010, 9500, 1, 2, …, 17]`，而 `chunk_map` 是 `[0, 1, …, 17]`，
错位后 `pos` 越界、兜底成 `best_idx=0, best_meta={}`，于是每张视频封面都钉在片头。
现在改成**按 `chunk_idx` 建字典**，并把「最匹配帧」限制在真实帧行
（`chunk_idx < AI_TAG_BASE`）里选——AI 标签向量是整段拼图生成的，不对应任何一帧。

**② 同一个查询，`tier=vector` 和 `tier=deep` 定位到不同的帧。** L1 只拿得到缓存的那一份查询向量
（`QUERY_INSTRUCTION`），L2 的 `sim_main` 却是「含无指令那一份、以及扩展词」的最大值。
两边口径不一致，搜「拍手」在 `vector` 下定位到 0.25s、`deep` 下定位到 5.2s。
现在帧定位统一用 `sim_frame = dot(qvecs[0], v)`（主查询向量），**分数仍取全局最大值**
不受影响。顺带发现 0.25s 那一帧才是对的——那个瞬间小女孩双手合在胸前，
正是「拍手」，5.2s 是「挥手」。

**③ 首次悬停不生效。** `hoverPlay` 只在「视频已经加载过」的 `else` 分支里读 `data-start`，
第一次悬停走的是加载分支，于是第一次永远从 0 开始、第二次才跳到命中帧。
现在 `loadedmetadata` / `loadeddata` 都调一次 `seekStart()`。

> 浏览模式（没在检索）不受影响：没有 `matched_timestamp` 就不带 `&t=`、也不带 `data-start`，
> 封面仍是默认的中间帧、预览从 0 播。

## 麦克风录音检索（指纹优先 → 意图分流 → 双路兜底）

点麦克风录音 → 停止 → 点「搜画面」，后端按**三步**决定怎么搜。

### 检索范围：三条路各搜什么，是一张固定的表

| 你做的事 | 判定 | 走哪条路 | **检索范围** |
|---|---|---|---|
| **普通说话** | 说话 | 本地 ASR 转文字 → 语义检索 | **全库**（图片/音视频/文档都参与，`kind=null`） |
| **唱歌 / 哼唱** | 哼唱 | 声学指纹 → 没命中再用 ASR 转出的歌词搜 | **仅音频 + 视频**（`kind=["audio","video"]`） |
| **原音外放** | 指纹精确命中 | 声学指纹（连 ASR 都不跑） | **仅音频 + 视频** |

唱歌这条为什么必须把 ASR 兜底也锁在音频+视频：哼唱/唱歌的转写是**歌词**，歌词只可能
出现在音视频的 ASR 转写里。早先这里没锁范围，于是搜出一串无关的 `6.wps`、`未命名.et`
（实测提示行是「找到 4 项」里混着 3 个文档）。锁上以后同一个查询只剩 3 条音视频。

范围是怎么传下去的：前端 `ui.html` 的 `voiceSearchAsText(text, conf, {kind: AV_KINDS})`
把 `kind` 交给 `doSearch(opts)`；`/v1/search` 的 `kind` 参数**同时接受单个字符串和数组**
（`fastsearch._kind_sql` 会展开成 `kind IN (?,?)`），所以「音频+视频」是一个请求就能完成，
不需要搜两遍再合并。提示行会写明「· 仅音频+视频」。

### 第一步：指纹优先（无条件先跑）

不管听起来像说话还是哼唱，先拿这段录音去 `fingerprint.search_robust()` 查一遍
音频与视频。命中就说明「这段录音就是库里某个文件的同一段」，直接出结果，
**连 ASR 都不跑**（指纹 0.1~0.3 秒，ASR + 语义检索要几秒）。

为什么必须放在最前面：意图判别是纯声学启发式，而**把原曲外放给麦克风听**这种
「完整混音 + 歌词 + 伴奏」的片段恰好卡在阈值上——实测库里原曲的干净截取
`hum_score` 只有 0.44~0.49（阈值 0.46），连 15 秒的干净截取都会判成「说话」。
一旦判成说话就走 ASR，而原曲有歌词、ASR 转得出文字，于是**指纹永远轮不到**
（指纹兜底只在 ASR 转不出字时才触发），等于没参与。指纹优先从结构上堵掉这个漏洞。

#### 为什么不能用「单次比对 + 一个分数阈值」

外放原曲给麦克风听，中间隔着**房间混响 + 麦克风频响 + AGC**，实测（本机扬声器
→ 外置麦克风，素材为晓_FR.mp3 第 40~52 秒）：

| | 逐位严格比对的最佳相似度 |
|---|---|
| 真·外放原曲（音量 18% 与 70% 各测一轮） | **0.61 ~ 0.74** |
| 无关音频（说话 / 合成哼唱 / 房间噪声） | **0.71 ~ 0.79** |

**两者完全重叠**——把外放音量从 18% 提到 70%（RMS 提高 32 倍）分数一点没涨，
说明退化不是信噪比问题，而是混响把指纹在时间轴上「糊」开了。所以任何单一阈值
都必然要么漏真、要么收假。

#### 实际用的三层判据（`fingerprint.search_robust`）

1. **逐帧容忍**：比对时允许指纹在时间轴上错开 ±2 帧（混响会把相邻帧互相污染）。
   实测把真阳性从 0.65 抬到 0.73~0.76，但假阳性也跟着抬到 0.71，所以单靠它不够。
2. **多窗口投票**：把录音切成若干约 4 秒的窗口（50% 重叠、最多 12 窗、短录音自动
   用小窗），**每个窗口单独选一个 top1**，要求同一个文件在**每一个**窗口里都排第一。
3. **对齐一致性**：`base = 库内偏移 − 窗口起点`，真匹配时每个窗口算出的 base 应当
   恒定（要求 ≥2/3 的窗口落在中位数 ±4 帧内）。假阳性是「哪首歌碰巧分了最高」的
   随机事件，base 会乱跳（实测假阳性出现 422 / 498 / 937 / 1193 帧的抖动）。

在本机全部实测样本上（20 条真阳性 + 7 条假阳性）：**7 条假阳性全部拒绝，16 条真
阳性接受**；剩下的 4 条（都是音量只有 18% 的 11.6 秒录音、只有 2/3 窗口一致）会
回落到 ASR 走歌词检索，用户仍能搜到歌，只是慢一点、走的是另一条路。

#### 一个更隐蔽的坑：fpcalc 默认只指纹前 120 秒（已修）

`fpcalc` 的 `-length` **默认是 120 秒**，不显式放开的话任何超过 2 分钟的音视频都只
会为「前 2 分钟」建指纹。实测 207 秒的歌默认只存 **948** 项，加 `-length 86400`
后是 **1650** 项——**用户播放 2 分钟之后的段落永远匹配不到**。`fingerprint.py` 已
显式传 `-length 86400`，并重建了全部指纹。

附带确认：fpcalc 的帧数满足 `n ≈ (时长 − 2.7 秒) / 0.1238`——开头约 2.7 秒是算法
预热，不出指纹。因此每帧固定 **0.1238 秒**，窗口大小按帧数定死，不要用
「文件头时长 ÷ 帧数」去推算（实测 `hum_real.wav` 报 7.65 秒却只有 40 帧，会把窗口
切错）。

命中时识别条显示「听出原曲：指纹精确匹配 · 文件名 把握 N%」，并给一个「改用文字搜」
的出口。用户明确点了「改用文字搜」时（`force='text'`）跳过这一步，尊重他的选择。
诊断用：请求体里带 `keep: "<服务器本地路径>"` 可把这次录音另存一份用于事后分析
（默认不留盘）。

### 「同一首歌」关联：指纹跨不过去的场景，用索引期的关系补上

指纹是**同一段录音**级别的匹配。真实例子：`元宵喜乐（FR).mp4` 拿 `忆_FR.mp3` 的
第 **6~19 秒**当背景音乐，而用户上传的 `测试.mp3` 是该曲第 **84.25~91.55 秒**
——同一首歌的两段不同录音。实测：

| 比法 | 结果 |
|---|---|
| 指纹（视频 15~30s vs 忆_FR） | 0.751（跨段匹配只有 0.69，低于无关歌曲噪声基线） |
| 谐波色度（视频 15~28s vs 忆_FR **6~19s**） | **0.476** |
| 谐波色度（视频 15~28s vs 忆_FR **84~97s**） | 0.072 |

差 6~20 倍，即**视频里放的确实是这首歌，但是另一段**。所以「拿歌曲中段去搜、想搜出
用了这首歌开头的视频」在指纹层面**原理上做不到**。

**伴奏分离也救不回来**（用户问过，实测否）：装了 demucs 4.1.0 跑
`--two-stems=vocals`，同一段对比——原始混音 **0.751**、分离出的伴奏
`no_vocals` **0.727**、人声 `vocals` 0.714；整段 12~46s 从 0.682 掉到 0.631。
分离模型引入的伪影抵消了收益。轻量分离同样无效：中置 (L+R) 0.751（与原始相同）、
侧向 (L−R) 0.604、REPET 中值滤波 1.5s/3s/6s = 0.745/0.722/0.630。

**解决办法是索引期建立「同一首歌」关系**（`fingerprint.detect_links`）：
把每个音视频的指纹切成约 5 秒的窗口，每窗各自去目标曲里找最佳位置——真关联的
**底对齐（目标位置 − 窗口起点）恒定**，假关联则乱跳。判据三条：

1. 至少 **3** 个窗口指向同一目标，且底对齐落在 **±3 帧**内；
2. 这一簇的平均相似度 ≥ **0.70**；
3. ★ 这一簇的均分要比**全部窗口的均分**高出 **≥0.05**。

第 3 条是实测逼出来的：本库三首歌同专辑、结构相近，**每一对**都能凑出 3 个底对齐
一致的窗口（0.649~0.719），光看「有一致簇」全是假阳性；而真关联的簇显著优于全局
（忆_FR→元宵 +0.071、元宵→忆_FR +0.092），假关联最多只有 +0.027。加上这条之后，
本库 12 个有序对里**只留下真正的那 2 条**，0.3 秒扫完。

命中之后：检索命中该曲的任意一份载体，就会把**同一首歌的其它载体**一并带出来，
带 `linked: true` 与 `link_note: "同一首歌"`，前端显示紫色的「同一首歌」徽标
（与绿色的「N% 匹配」区分开），**且不参与匹配门槛**——它的分数是关联置信度，
不是这次查询的相似度。实测上传 `测试.mp3`：

```
忆_FR.mp3          audio  0.989   (84.25s)
元宵喜乐（FR).mp4    video  0.79    ←同一首歌（与 忆_FR.mp3）
```

索引完成后会自动重算关联（秒级，只比指纹切片、不解码音频）；也可手动触发：
`GET /v1/links` 查看当前关联，`POST /v1/links {"rebuild": true}` 重算。

### 第二步：意图分流（指纹没命中时才需要）

`voice_intent.py` 判断这段录音**是说话还是哼唱**，再走两条完全不同的路：

| 判定 | 依据（音高特征） | 走哪条路 |
|---|---|---|
| **说话** | 音节调制强、音高不稳 | 本地 ASR（Qwen3-ASR）转成文字 → 塞进检索框走语义检索；识别条上显示转写文字，可点「改文字」手动纠正后回车重搜 |
| **哼唱** | 长时段音高极稳、调制弱 | Chromaprint **声学指纹**匹配（此时用更宽的阈值，因为严格的已经在第一步试过了），结果只保留音频与视频 |

分流用纯 numpy 实现（`voice_intent.py`，无额外模型）：自相关求 F0，算「长稳定音高
时长」与「2~10Hz 包络调制深度」为主判据，配合过零率、高频占比、谱平坦度，得到
`hum_score`，阈值 0.46。说话样本 0.27~0.30、哼唱样本 0.62~0.99，判别间隔 0.31；
纯静音、粉红噪声、短于 0.8 秒的录音都会被拒绝并给出提示。ASR 未启用时不会静默
失败，而是弹出「去打开设置」的引导卡片。

**已知限制（指纹原理决定）**：指纹只能认出**同一段录音**——滤波、压缩、轻微变速
都没问题（实测 0.86~0.95），但**音高一变就崩**（升调 4 个半音掉到 0.56 且认错文件）。
所以「把原曲外放给麦克风听」能搜到，「自己哼这段旋律」搜不到。哼唱无结果时会如实
说明这一点，不会乱报。

### 第三步：分类判错也不影响结果：双路兜底 + 一键切换

说话和唱歌在声学上本来就挨着（唱歌带歌词 → 音节调制强 → 长得像说话），靠一个阈值
不可能全判对。所以判定结果**不再是成败的分水岭**，两条路互相兜底：

| 情况 | 自动动作 | 识别条上的出口 |
|---|---|---|
| 判为哼唱、指纹命中 | 直接出结果 | 「改用文字搜」（也许能转出歌词当文字搜） |
| 判为哼唱、指纹 0 命中 | 顺手跑一次 ASR，转出文字就自动改走歌词文字检索（**范围锁在音频+视频**） | 「改用指纹搜」 |
| 判为哼唱、两条路都没结果 | 给说明卡 | 「改用指纹搜」（用宽松阈值再试一次指纹） |
| 判为说话、转出文字 | 走语义检索，结果太弱（0 条或最高分 < 0.45）时**自动补跑指纹**并把命中并到结果最前 | 「改用指纹搜」 |
| 判为说话、转不出文字 | 自动补跑指纹，有命中就直接展示 | 「改用文字搜」 |
| 两条路都没结果 | 清空旧结果 + 说明卡 | —— |

**这两条是有意为之，别顺手「优化」掉**（2026-10-01 与用户逐条确认）：

- **指纹先跑、没命中才跑 ASR**，不是两条并行。指纹命中时 ASR 完全不跑（0.1~0.3 秒出结果）；
  并行会让每次录音都多花几秒，而指纹一旦命中，ASR 转出来的文字就是多余的。
- **说话路径保留「文字结果弱 → 自动补跑指纹」的兜底**（0 条或最高分 < 0.45 时触发）。
  它不符合「说话只走 ASR」的字面表述，但正是它兜住了「唱歌被误判成说话」的情况，
  所以刻意保留而不是删掉。

**ASR 歌词进了关键词索引**：转写文本（`meta.asr_text`）现在参与 L0 词法匹配
（`fastsearch.search_lexical`），所以「手心里的汗珠」这种歌词原文 **1ms 命中**，
不用过模型——原先只能靠向量，而 WeMM 对「短查询 vs 长文本」区分度不足，歌词反而会
输给毫不相干的空文档。整句口语（「帮我找一下手心里的汗珠那首歌」）走
`fastsearch.content_run`：取 5 字片段滑窗匹配，命中片段要求含 ≥3 个实词字，避免
「帮我找一下」这类套话蒙中。实测：整句 → 晓_FR.mp3 排第一（0.63），歌词片段 → 0.88。

**哼唱路径的阈值更严**：自动判成哼唱时指纹按「错误率 ≤ 0.18（相似度 ≥ 0.82）」筛，
而不是默认的 0.30。原因：实测真人哼的旋律会跟无关音视频擦出 **0.63~0.74 的假阳性**，
而「同一段录音」稳定在 **0.86~0.99**（库内歌曲片段 0.988），卡在 0.82 刚好把两者分开。
手动按「改用指纹搜」时不收紧，尊重用户选择。

**历史音视频的 ASR 会补跑**：索引时遇到「mtime 没变」原本会整个跳过，导致 ASR 打开
之前入库的歌曲永远没有歌词。现在只要 ASR 开着、该文件 meta 里还没有 `asr_text`，
就会被重新索引并补上转写（`indexer.py` 的 `_asr_pending`）；视频的音轨也会一起转写。

**ASR 只转出语气词时不再拿去搜**：实机日志里出现过指纹 0 命中 → ASR 兜底只转出
「嗯。」→ 前端拿这两个字去搜，撞出 20 条毫不相干的素材。现在 `app.py` 的
`_voice_text_ok()` 会先判断转写是不是一句能检索的话（去标点后 ≥2 字、去重 ≥2 个不同字、
不全是「嗯/啊/哦」这类填充词）；不是就当没听清处理，并给出
「听起来你在哼旋律、没有唱词」的说明卡，而不是端上一屏噪音。

**指纹的假阳性漏洞（已修）**：实测 3 秒的噪声 / 纯正弦 / 静音，`fpcalc` 会给出
**完全相同的常量指纹**（如 `[627964279, 627964279, 627964279]`）——拿它去滑动匹配，
只要库里任何一处出现过该常量就是 0 位错误、相似度 **1.000** 的假阳性
（实测随机噪声对 `元宵喜乐（FR).mp4` 报 1.000）。`fingerprint.query_quality()` 现在会
在检索前挡掉这类查询：项数 < 3、或去重后不足一半（平稳信号）直接返回「没匹配到」并
说明原因。实测：噪声/纯音/静音 → 0 命中；真歌 3 秒 → 1.000 晓_FR.mp3（次优 0.771，
区分度明确）；真歌 8 秒 → 0.988 晓_FR.mp3。

### 为什么「哼着旋律找歌」做不到

指纹匹配的是**同一段录音**的声学指纹，不是旋律。实测同一段录音经过低通、压缩、
1.15× 变速仍然 **0.73~0.99** 能认出来，但**升 4 个半音就掉到 0.555 且认错文件**——
音高一变就崩。

想按旋律找歌（Query by Humming）需要完全不同的技术。这里做过两组本地实验，**都没能
把正确歌曲排到第一**：

| 方案 | 做法 | 结果 |
|---|---|---|
| A. 和声特征 | `chroma_cqt`（全曲）+ 12 转调全试的子序列 DTW | 告白 0.3126 / 忆 0.3266 / **晓 0.3294**（正确答案垫底） |
| B. 主旋律 | HPSS 去伴奏 + `pyin` 提旋律 → 单声部轮廓 + 子序列 DTW | 忆 0.4355 / 告白 0.4599 / **晓 0.4704**（仍垫底） |

失败原因是根上的：**没有做伴奏/人声分离**，从混音里提出来的「主旋律」跟真正的唱腔
对不上，而流行歌彼此的和声走向又高度相似，于是所有候选的代价都挤在一起、没有区分度。
要做可用得引入人声分离模型 + 专门的旋律检索，工程量大且效果仍不保证。

**所以能走通的路是**：唱出歌词（ASR 抓歌词 → 文字检索，实测有效）；或者把原曲
**外放**给麦克风听（指纹 0.86~0.99）。

> 「以音搜素材」入口（上传音频文件搜）**只走指纹**，不做意图分流；只有麦克风录音
> 才判断说话/哼唱。

## 新增索引源时，先问一句「现在索引还是稍后」

「添加素材」的流程**不再是选完目录就直接开跑**：

```
选择文件夹 → POST /v1/sources/add（只登记来源）
          → POST /v1/sources/scan（统计 + 估时）
          → 弹对话框：[稍后再索引] [立即建立索引]
                ├ 稍后 → 关闭。来源留在左侧列表，标「未索引」
                └ 立即 → POST /v1/index {paths:[p]} → pollIndex()
```

对话框里给的是用户真正需要的那几个数：

| 行 | 来源 |
| --- | --- |
| 共 N 个文件，其中 M 个已经索引过 | `scan_source()` 走一遍 `os.walk`（跳隐藏目录，上限 10 万个） |
| 构成：图片 / 视频 / 音频 / 文档 / 其他 | `_kind_of()` 按 `ix.IMAGE_EXT / VIDEO_EXT / AUDIO_EXT / DOC_EXT` 分类 |
| 大小 | `os.path.getsize` 累加 |
| 预计约 X | `SCAN_EST = {image:0.7, video:11, audio:2, document:2}` 秒/个，**再乘 `fresh/total`** |

两点关键：

* **估时按「还没索引过的文件」折算**（`fresh = total - indexed`）。同一目录再看一次是
  `fresh 0`，界面直接说「已全部索引过，只做增量检查 —— 几秒」，而不是又报一次全量时间。
* 视频那一项系数 11 秒是**最粗的估计**，因为它们要逐帧编码；`estimate_sec >= 600`
  时对话框会加一条橙色警告，明说「可以先等空闲再索引」。

「稍后」不是不给路：来源会留在左侧，带一个 `未索引` 徽标（`files === 0` 时出现）。
鼠标停上去徽标会变成「✨ 去索引」，点它就打开上面这个对话框。

### 「没索引」只等于「搜不到」，不等于「看不见」

这里**改过一次设计**，值得记下来。最早的做法是：未索引的来源在浏览视图里是**空的**，
而且 `selectSource()` 一发现 `s.files === 0` 就**直接弹**「要不要现在建索引」。
结果是——用户选了「稍后」，进去却连一张缩略图都看不到，随手一点又被弹窗拦一次。
这不是「稍后」，这是**换了个方式逼你立刻索引**。

现在改成：

* **未索引的目录照样能进去浏览。** `browse_all()` 里加了
  `_fs_merge(seen, roots, scope_root, kind)`：对于**一个文件都没索引过**的来源根，
  直接 `os.walk` 把目录里的素材列出来（`fs_browse()`），条目带 `unindexed: true`。
  走的是纯文件系统，**不写 `items` 表、不生成向量**。
* **`selectSource()` 不再弹窗**，选中就是选中。要索引得自己点徽标或提示条上的按钮。
* **结果上方有提示条**（`renderUnidxBar()`）：说清「能看能打开、但用文字搜不到」，
  右边给一个「立即建立索引」。当前来源已索引时这条不出现；搜索态和垃圾桶里也不出现。
* **卡片左下角带「未索引」角标**（`.unidxchip`），一眼能分清哪些还搜不到。
* **计数也跟着算进去了。** `scoped_stats()` 会把未索引来源里的素材计进 `files` / `by_kind`，
  否则会出现「浏览里有 23 张卡片、侧栏却写 22」这种自相矛盾。
  **但 `vectors` 只算索引里的**——它描述的是索引规模，不该被兜底撑大。

`fs_browse()` 有两个护栏：`FS_BROWSE_MAX = 2000`（单次最多列这么多文件，
免得 `/Users/.../CC工作区` 这种 4 万文件的目录把页面拖死）和 `FS_BROWSE_TTL = 20`
（结果缓存 20 秒，连续点来点去不重复走目录；缓存最多留 16 个根）。
跳隐藏目录与 `.` / `._` 开头的文件。

### 索引源一多，列表可以折叠

侧栏的 `全部来源` 同时是这一组的折叠开关：**单击收起 / 展开下面的目录列表**，
右侧那个箭头跟着转 90°，折叠时旁边还会显示藏了几个（`全部来源 3 ›`）。

* 状态存在 `localStorage.srcFold`，刷新和重启都记得。
* 折叠状态下点了某个具体来源、或者刚添加了新目录（`doIndex()` / `selectSource()`），
  **会自动展开**——否则用户会以为自己的操作没生效。
* 点 `全部来源` 除了折叠，也照旧把它切回「不过滤来源」；如果它本来就是当前选中项，
  这一次点击就只做折叠，不重复刷新列表。
* **两个来源重名时**（比如 `CC工作区/未命名文件夹` 和 `Downloads/未命名文件夹`），
  行首会补一段灰色父目录名 `CC工作区 / 未命名文件夹`——父目录放前面，是因为侧栏窄、
  靠后的字会被省略号吃掉，而能区分两者的恰恰是父目录。真正的父目录名在 `title` 里。

### 索引源名字太长：鼠标悬停时来回滚一遍

侧栏只有 193px 宽，像 `86868686868686868686868` 这种名字必然被省略号吃掉，光看开头
根本分不清。所以和「最近上传」用同一套做法：**默认还是省略号，鼠标移到那一行才滚动**。

```css
.src .nm > i{display:inline-block;font-style:normal;white-space:nowrap}
.src .nm.more{text-overflow:clip;
  -webkit-mask-image:linear-gradient(90deg,transparent 0,#000 14px,#000 calc(100% - 10px),transparent);
  mask-image:linear-gradient(90deg,transparent 0,#000 14px,#000 calc(100% - 10px),transparent)}
.src:hover .nm.more > i{animation:srcMarquee 2.8s ease-in-out infinite alternate}
@keyframes srcMarquee{from{transform:translateX(0)}to{transform:translateX(calc(-1 * var(--sc,0px)))}}
```

真正的名字包在 `<i>` 里，`srcMeasureNames()` 量出 `inner.offsetWidth - nm.clientWidth`
作为溢出量，超过 2px 才挂 `.more` 并把 `--sc` 设成「溢出量 + 8px」（末尾留点气口）。
差一点点就不滚，免得那些刚好卡在边界上的名字无缘无故晃。

**两个坑（都踩过）**：

1. **折叠时量不准。** 折叠状态下这些行在 `#srcfold` 里，而 `.srcfold.folded{display:none}`
   ——量出来 `clientWidth` 全是 0，于是全都判定为「不溢出」。结果就是**展开后名字明明
   溢出了却纹丝不动**。修法：`applySrcFold()` 里改完折叠状态立刻调一次 `srcMeasureNames()`。
2. **隐藏的行不能照算。** 反过来，如果展开状态下滚得好好的，一折叠又跑一遍测量，就会
   拿 0 去比、把已经设好的 `.more` 和 `--sc` 全清掉。修法：循环里 `if(!nm.clientWidth) return;`
   直接跳过不可见的行。

实测（`86868686868686868686868`）：折叠时 `more=false`；展开后 `more=true`、`--sc=60px`
（`inner=189 / nm=137`，溢出 52px）；强制动画后 `transform` 从 `matrix(1,0,0,1,-7.5,0)`
走到 `matrix(1,0,0,1,-36.8,0)`，确实在动。另外 `.rm`（那个 × ）是 `opacity:0` 而不是
`display:none`，**一直占着宽度**，所以悬停时 `.nm` 的宽度不会变，`--sc` 不会失效。

### 「索引源」右边的添加按钮

那一行右端的 `+` 原来只是个 15px 的灰色字符（`color:var(--text-2)`，要 hover 才变蓝），
缩在分组标题的右端基本没人会注意到。现在改成**常驻的蓝色胶囊按钮**：

```css
.sec .plus{cursor:pointer;display:inline-flex;align-items:center;justify-content:center;gap:3px;
  height:19px;min-width:19px;padding:0 6px;border-radius:10px;flex:0 0 auto;
  background:var(--blue);color:#fff;font-size:0.6875rem;font-weight:600;line-height:1;
  letter-spacing:0;text-transform:none;box-shadow:0 1px 4px rgba(61,126,255,.35);
  transition:background .12s ease,transform .12s ease}
```

内容是 `<i class="icn" data-icon="plus" data-size="11"></i>添加`，实测 **48×19px**，
白字蓝底圆角 10px，hover 加深并放大到 1.06，按下缩到 0.96。`letter-spacing:0` 和
`text-transform:none` 是为了盖掉父级 `.sec` 给分组标题加的大写 + 字距——这两个属性
会继承下来，中文虽然不受影响，但胶囊里混着英文时会很怪。

### 索引源可以拖动排序

侧栏的索引源列表**整行都能拖**，把文件夹拖到想要的位置就行，顺序会存在服务端，
所以换浏览器、重启电脑都记得。

**顺序存在哪**：`~/Library/Application Support/FXseek/sources.json` 本来就是个
**有序 JSON 数组**（`[{path, name, added_at}, …]`），`sources_with_stats()` 直接按
数组顺序输出。所以排序只是**重排这个数组**，一行索引数据都不用动、不用重跑向量。

后端就一个接口：

```
POST /v1/sources/reorder   {"paths": ["/最前面的/目录", "/第二个/目录", …]}
```

`reorder_sources()` 会先按 `paths` 的顺序收集，**没提到的源按原相对顺序补在后面**
——前端万一漏传，也不会把谁的索引源弄丢。返回重排后的完整 `sources`。

**前端为什么要把 `loadSources()` 拆成两个**：原来它把「fetch + 渲染」揉在一起，
拖完必须等一个网络来回才能重画。现在拆成 `loadSources()`（取数据）和
`renderSources()`（只画 `#srclist`），拖完立刻 `renderSources()` 重画。

**拖拽的几个细节**：

* **落点用两条蓝线标** —— `dragover` 时按 `(e.clientY - rect.top) > rect.height/2`
  判上半还是下半，给自己加 `.drop-before` / `.drop-after`：
  ```css
  .src.drop-before{box-shadow:inset 0 2px 0 0 var(--blue)}
  .src.drop-after {box-shadow:inset 0 -2px 0 0 var(--blue)}
  ```
  **用 `box-shadow` 而不是 `border`**，否则加上的瞬间行会被撑高 2px，下面的行跟着
  跳一下，很难看。
* **`e.preventDefault()` 不能漏** —— `dragover` 里不调它，浏览器就认为这里「不接受
  放置」，`drop` 根本不会触发。
* **Safari 必须 `setData`** —— `e.dataTransfer.setData('text/plain', path)`。不设数据
  的话 Safari 不认这次拖拽，`dragstart` 之后什么都不发生。
* **抽走后下标要减一** —— 把第 `from` 行拖到第 `ti` 行前面时，因为 `from` 那一项
  已经从数组里抽走了，`ti` 在**新数组**里的位置会往前挪一格：
  ```js
  var t = from < ti ? ti - 1 : ti;
  arr.splice(after ? t + 1 : t, 0, moved);
  ```
* **乐观更新 + 失败回滚** —— 先改本地 `STATE.sources` 并重画（手感跟手），再发 POST；
  成功后拿服务端返回的 `d.sources` 再画一次（以服务端为准），失败就
  `toast('顺序没能保存，已恢复')` 并 `loadSources()` 拉回真实顺序。
* 左边那个文件夹图标就是**把手**：`.grip{cursor:grab}`，按住时 `grabbing`，正在拖的
  那一行 `opacity:.45`。

## 「全部」浏览时，文档排在最后

`「全部素材」` 的默认视图里，**图片 / 视频 / 音频一律排在文档前面**，三者之间不排序
（保持原有顺序）。排序逻辑在前端 `ui.html` 的 `applySort()`：默认顺序和「种类」顺序下
多跑一步 `mediaFirst()`，它按 `KIND_RANK = {image:0, video:0, audio:0, document:1}`
做一次**稳定**分区——`Array.prototype.sort` 在 V8 里是稳定排序，同权重的项保持原有
相对顺序，所以媒体内部仍然按用户已经选好的规则（默认顺序 / 种类 / 添加日期）排列。

「名称 / 大小 / 添加日期」是用户**显式**选的排序，就按他选的来，不再插队——否则
「按大小排序」却把文档全踢到后面，看起来像排序坏了。已经在单一类别里
（`STATE.kind` 非空）时 `mediaFirst()` 直接返回，不做无谓的重排。


## 设置页的结构（改设置页前先看这段）

设置页是**左侧栏 + 居中单列**，不是两列网格——`main > .wrap`（`max-width:880px;margin:0 auto`）
里面按 `.sec` 分段，每段 = 一个 `.sechd` 标题 + 若干张 `.card` **竖着堆叠**。

```
<section class="sec" id="sec-ai">      ← id 供侧栏导航跳转/高亮
  <div class="sechd">智能服务</div>
  <div class="card">
    <div class="cardhead">…图标 + <h2> + <div class="d">说明…</div>
    <div class="row">   ← 一条设置项
```

**一条设置行怎么写**：

| 写法 | 样子 | 用在哪 |
| --- | --- | --- |
| `<div class="row">` | 左标签 + 右控件，行的上边框当分割线 | 绝大多数设置项 |
| `.k` 里再套 `<span class="sub">` | 标签下面多一行灰色小字说明 | 需要解释这个选项时 |
| `<div class="row stack">` | 标签独占一行，控件另起一行，说明在控件下面 | 分段控件 + 多行说明（默认模式 / 匹配门槛 / 视频抽帧） |
| `<div class="row top">` | 标签与控件顶部对齐 | 多行文本域（提示词） |

**控件宽度是写死的，不再拉满整行**（以前输入框被拉到 1075px，很难看）：

| 类型 | 宽度 |
| --- | --- |
| `input[type=text]` / `password` / `select` | 330px |
| `input[type=number]` | 112px |
| `textarea` | 400px |
| 短字段加 `class="w-sm"` | 152px（语言代码这类） |

**侧栏的两件事**都在 `settings.html` 末尾的 `initSideNav()` / `initSetSearch()`：
分区导航点击平滑滚动 + 滚动时高亮当前段；搜索框按行文本、`placeholder`、卡片标题过滤，
规则是**标题命中 → 整张卡片展开；只有描述命中 → 只留卡片头（说明为什么它被匹配到）；
行命中 → 只留那一行**，并且把留下来的第一行的上边框去掉，免得顶部多一根线。
搜索无结果时显示「没有找到匹配的设置项」。

### 「关于」那一页（`#sec-about`）

侧栏最后一项。两张卡：**关于本应用**（版本 / 推理引擎 / 运行平台 / 本地规模 / 构建时间 + 三个按钮）
和**赞赏支持**（两张二维码）。事实全部来自 `GET /v1/about`，本机现算，不联网。

- **「检查更新」是诚实的**：这个应用没有在线更新源，所以它只回答「你跑的就是当前这份本地构建，
  没有更新的版本可下载」，不会假装联网比对过远端。真要说价值，是把版本和构建时间摆出来给人看。
- **「复制诊断信息」**把版本、构建时间、引擎及其路径、平台、数据目录、规模、缓存占用拼成一段文本
  丢进剪贴板。非安全上下文（用 http 访问局域网 IP）里 `navigator.clipboard` 会被浏览器拒掉，
  这时退回到 `prompt()` 让用户手动复制——两条路都要留着。
- **「推理引擎」显示的是一句人话**，不是路径：从 `model/config.json` 里读 `model_type` 映射成
  `Qwen3.5`、再拼上 `quantization.bits`（本机是「Qwen3.5 · 4bit 量化」）。读不到才退回目录名。
  完整路径放在 `engine_path` 里，前端挂在 `title` 上当 tooltip。

**打赏二维码怎么放的**：图片在 `assets/donate-wechat.jpg` / `assets/donate-alipay.jpg`，
由 `_assets()` 按**白名单**服务（`/assets/<名字>`，和 `_vendor()` 同一套 realpath 二次校验），
不走外链也不塞 `data:` URI——打包成 app 后要能离线用。

两张图都是从整张分享图里**裁到只剩二维码**的：微信那张原本带「觉得好用不错，赏杯咖啡」文案
和金色底栏（裁掉 y≥750 的部分），支付宝那张原本是「支付宝 logo + 推荐使用支付宝 + 二维码 +
商户名 + 打开支付宝[扫一扫]」的长图（只留白底框里那块 1036×1036 的正方形）。
裁的时候**只缩不放**（上限 720），所以微信那张出图是 533×533、支付宝 720×720——**都是正方形**，
CSS 里又被同一个 `height:196px` 的方框约束，于是两边渲染出来都是 178×178，大小一致。

> 踩过的坑：拼接对照图时贴图偏移写成了 `(0-L)*k`，忘了裁剪原点可能被 `max(0, L)` 抬到 0，
> 结果二维码全挤在左上角。偏移必须按**实际裁剪原点**算：`(cl-L)*k`。

缓存头用 `Cache-Control: no-cache` 而不是长缓存：这两张图才几十 KB 又是本地读，
长缓存只会让「换了图用户一周内还看旧图」变成新的坑。

**右边那一格：去 GitHub 点个 Star。** `.donrow` 是 `repeat(auto-fit,minmax(200px,240px))`，
两张二维码卡占不满 838px 的容器，右边会空出一格。现在那里放第三张卡（`a.doncard.starcard`）：

```html
<!-- ★ 项目地址占位符：换成真实仓库地址即可，只有这一处 href 要改。 -->
<a class="doncard starcard" href="https://github.com/FRr688/FXseek"
   target="_blank" rel="noopener noreferrer" title="在 GitHub 上打开项目页">
```

三个要注意的地方：

- **整张卡是 `<a>`**，所以它必须**看着像卡片、悬停有明显反馈**（边框转 `--blue`、GitHub 标变蓝放大、
  按钮加深），否则没人知道能点。另外补了 `:focus-visible` 的蓝色轮廓，键盘 Tab 也能用。
- **`.starimg` 也做成 196px 高**（和二维码的 `.donimg` 一样），否则网格里另外两张会被
  `align-items:stretch` 拉伸、底下多出一块空白。实测三张卡都是 **240×276**。
- GitHub 标用的是**内联 SVG 的实心官方 mark**（simple-icons 的 path），不是 `icons.js` 里的线性图标
  —— 那是品牌标记，得保持原样。按钮里那个 ✩ 是给 `icons.js` 新加的 `star`（Lucide 星形）。

`target="_blank"` 是刻意的：点了不该把设置页导航走。

### 换图之后，光改响应头是没用的（踩过一次）

第一版把 `/assets/` 设成 `max-age=604800`（一周）。后来换了二维码图、把响应头改成
`no-cache`，**用户刷新浏览器还是看到旧图**。原因：

> 浏览器里已经存了一份「还很新鲜」的旧响应（它自己记着能新鲜一周），
> 于是**根本不会回服务器问**，也就永远看不到我们后来改的那个头。

`no-cache` 只有在浏览器**愿意发请求**的时候才有意义。要强制重取，只能**换 URL**。

所以现在：`GET /v1/about` 多返回一个 `asset_ver`（= `assets/` 里最新的 mtime），
前端 `applyAssetVer()` 把它拼成 `?v=<asset_ver>` 挂到 `img[data-asset]` 上。
换了图 → mtime 变 → URL 变 → 必然重新拉。HTML 里那个写死的 `?v=2` 只是兜底
（JS 挂了也还有一层），真正生效的是 mtime 那一版。

顺带把两个 HTML 页面（`/` 和 `/settings`）也加上 `Cache-Control: no-cache` ——
改完页面不用再教用户按 Cmd+Shift+R。



## 界面语言（简体中文 / English）

设置页「外观 → 界面语言」可以切换中英文。**中文是原文，英文是译文** —— 所以切回
中文永远不会出问题，翻译挂了也只是回到中文，不会把页面搞成空白。

### 实现：词典 + DOM 翻译器，不改调用点

全部逻辑在 `wemm_app/i18n.js`（`/i18n.js` 路由直接读盘，带 `no-cache`），
运行时由 `window.I18N` 暴露：

```
I18N.setLang('en'|'zh')   // 切语言，并翻译整页
I18N.lang()               // 当前语言
I18N.dict                 // 词典本体（调试用）
I18N.T('中文', 'English') // JS 里要按语言分支时用它
```

页面**静态文案一行都不用改**：`applyNode()` 用一个 `TreeWalker` 扫整棵 DOM，
把文本节点和 `title / placeholder / aria-label / alt` 四种属性里的中文换成英文。
`ui.html` / `settings.html` 里那几百处 `innerHTML` 模板拼接因此都不需要动 ——
**加词条只改一个文件**。

三条必须守住的规矩：

1. **幂等。** 用 `WeakMap`（`origText` / `origAttr`）记住每个节点的**翻译前原文**，
   每次都从原文出发算译文。不这么做的话，来回切几次语言，英文会叠着中文越滚越长。
2. **不碰用户数据。** 日志、文件名、路径、搜索历史**永远不翻** —— 靠 `SKIP_SEL`
   （`.loglist,table.logs,.qhist,.srclist .nm,.card .nm,.row .nm,.path,.p,.msgbody,.histbox,.logrow`）
   和 `data-no-i18n` 属性挡住。所以英文界面里看到的 `忆_FR.mp3`、`~/...`
   仍然是原样，这是对的，不是漏翻。

   ### `data-i18n-ok`：容器里「一半是文案、一半是用户数据」怎么办

   `SKIP_SEL` 是按**容器**写的，可侧栏「全部来源」、搜索历史「最近搜索」这类容器
   **既装固定文案（标题行）又装用户数据（目录名、搜索记录）**。而且 TreeWalker
   对元素返回 `FILTER_REJECT` 会**连整棵子树一起跳过** —— 所以给子节点加豁免是没用的，
   得让**被 REJECT 的那个容器自己**带 `data-i18n-ok`，再把里面真正属于用户内容的
   节点用 `data-no-i18n` 标回来。两者同时出现时**以 `data-no-i18n` 为准**。

   还有一个隐蔽情况：`SKIP_SEL` 里的 `.srclist .nm`、`.card .nm` 是**后代型选择器**，
   容器里的 `<span class="nm">` 用 `closest()` 会**命中它自己**。所以 `skip()` 里还要
   比一下「命中的容器」和「最近的 `data-i18n-ok` 祖先」谁离节点更近：同一个节点、
   或豁免在外层，就放行。判定逻辑见 `i18n.js` 里的 `skip()`，注释写全了。

   当前挂了 `data-i18n-ok` 的容器：`#srclist`、`#qhist`、`#histBox`。
3. **别拖慢主线程。** `MutationObserver` 只在英文模式下工作（中文是原文，直接
   no-op 省掉全部开销），并且**去抖 50ms** —— 索引/补全时 DOM 每秒变几十次，
   不去抖会把主线程吃满。

### 加载顺序：i18n.js 必须早于「读设置」那次渲染

踩过一次：设置页切成英文、回首页是英文，再进设置页又变回中文。

原因是 `i18n.js` 原来跟首页一样挂在页面**最底部**，而设置页的主内联脚本在解析期就
`loadSettings().then(applyLang)`，本地服务回得太快 —— `applyLang('en')` 跑的时候
`window.I18N` 还不存在，`if (window.I18N) I18N.setLang(v)` 就**静默跳过**了；
等 `i18n.js` 加载完，它尾部那次 `applyNode(document.body)` 又是在 `zh` 下跑的，
于是整页稳稳地停在中文。首页没这问题，是因为 `ui.html` 里专门写了一段
「等 i18n 就位后再补跑一次」。

现在的两道保险：`settings.html` 把 `<script src="/i18n.js">` 挪进了 `<head>`
（`i18n.js` 尾部有 `if (document.body)` 判断，提前加载是安全的），
`applyLang()` 里也改成「`I18N` 不到位就 50ms 一轮、最多等 2 秒再补一次」。

### 加词条：先词典，后正则

`i18n.js` 里两块，按顺序匹配：

```js
var ZH2EN = { "素材": "asset", "媒体库": "library", ... };   // 精确匹配，优先
var RULES = [ [/^已接入 (\d+) 个 Agent$/, 'Connected to $1 agents'], ... ]; // 带参数的走这
```

`translate(s)` 先查 `ZH2EN[s]`，查不到再逐条套 `RULES`，都不中就原样返回。

**坑（踩过好几次，照做可以省几小时）：**

- **JS 拼完 `innerHTML` 必须自己补翻一刀。** 翻译器只在 `setLang()` 和
  `MutationObserver` 回调里工作，而这一页的卡片、日志、状态行都是
  `await fetch(...)` 之后才拼进 DOM 的 —— 那次整页 `refresh` 早跑完了。
  约定：**每个「innerHTML 拼完」的渲染函数末尾都调一次**
  `if(window.I18N && I18N.refresh) I18N.refresh(root)`。已经接上的有 `settings.html`
  的 `loadMcp` / `loadAbout` / `loadIdleStatus` / `renderIdleBadge`（统一走 `relabel()`），
  `ui.html` 的 `loadDetail` / `render` / `renderHistory` / `renderSources` / `qhRender` /
  `refreshMcpBadge` / `showCtxMenu` / `showFmtMenu` / 排序菜单。
- **`loadAll()` 里几个 load 没 `await`。** `settings.html` 的 `loadAll()`
  是 `await loadCache(); await loadEnv(); ... loadIdleStatus(); loadMcp(); loadAbout(); relabel();`
  —— 后三个**没 await**，所以函数末尾那次 `relabel()` 是在它们渲染之前跑的。
  别指望它兜底，每个函数自己补翻。
- **粒度是「渲染后的整条文本节点」，不是句子。** `innerHTML` 里的 `<b>` 会把一个
  句子切成好几个文本节点：`缓存：<b>7</b> 个文件 · <b>0.17 MB</b> / 上限 1024 MB`
  实际渲染成 `缓存：`、`7`、` 个文件 · `、`0.17 MB`、` / 上限 1024 MB` 五条。
  按标点切碎的词条**永远命中不了** —— 词典键要照着**节点原文**写。
- **`&nbsp;` 是 U+00A0，不是普通空格。** 状态行用 `&nbsp;·&nbsp;` 拼接，规则里
  得显式写 `[\s\u00A0]`，用 `\s` 匹配不上。
- **`RULES` 顺序敏感，先匹配者胜。** 加规则前先 `grep` 有没有更宽的旧规则把新规则
  吃掉（曾经 `^已生成 (\d+) 个标签(.*)$` 遮住了新写的精确规则）—— 要**删掉旧的**，
  不能只加新的。
- **函数替换写 `rep(m)`，绝不能写 `rep.apply(null, m)`。** 后者会把匹配数组摊成
  位置参数，函数里的 `m` 变成整个匹配串，`m[1]` 取到的是字符串第 1 个字符 ——
  症状是冒出 `MCP: C agents connected: P` 这种乱码。
- **改文件时用字面中文去匹配，不要用 `\uXXXX` 转义串。** 文件里存的是原始
  CJK 字符，转义串搜不到（静默 0 命中，`assert count == 1` 会救你一命）。
- **`<title>` 要单独处理。** 它在 `<head>` 里，`applyNode(document.body)` 够不着，
  所以 `setLang()` 额外调 `setTitle()`；并且 `document.title` **不是 HTML**，
  词典值里给文本节点用的 `&amp;` 会原样显示成字面量，所以要过一遍 `unent()`。
- **带图标的整行（`.hintline`）：翻到的是 `<svg>` 后面那个文本节点。**
  `#animHint` 里 `renderStaticIcons()` 会把 `<i class="icn">` 换成 `<svg>`，
  所以真正被翻的节点原文带一个**前导空格**。三档（跟随系统 / 完整 / 关闭）里
  当初只收了「完整」一条，另外两档在英文界面下一直留在中文 —— 这类词条
  **两种形态都要写**（带前导空格与不带）。
- **`<b>` 两侧的尾空格。** 「只知道……不知道<b>什么时候该用</b>」在英文里要拼成
  一句话，前一个文本节点的译文**必须带尾空格**，否则渲染出来是
  `it doesn’t knowwhen to use them.`；句号后接 `<b>` 同理。改完顺手把 `<b>` 里
  那句改成小写起头（`when to use them`），它在这儿不做首词。
- **空态占位符（`.tempty`）得单独捞。** 运行日志卡片 `.logview` 整块在 `SKIP_SEL`
  里（里面是用户自己的文件名和路径），而 `TreeWalker` 在**容器那一层**就 REJECT 了，
  子树根本走不到 —— 在 `skip()` 里给 `.tempty` 开豁免没用。`applyNode()` 末尾于是
  自己 `querySelectorAll('.tempty')` 捞一遍再翻，`暂无日志` 才跟着语言走。
- **模板字符串里的内联换行，词典救不了。** `translate()` 只剥**首尾**空白
  （`i18n.js:1429-1445`），所以用反引号拼出来、中间带着 `\n` 和缩进的句子
  （详情栏那条 hintline 就是：`…原文完整保留。\n          想逐字对照原文…`）
  **永远命中不了词条** —— 症状是英文界面里单这一句留中文，别的都翻了。
  更麻烦的是同一个 `\n` 有好几处缩进量不同。
  这类只能走 `RULES`：整句用 `\s*` 吃掉换行、捕获组接住变量部分，
  再用函数替换拼英文。**判断口径：带内联换行的串一律进 `RULES`，不要进 `ZH2EN`。**
  （`i18n.js:860` 那条旧词条本身就带 `\n          `，能命中是因为整串是静态的、
  每次缩进都一样 —— 别拿它当反例。）

改完 `node --check i18n.js`，刷一下浏览器即可（HTML/JS 都是每请求读盘，不用重启）。


## 把媒体库接给本机 AI Agent（MCP）

编排助手（DSH、Codex、Claude Code、opencode、WorkBuddy、Hermes）可以通过
**MCP** 直接调用这个媒体库。用户在对话里说「帮我找有气球的图片」，助手就能拿到
文件路径，然后自己打开、整理或加工。

设置页有一个独立的 **「MCP 服务」** 大类，会自动扫描本机装没装这 6 个 Agent，
每个都能单独开关；主界面右上角「添加素材」左边会在**有 Agent 接入时**亮起一个
绿色的 `MCP N` 徽标（没接入就整块藏起来，不占地方）。

### Agent 列表上的图标是官方 logo

那一列原来是一块一块的首字母方块（`DSH` / `OC` / `WB` / `HM` / `CX` / `CC`），
六个方块长得一样，扫一眼分不出谁是谁。现在换成各自的官方标志，都由
`agent_logos.js` 提供（本地文件，打包后离线也能用）：

```js
window.agentLogoHTML(id, size)   // 返回一段 HTML：矢量图或 <img>
window.AGENT_LOGOS = {MARK, STYLE, IMG}
```

* `MARK` 是**四条 24×24 的官方路径**，取自 [simple-icons](https://simple-icons.org)
  的 `deepseek` / `openai` / `claude` / `opencode`（与 opencode 官网 brand 页一致）。
* `IMG` 是**两条内嵌的 base64 PNG**：`workbuddy` 来自
  `/Applications/WorkBuddy.app/Contents/Resources/icon.icns`，`hermes` 来自
  `~/.hermes/hermes-agent/assets/banner.png` 那块像素风 `HERMES-AGENT` 字标里裁出的 `H`。
* `STYLE` 给矢量那几个配品牌底色：DeepSeek `#4D6BFE`、opencode `#211E1E`、
  OpenAI `#0d0d0d`、Anthropic `#D97757`；渲染成「品牌色圆角底 + 白色标志」。

**没有照搬这几个 .app 自带的图标**，因为实测下来它们并不合适：OpenCode.app 的
`icon.icns` 其实是 macOS 的通用占位图（不是真 logo）；Hermes.app 的是一张动漫人物
插画，缩到 30px 糊成一团、而且大片白底在深色主题上很刺眼；Codex++.app 用的是第三方
包装器的紫云图标，不是 OpenAI 的。另外 simple-icons 里那个 `hermes.svg` 是**爱马仕
时装品牌**的标志，跟本机的 Hermes Agent 毫无关系，**不能用**——`workbuddy` 则在
simple-icons 里没有条目（404）。

设置页这边 `.mcprow .mi` 去掉了原来那层绿色渐变底（logo 自己带底色），未安装的 Agent
加 `filter:grayscale(1);opacity:.55` 压暗。`mcpLogoHTML(id)` 在 `agentLogoHTML` 拿不到时
会**回退成原来的首字母方块**，所以脚本没加载也不会开天窗。

### 为什么是 stdio，而不是再开一个端口

常见的做法是让 FXseek 常驻监听一个 HTTP 端口，Agent 通过 HTTP 连过来。这里**没有**
这么做，理由是：

- **不用管生命周期。** 主服务可能没开、可能换了端口、可能用户根本没启动。
  stdio 模式下，Agent 需要时才拉起 `mcp_server.py` 子进程，用完就退，不存在
  「服务没起来所以工具挂了」这种状态。
- **不用管鉴权。** 一个监听端口的本地服务，任何本机进程都能连；stdio 的管道只属于
  拉起它的那个 Agent。
- **不改现有架构。** `mcp_server.py` 是个**纯翻译层**，自己不做检索，把请求转发给
  已经在跑的 `127.0.0.1:8231`。检索逻辑一行都没动。

代价是每个 Agent 各有一份子进程（约几十 MB），但它是懒加载的，不用就不占。

### 六个 Agent 的配置形状都不一样

这是这块最费劲的地方 —— 六家的配置文件格式、位置、键名全不同：

| Agent | 配置文件 | 键结构 |
| --- | --- | --- |
| DSH | `~/.dsh/storages/mcp_connector.json` | `tables.connections.<key>` |
| opencode | `~/.config/opencode/opencode.json` | `mcp.<name>`，`type:"local"`，**命令和参数合并成一个数组** |
| WorkBuddy | `~/.workbuddy/mcp.json` | `mcpServers.<name>` = `{command, args}` |
| Hermes | `~/.hermes/config.yaml` | `mcp_servers.<name>`（YAML） |
| Codex | `~/.codex/config.toml` | `[mcp_servers.<name>]`（TOML） |
| Claude Code | `~/.claude.json` | 顶层 `mcpServers.<name>` |

`mcp_agents.py` 用一张注册表把差异吃掉，对外只暴露
`detect_all()` / `enable(ids)` / `disable(ids)` 三个无参数的接口。

**几个改别人配置文件时必须守的规矩**（都踩过坑）：

1. **先备份，且只备份一次。** 写成 `<file>.fxseek.bak`，但如果备份已存在就**不覆盖**
   —— 否则用户第二次点「开启」时，被污染的文件会被当成原件存下来，备份就废了。
2. **原子写。** 临时文件 + `os.replace`，中途出错不会留下半个文件。
3. **解析不了就别动。** JSON 解析失败直接返回失败，绝不「猜一个结构写回去」。
4. **YAML/TOML 的引号不能用 `json.dumps`。** 它会把中文转义成 `\u5de5\u4f5c`，
   在 JSON 里合法，写进 YAML/TOML 就变成**字面的反斜杠 u 文本**，路径直接废掉。
   统一用 `_q()`：一律加双引号、只转义 `\` 和 `"`，不动非 ASCII。
   （TOML 还有更狠的：裸值里出现中文会让整个文件解析失败，`tomllib` 直接报
   `Invalid value`。）
5. **TOML 的节有「吞噬」效应。** `[xxx]` 会一直吃到下一个 `[` 开头的行为止。
   最初把 `[mcp_servers.fxseek]` 直接追加到文件末尾，结果被最后一个节
   （这个机器上是 `[tui]`）吞掉，变成了 `tui` 里的键 —— 文件能解析，但 Agent
   读不到 MCP 配置。现在会找到 `[mcp_servers]`，跳过紧跟的键值行，把新节插在那儿。
6. **YAML 不能重复开键。** Hermes 原本已有 `mcp_servers: {}`，早期实现会在文件
   末尾**再开一个同名的 `mcp_servers:`**，重复键 + 读不回来。现在区分三种情况：
   空映射要展开成块 / 已经是块就往下插 / 不存在才追加。

实测往返（开 → 检测 → 关 → 再检测）在 6/6 全通过，且 `yaml.safe_load` 与
`tomllib.load` 都能正常解析，用户原有的 `memory`、`tui`、`hooks.state`、
`projects`、`plugins`、`cua_repl` 等键一个不少。

### Agent 能用到的 8 个工具

**全部只读**。删除、导入、改设置这些**不开放**给 Agent，避免「助手自作主张动了
用户的文件」。

| 工具 | 用途 |
| --- | --- |
| `search_media(query, kind?, top_k?, tier?)` | **按内容**找素材（文件名不参与打分） |
| `find_by_name(name, kind?, limit?)` | **按文件名**找素材（内容不参与打分） |
| `search_by_image(image_path)` | 以图搜图 |
| `search_by_audio(audio_path)` | 以音搜素材（音频指纹） |
| `get_media_info(path)` | 按路径查详情 |
| `list_sources()` | 列出索引源 |
| `list_recent(limit?, kind?)` | 最近上传 |
| `library_stats()` | 库总览 |

#### 为什么「按内容」和「按名字」是两个工具

不是凑数。**这两个信号必须分开**，混在一起两边都会变差。

用户的文件名经常是随手起的、甚至写错的（「最终版」「稿2」「未命名-1」）。如果把它
混进内容排序，一个名字取得巧的文件就能压过真正相关的东西；反过来，如果只留内容
排序，用户明确报出「找那个叫季度报告的」时又抓瞎。

所以两条路彻底分开，**各自不碰对方的信号**：

```
search_media   →  /v1/search  {lexical: false}   AI 描述、标签、逐帧、正文、转写文本
find_by_name   →  /v1/find    （压根不做语义）    文件名、路径
```

实测最能说明问题的一组：

| 调用 | 结果 |
| --- | --- |
| `find_by_name(name="气球")` | **0 条** —— 那个文件叫 `文件12.png`，名字里没有「气球」 |
| `search_media(query="有气球的画面")` | **1 条** `文件12.png`（0.7737）—— 它的 AI 标签里有「彩色气球」 |

同一件事的两个侧面，两个工具各答对一半。技能正文里专门写明了「用户说『找有气球的
画面』要用 `search_media`，说『找那个叫季度报告的文件』要用 `find_by_name`」，
并且让 `find_by_name` 在返回 0 条时自己提醒一句「这里只比文件名，要按内容找请用
`search_media`」。

**`find_by_name` 会扫未建索引的目录**（`/v1/find` 先查 `items` 表，再按名字走一遍
注册的来源目录），命中的条目带 `"unindexed": true` —— 这种文件搜得到、打得到开，
只是还没有向量，所以 `search_media` 找不到它。走访有上限
（`FIND_MAX_VISIT = 40000` 个文件、`FIND_MAX_HITS = 300` 条命中），
超了会在返回里给 `truncated`。

#### 排序六级 + 分词兜底

```
0  精确同名                       女孩.mp4        ← 查「女孩」
1  名字以它开头                   女孩照片.png     ← 查「女孩」
2  名字里含它                     小女孩.jpg      ← 查「女孩」
3  分词兜底（覆盖率 100%）        季度经营分析报告.docx  ← 查「季度报告」
4  分词兜底（覆盖率 ≥ 60%）
5  只在路径里含它                 868686…/2.dps   ← 查「868686」
9  没命中
```

**为什么要有 3/4 这两档**：用户记文件名常常只记个大意，中间还夹着别的字。
「找那个叫季度报告的文件」——库里那个叫 `季度经营分析报告.docx`，**不包含**
「季度报告」这四个连着的字，纯子串匹配必然落空，可这明明就是他要找的。

所以整串没命中时再松一层（`_find_fuzzy()`，`app.py`）：

- **中文按「字集合覆盖率」**（不看顺序，容忍中间夹字）：查询里的字有六成出现在
  文件名里就算命中。`季度报告` vs `季度经营分析报告.docx` → 4/4 = **1.0**。
- **拉丁按「整词」**：`report` 和 `2024` 分开算，认出一个算一个。
- **至少两个单位才兜底**（`FIND_FUZZY_MIN_UNITS = 2`）—— `find_by_name("a")` 不能
  把整个库倒出来（`~/…` 路径里全是 `a`，所以**单字连 path 档都不撞**）。
- **覆盖率下限 60%**（`FIND_COVER_FLOOR`），且同档内按 `ratio` 降序排。

兜底命中的结果带 `"approx": true` 与 `"match_ratio"`，返回体里还有一句
`approx_note` 提醒 Agent：「文件名里没有你要的整串……**报给用户时把完整文件名
念出来让他确认**」——别把 `季度经营分析报告.docx` 当成用户说的那个名字。

实测：

| 调用 | 结果 |
| --- | --- |
| `find_by_name("季度报告")` | ✅ `季度经营分析报告.docx` `approx: true, match_ratio: 1.0` |
| `find_by_name("季度经营分析")` | ✅ `季度经营分析报告.docx`（精确，rank 2） |
| `find_by_name("气球")` | ❌ 0 条（名字里真没有，内容才有 → 该用 `search_media`） |
| `find_by_name("a")` | ❌ 0 条（单字不兜底、也不撞 path） |
| `find_by_name("868686")` | 22 条（路径里含它，rank 5） |

### 结果做了相关度截断

这一点很关键。如果直接把 `do_search` 的原始结果丢给 Agent，会出现这样的问题：
用户问「太空」，库里根本没有太空的素材，但向量检索**总会**返回分数最高的一批，
Agent 就会一本正经地拿几张不相干的图当成「太空素材」汇报。

所以 `mcp_server.py` 里加了 `_filter_relevant()`：

```python
REL_FLOOR  = 0.46   # 低于这个绝对分数，不要
REL_RATIO  = 0.62   # 低于「最高分 × 这个比例」的，不要
TOP_FLOOR  = 0.50   # 最高分都不到这个数 → 整批不返回
```

`TOP_FLOOR` 是必须的：实测「太空」会返回一簇 0.42~0.43 的结果，彼此分数接近，
**光靠相对比例切不掉**（比例全是 1.0），只能用绝对分数线拦。

**`REL_FLOOR` 从 0.42 提到 0.46** 的原因：技能正文里写的是「0.5 左右属于弱相关」，
而 0.42 会把 0.4518 的 `个人简历 范锐.doc`、0.4429 的 `比较.txt` 一起塞给 Agent ——
用户问「日落的风景」，Agent 收到 3 条，其中两条是 Word 和文本文件，很荒谬。
提到 0.46 之后 `日落的风景` 只剩那条 0.6461 的图片。

实测效果（全部打标之后）：

| 查询 | 结果 |
| --- | --- |
| 有气球的画面 | 1 条（0.7737） |
| 海边的日落 | 1 条（0.8377） |
| 一张狗的图片 | 1 条（0.8699） |
| 一个小女孩拿着花 | 3 条（0.9150 / 0.8083 / 0.5705） |
| 太空飞船 | **0 条** ✅ |

### 三个「别让 Agent 误会」的细节

**⓪ `lexical: false`：Agent 只按内容排序，不看文件名。**

`/v1/search` 默认会做**文件名/路径加成**（`indexer.py` 的 `_lexical_boost`）——整串命中
文件名 +0.30、单字命中按比例 +0.20。这是给界面用的：搜「狗」得让
`小狗在操场奔跑.png` 明显浮上来，搜一个精确文件名也要能秒中。

但对 Agent 这是**有害**的。用户的文件名经常是随手起的、甚至写错的（「最终版」「稿2」
「未命名-1」），拿它当证据会把 Agent 带到沟里。所以 MCP 那条路永远发
`body["lexical"] = False`：

```python
# mcp_server.py · tool_search_media
body["tier"] = args.get("tier") or "deep"
body["lexical"] = False     # 文件名可能是错的，只按内容相似度排
```

效果（同一个查询「小女孩穿绿色连衣裙」）：

| | `女孩.mp4` | `文件12.png` | `元宵喜乐（FR).mp4` |
| --- | --- | --- | --- |
| 界面（`lexical: true`） | **1.0744** ← 文件名也叫「女孩」 | 0.9900 | 0.8821 |
| Agent（`lexical: false`） | 0.9900 | 0.9900 | 0.8821 |

注意界面那一列的 **1.0744** —— 余弦相似度不可能大于 1，多出来的是文件名加成**加**上去的。
所以 `_slim_result()` 里把对外报的分数钳到 `[0, 1]`：

```python
if isinstance(raw_score, (int, float)):
    raw_score = max(0.0, min(1.0, round(float(raw_score), 4)))
```

技能正文里告诉 Agent 的是「0.9 以上基本就是要找的」，报一个 1.07 会让它没法判断。

**`use_name` 只关掉文件名那一档，转写文本那一档保留** —— 音频的 `asr_text` 命中是
**内容**证据（歌词、台词就在文件里），不是文件名，关掉它会让「搜歌词找歌」整条路废掉。

另外，**两条结果分数一样（尤其都顶到 0.99）是正常的** —— 说明它们内容上确实都命中。
这种情况要让 Agent 把各自的 `ai_description` / `ai_tags` 都念给用户，而不是凭文件名替他挑。
技能正文里专门写了这一条。

**① `tier` 默认 `deep`，不跟随调用方。**

`/v1/search` 的 `tier=auto` 是给界面用的省时策略，但它有个副作用：`auto` 会先查查询向量
缓存（`fastsearch.py` 的 `qcache_get`），**命中就走 L1 快路径，没命中才落到 L2 深度检索** ——
于是同一个查询两次的分数能差一大截：

```
有气球的画面   冷启动 0.7737  /  缓存命中 0.6349
小狗在操场上跑  冷启动 0.7948  /  缓存命中 0.5315
```

界面无所谓（反正只用来排序），但 Agent 会**照着分数判断相关不相关**，这种不确定性不能留。
耗时代价很小：`auto` 0.10~0.30s、`deep` 0.33~0.42s。所以 `search_media` 一律
`body["tier"] = args.get("tier") or "deep"`。实测连问两轮分数完全一致。

**② 错误分两类，别把「文件不存在」说成「暂时不可用」。**

原来 `tools/call` 把**所有**异常都包成「媒体库暂时不可用：…」，于是 `get_media_info`
传一个不存在的路径会返回：

```
媒体库暂时不可用：FXseek 返回 HTTP 400：{"error": "文件不存在或不可访问"}
```

这句话会**骗 Agent 一直重试** —— 它以为服务在打嗝，其实那个文件就是没有。现在
`BackendError` 带一个 `kind`：

```python
class BackendError(Exception):
    def __init__(self, message, kind="unreachable"):   # unreachable | rejected
```

`_request` 里 `400 <= e.code < 500` 时取出后端的 `{"error": ...}` 原文，标成
`kind="rejected"`（**重试无用**）；5xx 和连不上仍然 `unreachable`（可以重试）。`tools/call`
按 kind 决定措辞：

```python
txt = str(e) if e.kind == "rejected" else "媒体库暂时不可用：%s" % e
```

现在同样的调用回的是 `"文件不存在或不可访问"` —— Agent 会如实转告用户。

### 配套的 Skill

MCP 解决「能不能调」，Skill 解决「**知不知道该调、以及怎么调**」。

技能源文件在 **`wemm_app/fxseek_skill/SKILL.md`**（随 app 一起走，所以打包后也在）。
**开启 MCP 时会被自动复制**到六家各自的 skills 目录：

| Agent | 技能落到哪 |
| --- | --- |
| DSH | `~/.dsh/skills/fxseek-media/SKILL.md` |
| opencode | `~/.config/opencode/skills/fxseek-media/SKILL.md` |
| workbuddy | `~/.workbuddy/skills/fxseek-media/SKILL.md` |
| hermes | `~/.hermes/skills/fxseek-media/SKILL.md` |
| codex | `~/.codex/skills/fxseek-media/SKILL.md` |
| claude code | `~/.claude/skills/fxseek-media/SKILL.md` |

内容（`fxseek-media`）：

- 什么该用 / 什么不该用（找网上的东西用 `web_search`，找代码用 `grep`）
- 查询怎么写（**中文自然语言，不要翻译成英文、不要堆关键词**，附好坏对照表）
- 返回结果怎么读（`score` 0.9 以上基本就是要找的，0.5 左右值得跟用户确认）
- `count: 0` 时该如实说没有，**不要编造路径**
- 三个完整的对话范例，以及「素材是个人照片/录音，不要主动扩散路径」的边界

#### 三条规矩（都很重要）

1. **只在缺失时才写。** 已经存在就一律不动 —— 用户很可能自己改过那份说明书，
   替他们覆盖等于把改动丢了。想强制重写要显式 `force=true`。
2. **关闭 MCP 不删技能。** 关掉检索不等于要人家把说明书也扔了；删别人目录里的
   东西是不可逆的，不做。（`disable()` 沿途只回报 `skill_kept`，不碰文件。）
3. **单个 Agent 注入失败不影响别人，也不影响 MCP 本身能不能用**，只在结果里标出来。

对应地，`/v1/mcp/toggle` 在**开启**时顺带注入，返回值里会多一个 `skill_created`
（这次新建了哪几家）；**关闭**时返回 `skill_kept`（保留了几份）。
设置页 Agent 列表每行有个 `📘 技能` 小标记，**已经接入了却没有技能**时会变成
琥珀色的「技能缺失」，旁边就是「重新注入技能」按钮。

```bash
# 只补缺失的（默认）
curl -s -X POST http://127.0.0.1:8231/v1/mcp/skill -H 'Content-Type: application/json' -d '{}'

# 强制覆盖已存在的（会把用户改过的版本冲掉，慎用）
curl -s -X POST http://127.0.0.1:8231/v1/mcp/skill -H 'Content-Type: application/json' -d '{"force": true}'

# 命令行直接注入（--force 可选）
./venv/cpython-3.11/bin/python3.11 mcp_agents.py --skills
```

### POST /v1/search · POST /v1/find

两条**刻意分开**的检索路。`/v1/search` 按内容，`/v1/find` 按文件名，互不污染
（为什么分开见「[为什么「按内容」和「按名字」是两个工具](#为什么按内容和按名字是两个工具)」）。

```bash
# 按内容找（语义检索）
curl -s -X POST http://127.0.0.1:8231/v1/search \
     -H 'Content-Type: application/json' \
     -d '{"query":"有气球的画面","top_k":10,"tier":"deep"}'
# {"tier":"deep","elapsed_ms":412,"count":1,
#  "results":[{"score":0.7737,"kind":"image","name":"文件12.png", ...}]}

# 关掉文件名/路径加成（Agent 那条路这么发；界面默认 true）
curl -s -X POST http://127.0.0.1:8231/v1/search \
     -H 'Content-Type: application/json' \
     -d '{"query":"小女孩穿绿色连衣裙","lexical":false,"tier":"deep"}'

# 按文件名找（不做任何语义）
curl -s -X POST http://127.0.0.1:8231/v1/find \
     -H 'Content-Type: application/json' -d '{"name":"FR","kind":"audio"}'
# {"name":"FR","count":3,"total":3,"visited":23,"truncated":false,
#  "results":[{"name":"告白_FR.mp3","path":"…","kind":"audio","rank":1,"unindexed":false}]}
```

`/v1/find` 的排序按四级 `rank`：**0** 精确同名 → **1** 名字以它开头 →
**2** 名字里含它 → **3** 只在路径里含它。`unindexed: true` 表示这个文件还没建索引
（它在注册的来源目录里，但 `items` 表没有它），所以 `search_media` 找不到它。
走访上限 `FIND_MAX_VISIT = 40000` 个文件、`FIND_MAX_HITS = 300` 条命中，
触顶时返回 `truncated: true`。

```bash
     -H 'Content-Type: application/json' -d '{"path": "/abs/path/歌.mp3"}'
# {"ok":true,"text":"阳光洒满教堂的窗棂…","chars":367,"vectors":1,"seconds":18.1}

# 「立即补全」：绕开空闲门槛与每轮上限，把待处理的一次补完（异步，立刻返回）
curl -s -X POST http://127.0.0.1:8231/v1/ai/backfill \
     -H 'Content-Type: application/json' -d '{"action":"start","what":"tag"}'
# {"ok":true,"pending":6,"backfill":{"active":true,"what":"tag","done":0,"failed":0,...}}
curl -s -X POST http://127.0.0.1:8231/v1/ai/backfill \
     -H 'Content-Type: application/json' -d '{"action":"stop"}'          # 中途停
# action 还有 "status"。what 取 "tag" | "asr" | "both"；
# what="both" 但 ASR 没开时会自动降级成 "tag"。

# 待处理清单 + 闲置处理进度
curl -s http://127.0.0.1:8231/v1/ai/status
# {"total":6,"tagged":6,"pending":0,"idle_tag":true,"idle_asr":true,
#  "idle_minutes":30,"idle_batch":10,"idle_for":12.3,"running":false,
#  "run_tagged":0,"run_asr":0,"last_path":null,"last_kind":null,"last_error":null,
#  "asr_pending":0,
#  "backfill":{"active":false,"what":"tag","done":1,"failed":0,"started":...,"finished":...}}
curl -s http://127.0.0.1:8231/v1/asr/status
# {"total":6,"done":6,"pending":0,"running":false,"enabled":true,"items":[]}
```

`backfill.finished` 有值就表示这一轮跑完了，`done` / `failed` 会一直留着，所以按钮复位之后
界面还能显示「上次补全：完成 N 个」。**别用 `last_path` 判断「正在处理谁」** ——
它是上一次留下的，只有 `running == true` 时才有意义。

失败时返回 `{"ok": false, "message": "…"}`（例如「这个文件里没有音频轨，没有可转写的内容」、
「这个素材还没有索引，先刷新索引再打标」），前端直接把 `message` 弹成提示。

## 搜索历史（框内双击唤出）

在搜索框里**快速双击**，下面会挂出一个下拉菜单：最近 10 条搜索 + 末尾一条
`清除全部记录`（点了会 `confirm` 一次）。点某一条就填回搜索框并立刻重搜。

只记两类**文字**：

| 来源 | 怎么进历史 | 图标 |
| --- | --- | --- |
| 手打的查询 | 回车，或输入框**失焦**时 | 放大镜 |
| 录音转写出来的文字 | `voiceSearchAsText()`（说话、哼唱兜底、点「改用文字搜」都走它） | 麦克风 |

以图搜图、以音搜素材（指纹）、哼唱直接命中，都**不进**历史——它们没有"文字查询"。

### 为什么打字这条路是「失焦」而不是「每次检索」

搜索框是**实时检索**（输入防抖 260ms 就跑一次）。如果每次 `doSearch()` 都记一笔，
打「小狗在操场」会留下「小」「小狗」「小狗在」「小狗在操」「小狗在操场」五条垃圾。

所以 `doSearch(opts)` 里判断的是 `!opts.live`：

* `doSearch({live:true})`（打字触发）→ **不记**
* `doSearch()`（回车）/ `voiceSearchAsText()` → **记**
* `doSearch({noHist:true})`（从 `?q=` 链接进来）→ **不记**，那不是用户敲的

实时检索下用户往往不按回车，所以还补了**失焦落库**：谁手打过（`_qTyped` 标记）
就在 blur 时记一笔。语音写入的值会把 `_qTyped` 置回 false，不会被误记成"打字"，
也不会把已有的麦克风图标降级成放大镜（`histAdd()` 里 `voice` 优先保留）。

### 其他

* 存储：`localStorage.searchHistory`，形如 `[{t:"小狗",k:"text",ts:…}]`，最多 10 条，
  同一个词再搜一次只是**提到最前**，不新增。
* 收起：按 Esc、点面板以外的地方、开始在框里打字——三种都会关。
* 面板内的条目带 `onmousedown="event.preventDefault()"`，这样点它时输入框不会先失焦，
  免得 `blur` 把面板提前收起、点在空处。

## 以图搜图 / 以音搜素材之后，怎么回到首页

搜索框**右端只有一个「取消搜索」出口**：不管你是刚打完字、还是刚用图片/音频搜过，
那里都会亮起同一个蓝色胶囊「× 取消搜索」，点它就回到未输入的首页状态——清空搜索框、
清掉以图/以音状态、重新铺满 23 项浏览列表。Esc 也能取消（历史面板开着时 Esc 先收面板，
再按一次才取消搜索）。

| 当前状态 | 「取消搜索」在哪 | 点了做什么 |
| --- | --- | --- |
| 打了字 | 搜索框右端 | 清空搜索框，回首页 |
| 以图搜图 / 以音搜素材 | 搜索框右端 | 取消这次检索，清空搜索框，回首页 |
| 麦克风（说话 / 哼唱） | **语音识别条右端** | 收起语音条，清空搜索框，回首页 |

**同一个按钮在任意时刻只出现一个。** 麦克风那一路，语音条上本来就有一个 ×，
现在换成和搜索框里**长得一模一样**的蓝色胶囊；同时 `syncClr()` 会在语音条存在时
把搜索框里那个藏起来——否则麦克风说完话，同一屏上会并排出现两个「取消搜索」。
用户一开始在搜索框里打字（`input` 事件）、或从搜索历史里选一条，语音条会自动收起，
搜索框那个胶囊随即回来。

> 早先打字时这里是另一个暗淡的小 ×（只清空搜索框、不带字），两种外观反而让人犹豫
> 「这个 × 是清字还是取消检索」。统一成一个带字的胶囊之后，不需要再判断。

实现上有一处刻意：**侧栏原来那张「当前输入」预览卡被删掉了**。状态改由 `QMODE`
（`'image' | 'audio' | null`）与 `QNAME` 承载，`syncClr()` 是**唯一的显隐出口**——
它看三件事：搜索框里有没有字、`QMODE` 是不是非空、**当前有没有语音识别条**。
原先散在 9 处的 `$('#clr').style.display = …` 全部收拢到它，`doSearch()`（打字或语音
= 新的一次检索）会顺手把 `QMODE` 置空，所以打完字状态不会残留。

**代价与补偿**：预览卡没了，用户就看不到"这一屏是用哪张图/哪段音频搜的"。补偿是把
信息挪进结果区那行提示，由 `qmodeNote()` 拼前缀：

```
以图搜图「文件12.png」 · 找到 3 个相似素材 · 已隐藏 20 项低匹配 · 按相似度排序
以音搜素材「晓_FR.mp3」 · 找到 1 个匹配素材 · 按相似度排序
```

> ⚠️ 删 `.qpreview` 那段样式时踩过一个坑：`.imgquery` 系列规则被夹在中间一起删了，
> 而 `.imgquery` 还被内容区的「待传输录音」横条（`showPendingAudio()`）用着。
> 改样式时如果按范围整段删，**先 grep 一下类名还有没有别的使用者**。

## 侧栏的「最近上传」（图片 + 音频，最多 10 条）

侧栏「临时垃圾桶」下面是**最近上传**区：以图搜图、以音搜素材用过的文件都留在这里，
图片和音频合起来最多 10 条，同一份文件再传一次只是**提到最前**。点条目 = 重跑那一次检索。

右上角两个图标：垃圾桶（清空，会 `confirm`）和**视图切换**。两种视图**都是上下滑动**，
用的都是那条跟主题走的细滚动条：

| 视图 | 排布 | 单条尺寸 |
| --- | --- | --- |
| 小图标 | 每行 1 个，最多 10 行 | 行高 **44px**，缩略图 30×30，▶ 紧跟在缩略图右边，× 在最右端 |
| **大图标（默认）** | **2 列 × 5 行**网格（10 条正好 5 行） | 卡片 86×98，封面 74×66，▶ 浮在封面正中 |

**空的时候**，两种视图显示的是同一段文字、同样居中、同样三行：

```
还没有上传过图片或音频
「以图搜图」「以音搜素材」
用过的都会留在这里
```

> 一开始小图标视图下的空态被压成了一列 4~6 个字（`还没有上传过 / 图片或音频 / …`
> 共 6 行，还是左对齐）。根因是 `.qhbody` 是 `display:flex; flex-direction:column`，
> `.qhempty` 作为 flex item 被内容撑成一条窄带。修法是让它占满整行：
> `flex:0 0 auto; align-self:stretch; width:100%; box-sizing:border-box;`。
> 大图标视图下 `.qhbody` 变成 2 列 grid，还得再加一条 `grid-column:1 / -1`，
> 否则空态只占左边那半格（实测只有 89px 宽）。

> 小图标的行高原来只有 36px、缩略图 26px，一屏塞得下 7 行多，看着像一串紧凑的目录。
> 调到 44px / 30px 之后一屏约 6 行，剩下的靠滚动——10 条变成一条**看得出还能往下滑**的
> 列表，而不是一屏糊完。

> 大图标视图最初是「一排 84px 的卡片 + 横向滑动 + 底部一条自绘进度条」。改掉的原因：
> 侧栏只有 222px 宽，横向滑动一屏只看得到三张半，第 4 张之后全靠拖着走；而上下滑动时
> 原生滚动条本来就在，再画一条进度条纯属多余——`#qhBar` 元素与 `qhSyncBar()` 已整个删掉。

### 名字太长怎么办：hover 时来回滚一遍

侧栏只有 222px，`会议录音-09-30.m4a` 这种名字必然被省略号吃掉。渲染完之后
`qhMeasureNames()` 逐个量一遍：内层 `<i>` 比外层 `.nm` 宽出 2px 以上就打个 `.more`，
把多出来的像素写进 CSS 变量 `--sc`。默认状态右边是一道渐隐（`mask-image`），
**鼠标停在那一行上时**名字才以 `qhMarquee` 动画往返平移 `--sc` 的距离
（`2.6s ease-in-out infinite alternate`），滚起来的时候左边也补一道渐隐，
免得第一个字被切得生硬。

**大小两个视图都滚。** 一开始只做了小图标列表，大图标视图里被截断的名字就只能干看着
——那个视图的格子只有 77px 宽，长名字截得比小视图还狠，所以后来把
`.qhbody:not(.big)` 这个限制去掉了，`qhMeasureNames()` 里对 `QH_BIG` 的提前 return 也删了。

大图标视图的 `.nm` 是 `text-align:center`，不过**溢出的名字本来就从左边第一个字开始显示**
——居中对齐在内容超出容器时会退化成「start」对齐（浏览器为了避免开头被切掉做的保护），
实测 `innerLeft === nmLeft === 24`。没溢出的短名字才真居中（`小狗.png`：`innerLeft 136`
对 `nmLeft 120.5`，正好居中）。所以滚动方向和另外两处一致，不用额外调对齐。

两个细节和侧栏的 `srcMeasureNames()` 保持一致：不可见的行（`!nm.clientWidth`）直接跳过，
免得拿 0 去比、把已设好的状态误清掉；`html[data-anim="off"]` 下不滚（看不全还有
`title` 的原生提示兜底）。

> 试听按钮原来紧挨着 ×，手一抖就点到删除。现在按钮顺序是
> `缩略图 → ▶ → 名字 → ×`：▶ 贴着缩略图（left 47px），× 在最右端（left 164px），
> 实测两者相距 **95px**。

| 存什么 | 存在哪 | 为什么 |
| --- | --- | --- |
| 条目（类型 / 名字 / 缩略图 / 时间） | `localStorage.uploadHistory` | 很小 |
| 图片缩略图 | 同上，`canvas` 缩到 160px 的 JPEG（4~8KB） | 原图 dataURL 动辄几 MB，塞 localStorage 会爆配额 |
| 原始字节 | **只在内存**（`QH_BYTES`，刷新即丢） | 音频整段几 MB 起步，持久化不划算 |
| 音频试听片段 | **IndexedDB** `fxseek-hist` → `clips` | 见下 |

### 音频的试听按钮：为什么是 IndexedDB

音频条目右侧有个 ▶（大图标视图里浮在封面中央，hover 才显形）。点一下试听、再点暂停、
换一条会停掉上一条。

原始字节只在内存里，刷新就没了——历史条目要能**跨会话**试听，就得另存一份小片段。
`qhMakeClip()` 把上传的音频用 `decodeAudioData` 解出来，取**前 20 秒**，用
`OfflineAudioContext` 重采样成 **12kHz 单声道**，再手写一个 44 字节头的 16 位 PCM WAV：
`20s × 12000Hz × 2B ≈ 480KB`，10 条约 4.8MB。localStorage 装不下（Safari 上限 5MB），
IndexedDB 正好；删单条 / 清空时会连带把片段删掉。

**顺带得到一个好处**：指纹算法对采样率和声道数不敏感，所以刷新之后点音频条目，
拿这段 20 秒片段去比指纹照样能命中——实测 `忆_FR.mp3` 的片段 → `0.99` 命中原曲
（外加「同一首歌」关联）。片段也丢了才会退化成提示「请再选一次这个文件」。

## 数据放在哪、怎么清理

### 数据目录：代码只读，数据可写

老版本把索引库写在 `<程序目录>/data/` 下。开发时没问题，打包成 macOS `.app` 之后会踩三个坑：

1. `/Applications` 里的 `.app` 普通用户没有写权限，装完就索引不了；
2. 升级替换 `.app` 会把用户索引好的向量库一起覆盖掉；
3. 往 bundle 里写文件等于改了签名内容，Gatekeeper 会报「已损坏」。

所以路径解析统一收在 **`paths.py`**（唯一知道「数据放哪」的模块），按顺序取：

| 顺序 | 位置 | 说明 |
| --- | --- | --- |
| 1 | 环境变量 `FXSEEK_DATA_DIR` | 便携模式 / 多实例 / 测试；**指定了就完全用它，不做迁移** |
| 2 | `~/Library/Application Support/FXseek` | macOS 惯例；可写、不随升级或重装丢失 |
| 3 | `<程序目录>/data` | 老版本位置；**仅当上面都写不进去时**回退 |

首次启动时若 2 还没有数据、3 有数据，会自动**复制**过去（`shutil.copy2` + `copytree`，**只复制不删除**，老目录留作备份），并写一个 `.migrated_from_legacy` 标记避免重复搬运。

判断「能不能用」不是靠猜权限，而是 `_writable()` **真去建目录、写一个 `.write_probe` 再删掉**——只读卷、权限不足、沙箱都会被这一步挡住，挡不住才用新位置，否则打印一行说明并**回退到老位置，绝不把数据弄丢**。

`DATA_DIR` 目录权限 0700（只有当前用户能读）；`settings.json` 里含 API Key 明文，`save_settings()` 每次保存后 `chmod 0600`。

目录里一共 6 样东西：

```
~/Library/Application Support/FXseek/
├── index.db            向量库（items 表，vec 是 2048 维 float32 = 8192 字节/条）
├── fingerprints.db     音频指纹（Chromaprint）
├── settings.json       设置（含 API Key 明文，0600）
├── sources.json        索引源
├── trash.json          回收站
└── thumbs/             缩略图 / 视频首帧 / 音频波形缓存
```

设置页「数据与安全 → 数据存储位置」会显示当前位置、各文件体积，以及下面两个清理入口。

### 三类「垃圾」分别怎么清

| 类型 | 什么时候产生 | 什么时候清 | 入口 |
| --- | --- | --- | --- |
| **失效向量** | 索引过某文件，之后文件被删除或移走 | 启动后 6 秒自动清一次；也可手动 | `GET/POST /v1/gc`、设置页按钮 |
| **失效指纹** | 同上（**指纹库是另一个 db，以前漏了**） | 跟失效向量一起清 | 同上 |
| **回收站条目** | 删除素材时 | 30 天后自动进废纸篓 | 回收站面板 |
| **缩略图缓存** | 浏览时按需生成 | 超过 `cache_limit_mb` 时按 mtime 淘汰最旧的 | 设置页「预览缓存」 |

**失效向量**分两类，处理方式刻意不同：

- `missing` —— 磁盘上文件真的不存在了（彻底删除 / 外接盘拔了）。**启动自检自动删**，不用管。
- `orphan` —— 文件还在，但不属于任何已配置的索引源（典型来源：以前用路径直接索引过，后来索引源被移除）。**只报告、不自动删除**——外接盘没挂载、索引源临时移除都会长这样，自动删会把用户数据清掉。要删得手动传 `{"orphans": true}`。

#### 踩过的坑：指纹库是**另一个** db，GC 曾经只管索引库

`index.db` 和 `fingerprints.db` 是两个独立的库，**GC 一开始只清了前者**。
后果很隐蔽：把文件夹**改名或移动**之后重建索引，`items` 换成了新路径（老路径变成
「不存在」→ 被清掉），但指纹表是按 `path` 插入、按 `path` 删除的，**老那条没人管**。

于是「以音搜素材」会**同时**返回新路径和老路径两条 —— 同一个文件名出现两次，
其中一条标着「文件已移动」；用户去设置页点「立即清理失效记录」也**没用**，
因为那次清理压根没看指纹库。截图里就是这么被发现的。

现在三处都补上了：

1. **`gc_scan()`** 除了扫 `items`，还会调 `fingerprint.stale_paths()` 扫指纹库。
   返回体新增 `fp_stale`（指纹库里的失效条数）与 `fp_only`（**只**在指纹库里、
   `items` 里早就没了的那些）。`known` 仍然只数 `items`，所以它不会因为指纹残留而虚高。
2. **`gc_index()`** 调 `fingerprint.gc_remove(victims)` 一并删指纹，**并把
   `song_links` 里引用了这些路径的关系对也删掉**（否则「同一首歌」那一栏会指向
   一个已经不存在的文件）。返回体多了 `fp_removed`。`kept` 用单独的 `db_missing`
   算，不拿指纹残留去减 `known`。
3. **检索侧兜底**：`audio_search()` 与 `voice_search()` 的指纹分支，
   遇到 `os.path.exists(path)` 为假的候选**直接丢弃**并记一条 warn 日志
   （「忽略 N 条文件已不存在的指纹记录」）。清理是治本，这一层保证**万一没清成，
   用户也不会看到打不开的结果**。

```bash
# 扫描：fp_only / fp_stale 就是指纹库里的残留
curl -s "http://127.0.0.1:8231/v1/gc" | python3 -m json.tool
# {"missing": 1, "orphan": 0, "fp_only": 1, "fp_stale": 1, "known": 23, ...}

# 手动清理（默认只清 missing；orphans=true 才连源外记录一起清）
curl -s -X POST http://127.0.0.1:8231/v1/gc \
     -H 'Content-Type: application/json' -d '{"orphans":false}'
# {"removed": 1, "fp_removed": 1, "vectors_removed": 0, "kept": 23, ...}
```

删除条数 ≥ 20 才会 `VACUUM` 压实数据库（避免每次都重写整库）。索引任务正在跑时返回 `{"error": "索引任务运行中，请稍后再清理"}`。

**缩略图缓存**：`cache_limit_mb`（默认 1024）现在真的生效了——每次写新缩略图后调 `paths.enforce_thumb_limit()`，超限就按 mtime 从旧到新删到 **90%**（留一点余量，否则每次写入都会触发淘汰）。`limit <= 0` 表示不限制。被删的缩略图下次浏览时按需重建，不影响原始资产。

**启动自检为什么延迟 6 秒**：模型加载和端口绑定优先，清理是后台线程（`_gc_autostart`），`_STATE["busy"]` 为真时直接跳过，不跟索引抢 SQLite 写锁。

## 首次启动的示例素材（开箱即用）

新用户装完打开就能看到一屏现成的内容，不用先自己准备素材 —— 这既是体验，也是教程：
点开卡片能看到 AI 描述和标签，搜「狗」「夕阳」能出结果，对着搜索框能看到历史记录，
于是自然就想挨个试试搜索、以图搜图、哼一段找歌。

### 播种了什么

首次启动时（`seed.py` 的 `seed_if_needed()`，在 `run_server()` 里最先跑）会做五件事：

1. 把 `seed/assets/` 里的 9 个示例素材复制到 **`~/Documents/FXseek示例素材/`**
2. 把 `seed/tryme/` 里的 2 个体验素材复制到 **`~/Documents/FXseek体验素材/`**（不进索引）
3. 把预置的向量库 `seed/index.db` 装到数据目录（**57 条向量**，路径已改写）
4. 把预置的指纹库 `seed/fingerprints.db` 装到数据目录（3 首音频）
5. 写一份索引源记录指向示例素材目录，并注入搜索历史和「最近上传」记录

完成后写一个 `.seeded` 标记，之后**永不再跑**。

### 两个目录分得很清：进索引的 vs 只做体验的

| 目录 | 内容 | 落到哪 | 进索引吗 |
|---|---|---|---|
| `seed/assets/` | 9 个示例素材（2 图 / 1 视频 / 3 音频 / 3 文档） | `~/Documents/FXseek示例素材/` | **进**，首页网格就摆这 9 个 |
| `seed/tryme/` | `测试用图像.png`、`测试用音频.mp3` | `~/Documents/FXseek体验素材/` | **不进** |

分成两个目录是为了让首页严丝合缝：截图里首页是「全部素材 9 / 视频 1 / 图片 2 / 音频 3 / 文档 3」，
体验用的那两个文件一旦进索引，数字就变成 11，和教程截图对不上。

但它们又不能省 —— 新用户手上没有合适的图片和音频，怎么试「以图搜图」和「以音搜素材」？
所以让它们只出现在侧栏「最近上传」里当**一键体验入口**：这两条记录由 `seed/history.json`
的 `recentUploads` 注入，并在前端带上 `seed: true` 标记。用户点一下，`qhPick()`
发现是种子记录、本地又没有字节缓存，就去 `GET /v1/seed/bytes?name=<文件名>` 取回**原始文件**，
再调 `searchByImageData()` / `searchByAudioData()` 跑一次真实的检索。

为什么不直接拿缩略图去搜：图片缩略图只是 160px 的 JPEG，以图搜图喂这个精度会掉；
音频干脆没有缓存字节（IndexedDB 里只存过 20 秒试听片段，而且首次启动本来就没有）。
取原始文件最稳，实测「测试用图像.png」能查出相似项、「测试用音频.mp3」能命中同一首歌
（95% 匹配）。相关端点：

- `GET /v1/seed/thumb?name=&w=` —— 缩略图（先找 `tryme/`，再找 `assets/`，再找已落地的两个用户目录）
- `GET /v1/seed/bytes?name=` —— 原始文件（base64 data URL，仅供种子记录使用）

两个端点都只取 `os.path.basename(name)`，不接受路径。

### 侧栏那两条演示记录只注一次

「最近上传」里的 `测试用图像.png` / `测试用音频.mp3`、以及搜索历史里那 4 条示例查询，
**由后端注入**：首次启动时 `app.py` 的 `ui_history_seed_if_needed()` 把它们写进
`<data_dir>/history.json`，并在同一个文件里打一个 `seeded: true` 标记。

> 早先这里是前端 `ui.html` 的 `seedHistory()` 从 `/v1/seed/history` 拉种子写进
> localStorage 的（那时后端碰不到 localStorage，只能这么补）。判据是「本地为空就补」，
> 而「补过没有」只记在浏览器那边 —— 用户**自己删掉之后再打开又冒出来**，看着像删不掉。
> 现在判据换成用户数据目录里的 `seeded` 标记，前端那个函数只剩一个空壳。

- 全新用户（文件不存在）：注一份演示记录 + 打标记，开箱那两个体验入口不会缺；
- 用户**明确删过**——单条 `qhRemove()`、清空最近上传 `qhClearAll()`、清空搜索历史
  `histClearAll()` 都会立刻把新的（空）列表写回服务端，`seeded` 标记不动，
  下次启动一律跳过注入：**删了就是删了**；
- 老版本留下的文件（有记录但没有 `seeded` 标记）：只补标记，**绝不覆盖**已有记录；
- 清了浏览器数据 / 换一台浏览器打开：记录从服务端回来，删掉的不会复活。

**但光有这个标记还不够——早期版本里还有第二个坑，是 pywebview 的默认值。**
`webview.start()` 的 `private_mode` 默认是 `True`，而它在 macOS 后端的意思不是「无痕模式」，
而是**每次建窗都把 WebKit 的站点数据全清一遍**（`webview/platforms/cocoa.py` 里
`removeDataOfTypes_modifiedSince…`，起始时间 1970）。localStorage 正是存在那儿，
所以搜索历史、最近上传、以及上面那个开关，**每开一次应用全丢**。表现就是删了、重启、
`seedHistory()` 看本地是空的、又补回来。现在 `launcher.py` 显式传了
`private_mode=False`（并留了注释说明为什么不能省），实测：

| private_mode | 写一个 key 后重开窗口再读 |
| --- | --- |
| `True`（旧默认） | `null` —— 被清掉了 |
| `False`（现在） | `1` —— 还在 |

一条命令就能验证：同一个 key 两次跑 `webview.start(..., private_mode=False/True)`，
前者读得回来、后者读回 `null`。要改界面里其它「存在 localStorage 的东西」时，
别忘了这个默认值是全局的、影响所有窗口。

**所以搜索记录 / 最近上传真正的家不放 localStorage，放用户数据目录。**
用户的原话是「缓存记录也应该放到用户数据目录中」——这是对的：localStorage 在桌面版里
是 WebKit 的存储，换启动方式、清站点数据、换浏览器都会丢，而这两个列表是用户资产。

- 后端 `app.py`：`ui_history_get()` / `ui_history_put()` 读写 `<data_dir>/history.json`
  （搜索记录、最近上传、以及「演示记录别再补了」的开关 `seedOff`），路由
  `GET /v1/ui/history` 与 `POST /v1/ui/history`；写入是**原子写**（先 `.tmp` 再
  `os.replace`），读坏了/文件不存在都当空，不让它拖垮首页。上限搜索 50 条、上传 30 条。
- 前端 `ui.html`：`histSave()` / `qhSave()` / `seedHistoryStop()` 里都会调 `histSync()`
  （400ms 去抖，`true` = 立刻发）；**删除类操作**（`histRemove` / `histClearAll` /
  `qhRemove` / `qhClearAll`）在改完列表之后立刻 `histSync(true)`，顺序不能反 ——
  先发再改的话发出去的是「还没删」的旧列表（踩过）。
- 启动时 `histLoad()` **以服务端为准，本地缓存全量替换**。这里早先做的是「并集」，
  结果另一个窗口的 localStorage 里只要有旧条目，就会把用户删掉的东西合并回来 ——
  删了等于没删。只有「服务端还没建立（没有 `seeded` 且两个列表都空）」时才反过来把
  本地缓存推上去一次。localStorage 只当「打开页面立刻能渲染」的缓存，不再当数据库。
- 关窗口/切后台还会走一次 `histFlushBeacon()`（`sendBeacon`），免得 400ms 去抖还没到
  用户就把窗口关了，最后那一下改动丢掉。

### 判定条件（保守）

只要满足任一条就跳过播种，绝不覆盖用户已有数据：

- `.seeded` 标记已存在
- 数据目录里的 `index.db` 已有记录
- `sources.json` 非空

### 为什么示例的 AI 描述要「随包预置」而不是首次启动现算

向量库里那些「一只毛色浅棕的小狗在绿色跑道上欢快地奔跑……」的描述和标签，是调**视觉
模型**生成的，要花用户自己的 API Key。打包机上没法在构建时替用户现算。但没有这些文本：

- 详情页的「AI 描述 / 标签」是空的，示例图片点开一片空白
- 语义搜索质量大幅下降（搜「穿米色针织衫的女人」搜不到视频）

所以做法是**从开发机现有的库里把这些文本捞出来，连同向量一起打包**。这些描述是示例
素材本身的内容，不涉及任何用户隐私数据。`tools/make_seed.py` 负责这件事，第 2 步
`carry_ai_meta()` 按文件名从旧库搬 `ai_description` / `ai_tags` / `ai_model` /
`asr_text` / `asr_model`；第 3 步再按 `indexer.py` 的约定编号把它们编码成向量：

- `AI_TAG_BASE(9000)+i` —— 每个标签一条，让「针织衫」这类词能命中
- `AI_DESC_IDX(9500)` —— 整段描述一条

捞不到的（比如体验用的 `测试用图像.png`）就留空，**不编造** —— 它本来就不进索引，
只是去跑一次真实的以图搜图，不需要自己的描述。

### 重新生成种子库

示例素材改动过、或想更新示例的 AI 描述时才需要跑（普通改代码不用，种子库是静态资源）：

```bash
./venv/cpython-3.11/bin/python3.11 tools/make_seed.py
```

它会重建 `seed/index.db` 和 `seed/fingerprints.db`。**跑之前先停掉服务**，否则
`sources.json` / 指纹库可能被占。当前种子库：9 个素材 / 57 条向量 / 3 首指纹，约 7.3MB。

### 打包时注意

- **`seed/` 目录必须随包分发**（含 `assets/`、`tryme/`、两个 `.db`、`sources.json`、
  `history.json`），否则新用户启动是空库，或者「最近上传」里那两条点了报错。
- `seed.py` 用 `P.CODE_DIR` 定位 `seed/`，所以放进 `.app` 里也能找到；但**只读的
  `/Applications` 下无法写入**，好在 `seed/` 只读不写，写入的是用户数据目录。
- 示例素材落在 `~/Documents/`，用户可以直接删掉；删了之后索引会变成「失效记录」，
  设置页的「数据与安全」里能一键清理。
- **不要打包缩略图缓存**：`app.py` 的缩略图 key 是 `sha1(path|mtime|at)`，
  素材一换目录就全部失效，会按需重新生成，打包进去纯属浪费体积。

### 改示例素材要同步改的地方

- `seed/history.json` 的 `searchHistory` 是搜索框下拉里的「最近搜索」，内容要能命中
  `seed/assets/` 里的示例素材（当前是「狗 / 夕阳 / 财报 / 针织衫」）。
- 同一个文件里的 `recentUploads` 是侧栏「最近上传」，按**文件名**引用 `seed/tryme/`
  里的体验素材。改素材名时记得一起改，否则那一条点了会取不到文件、只能弹提示。

## 打包成 .app / .dmg

一条命令：

```bash
bash tools/build_app.sh          # 只出 dist/FXseek.app
bash tools/build_app.sh --dmg    # 再打成 dist/FXseek-<版本>.dmg
```

脚本做的是把它做成一个真正的 macOS 应用：`.app` 骨架 + `Info.plist` +
`Contents/MacOS/FXseek` 启动脚本（定位内置运行时 → `launcher.py`）+ ad-hoc 签名。
产物体积 **`.app` 547 MB / `dmg` 278 MB**（dmg 是 UDZO 压缩过的，实际下载就这个大小）。

打开后是一个 **pywebview 原生窗口**（`launcher.py`），流程是：

1. 先弹一个 520×430 的准备窗口（显示进度、速度、剩余时间，带「换源」按钮）；
2. 后台线程起本地 HTTP 服务（`run_server` 是阻塞的 `serve_forever`，必须在子线程，
   GUI 主线程留给 Cocoa —— 反过来会崩）；
3. 端口通了就把准备窗口换成主界面，窗口放大到 1440×900。

### 窗口行为：热启动、缩放、关闭三键

准备窗口只负责「首次下载」和「读模型」这两件慢事，但它有三个容易出戏的地方，
都踩过：

**1）模型已经在本地时，别再装成要下载。** 热启动时 `find_model()` 是毫秒级的，
`serve()` 线程往往比窗口里的页面先跑完，那几句 `prep.stage(...)` 打在还没加载的
页面上，被 `window.__seek && ...` 短路吞掉 —— 用户就对着 HTML 里写死的默认文案
「首次启动需要下载模型（约 1.9 GB）」干等二十秒。修法是**把方向反过来**：

- 页面加载完自己调 `window.pywebview.api.prep_state()` 把状态拉过来（`_push` 里
  攒着的最后一份 payload），不再依赖 Python 往页面推；`_arm_page_ready()` 再加 3 秒
  兜底放行。之所以不能用 `window.events.loaded += ...` 补发：**pywebview 的 macOS
  后端压根不触发 loaded 事件**（`cocoa.py` 里没有 `events.loaded.set()`）。
- 热启动时 `prep.mode("warm")` 给 `<body>` 加 `warm` 类，CSS 把下载源按钮、百分比、
  字节数整块 `display:none`，进度条换成一条 100% 宽的呼吸动画，只留一句
  「马上就好，不用管它」。

**2）标题栏第三个（绿色）按钮曾经是灰的、点不动。** 准备窗口是按 520×430 的固定
小窗设计的，建窗时 `resizable=False`；而 pywebview 的 macOS 后端只有在
`resizable=True` 时才给 `NSResizableWindowMask`，6.2 又没有运行期改 resizable 的
接口。所以切到主界面后由 `_tune_main_window()` 用 pyobjc 自己补：

- `setStyleMask_(styleMask() | NSResizableWindowMask | NSMiniaturizableWindowMask)`；
- `setContentMinSize_((1060, 680))` —— pywebview 6.2 的 macOS 后端**没有**
  `set_min_size()`，原来那句 `window.set_min_size(*WIN_MIN)` 一直被 `try/except`
  吞掉，主窗口其实能被拖成一条缝；
- `center()` —— `resize(1440, 900)` 是从原本 520×430 的位置长出来的，左下角不动，
  实测长到 `origin.y = -205`，小半个窗口掉在屏幕下方。

原生窗口从 `window.native` 拿（cocoa 建窗时做了 `pywebview_window.native = self.window`）；
**`window.gui.window` 这条路在这个版本拿不到**，那一层是空的 —— 第一版就是这么静默失效的。

**3）点关闭按钮先问一句。** 三态存在设置里（`close_action`，`ask` / `quit` / `tray`，
默认 `ask`）：

- `closing` 事件的返回值语义来自 pywebview 的 `Event.set` → `should_close`：
  **返回 `False` = 取消关闭，`True` = 放行**（事件是 `should_lock=True`，同步跑在
  Cocoa 主线程上，所以返回值有效）。
- `ask` 拦下关闭，再用 `AppHelper.callAfter` 弹原生 `NSAlert`：「退出 FXseek」/
  「最小化到菜单栏」/「取消」，带一个「记住我的选择，下次不再询问」的开关；
  `setInitialFirstResponder_(alert.buttons()[0])` 让回车落在「退出」上。
- 最小化到菜单栏 = `window.hide()`，**不再切 activationPolicy**。**这一步是为了后台常驻**：
  开了 MCP 的用户会把 FXseek 挂在那儿用（MCP 的 stdio server 转发到 `127.0.0.1:8231`），
  窗口一关服务就没了，所以关窗口只是把面板收起来，进程和 HTTP 服务照跑。菜单内容：

  ```
  服务 127.0.0.1:8231（后台运行中）   ← 灰色不可点，纯给用户看地址
  ─────────────
  打开面板 / 隐藏面板                 ← 一项两态，标题跟着状态变
  ─────────────
  退出 FXseek                         ← 真正结束进程
  ```

  退出走 `_quit_now()`：置标志放行关闭 → `window.destroy()`，再挂一个 3 秒的兜底线程
  `os._exit(0)`（隐藏过的窗口有时不触发 pywebview 自动退出）。

**4）菜单栏图标：必须由「子进程」去摆。** 这是这一版最费劲的一个坑，结论先写：

> macOS 对**由 LaunchServices 启动的进程**（用户双击 .app 就是这条路径）不给排菜单栏图标：
> `NSStatusItem` 建得出来、`isVisible()` 也是 True，但按钮窗口高度永远是 0，看不见也不报错。
> **由别的进程 `exec` 出来的子进程**则不受这个限制。

这不是猜的，是写了个最小的纯 AppKit 程序对照出来的：同一份代码，双击启动排不上
（`frame=(0,0,37,0)`），终端直接 exec 启动就正常（`frame=(665,930,37,30)`）；用 Finder 打开
一样失败；而**父进程哪怕是双击启动的，它 `Popen` 出来的子进程照样能排上**。所以：

- `tray_helper.py`：独立的菜单栏图标助手，`launcher.py` 等服务端口通了以后 `Popen` 它
  （带 `--port` 给菜单项点，带 `--parent` 让它在主程序没了之后自己退出）。它不占程序坞、
  不抢焦点（`Accessory`），菜单三项通过**本机 HTTP** 转给主程序：`POST /v1/panel/show`、
  `/v1/panel/hide`、`/v1/app/quit`（后端是 `app.py` 的 `PANEL_HOOKS`，由 `launcher.py` 的
  `_install_panel_hooks()` 注册；命令行直接跑 `app.py` 时没人注册，那几个口子会老实回
  「面板控制只在桌面版里可用」）。
- 退出时按 pidfile（数据目录里的 `.tray.pid`）把助手收掉，不然重启一次菜单栏就多一个
  点不动的图标。

**5）图标「建成功了」不等于「看得见」（这一版踩得最久的坑）。** 除了上面那条
LaunchServices 的限制，还有一条更邪门的：**同一个进程里，系统只显示「最后建的那个」
`NSStatusItem`，之前建的一律高度 0**。最小程序验证过（连建三个：`L0`、`L1` 永远高度 0，
只有最后那个 `L2` 是 `vis=True / h=30`）。于是：

- 建图标前先放一个**替死鬼**（`_SACRIFICE`）把「第一个」的名额占掉；
- 助手起来后 2.5 秒查一次按钮窗口高度，还是 0 就**换一个再建**（新建的会变成「最后一个」
  从而显示出来），最多试 5 次；实测常见的是一次失败、第二次就排上了；
- 5 次都不行就退出码 2 收场，主程序的 `_tray_keeper()` 线程发现后再重开一个助手进程
  （换个进程往往就好了）；
- 日志里那句 `[tray] 图标已排上（frame=...）` 是判断「到底有没有真的显示」的唯一可靠依据——
  `isVisible()` 会骗人，高度不会。

**6）点 Dock 图标要能唤回面板。** 两条路都得接：

- 应用不在最前面时点 Dock → 先激活，监听 `NSApplicationDidBecomeActiveNotification`；
- 应用已经在最前面、只是窗口被藏了 → 系统走
  `applicationShouldHandleReopen:hasVisibleWindows:`，得挂在自己的 delegate 上。pywebview
  自己装了 AppDelegate（管 `applicationShouldTerminate:` 等），所以**子类化
  `webview.platforms.cocoa.BrowserView.AppDelegate`** 再 `setDelegate_`，原行为一个不丢。

  这里有个隐藏顺序问题：pywebview 的 `webview.start()` 会给每个窗口调 `create_window()`，
  里面有一句 `app.setDelegate_(BrowserView._shared_app_delegate)`（`cocoa.py:615`），
  **会把 `start()` 之前装的 delegate 顶掉**。所以 `_install_reopen_hook()` 要调两次
  （`main()` 里一次、`on_loaded` 里一次），而且那份 AppDelegate 子类**只能定义一次**——
  pyobjc 里第二次定义同名类会抛 `_ReopenDelegate is overriding existing Objective-C class`，
  抛了之后 `setDelegate_` 就再也不会执行（之前「点 Dock 没反应」就是这个原因）。

- **右键程序坞图标是保底入口**：`_ReopenDelegate.applicationDockMenu_` 返回
  「打开面板 / 隐藏面板 + 退出 FXseek」，不依赖菜单栏，图标万一被挤掉也能从 Dock 找回面板。
- **`removeStatusItem_()` 在 pywebview 的 Cocoa 应用里会 SIGTRAP**（实测必崩，跟装不装
  AppDelegate 无关；同样的调用在纯 AppKit 脚本里没事），所以收图标只用 `setVisible_(False)`。
- `NSStatusItem` / `NSAlert` 都是**主线程限定**的，从别的线程建会抛
  `NSInternalInconsistencyException - NSWindow should only be instantiated on the main thread!`，
  所以这些都过一遍 `_on_main()`（在主线程就直接跑，否则 `AppHelper.callAfter`）。
- **收起来之后必须留一条能找回面板的路**：菜单栏图标（子进程）、点 Dock 图标（两条路已接）、
  右键 Dock 图标（`applicationDockMenu_`）——三条里任意一条能用，用户就不会把自己关在门外；
  助手摆不上时 `_tray_keeper()` 还会每 6 秒重开一个，最多 4 次。
- 加设置项时注意：`save_settings(patch)` 只写 `for k in DEFAULT_SETTINGS` 里已有的键，
  所以 `"close_action": "ask"` 必须先加进 `DEFAULT_SETTINGS`（`app.py`），否则存不进去。

**7）菜单栏狒狒「抓耳挠腮」动效 —— 这台 macOS 26 上最难啃的一块。** 结论先写：

> 状态栏图标**初设之后，运行期换图基本不刷新**：`button.setImage_`、`button.layer` 的
> `CABasicAnimation`（transform.rotation.z）、`display()`/`setNeedsDisplay_()`、
> `NSImage` 换 `representation`、`setLength_` 抖动 —— 全部实测屏幕纹丝不动（用
> `screencapture` + `PIL ImageChops.difference` 逐帧 diff 验证）。图标「会变」只有两种
> 情况：**①新建 NSStatusItem 以新图初设时；②`setVisible_(True/False)` 切换**。

据此，动效实现为「**重建式换帧**」+「**后台线程脉冲**」：

- **重建式换帧**：每 3 秒 `_scratch_apply(idx)` 重建一个 item（带替死鬼），让它以第 idx
  帧（静止 / 抬手 / 高抬，`assets/baboon_scratch1/2.png`）初设；旧 item **先留着**，
  新 item 确认排上（`button.window().frame().size.height > 0`）之后才 `setVisible_(False)`
  藏旧的 —— 排不上就保留旧姿势，图标永远不丢。
- **后台线程脉冲**：又一个邪门现象——**主线程在 `app.run()` 之后注册的
  `AppHelper.callLater` 定时器不触发**（`_verify` 那条 `callLater(2.5)` 是 run 前注册的，
  所以能跑；run 后新注册的一律石沉大海）。解法是 `threading.Timer` 后台线程每 3 秒醒来，
  在线程里调 `AppHelper.callLater(0.05, _scratch_tick)` —— **从后台线程注册的 callLater
  反而能被主 runloop 执行**（实测验证过）。重试链（`_retry_later`）走同一条通道。
- **兜底资源**：`assets/baboon_anim.gif`（三帧循环 GIF）已备好，`_baboon_frame(3)` 可加载；
  若将来验证 NSImage 在 status item 里能自动播 GIF，直接初设这一张即可，比换帧简单得多。
- **风险提示**：运行期新建 item 在「连续重建」时经常排不上（`laid=False`，probe 实测），
  所以动效是**尽力而为**的：排不上就停在静止帧，绝不崩、绝不丢图标。

### 桌面版里的三个界面改动（都跟 WKWebView 有关）

打包成 app 后界面跑在 pywebview 的 WKWebView 里，有三件事跟浏览器里不一样，顺手都修了：

1. **选中素材不再自动展开详情区。** 详情区默认折叠是为了首屏把位置让给素材，
   但原来 `selectCard()` 里有一句「折叠着就帮你展开」，结果一点卡片九宫格就被挤窄。
   现在只 `loadDetail(x)`（内容照常加载，用户自己点箭头展开时立刻就能看到），
   展不展开完全听 `toggleDetail()`。
2. **「下载」改成「路径源」。** WKWebView 没实现下载委托，`<a download>`
   在 app 里点了**没有任何反应**（不报错、不下载）。而这些文件本来就在本机，
   用户要的是「它在哪」。所以详情区、预览浮层、阅读器、Office 降级提示里的 5 处
   下载入口统一改成 `revealInFinder()` → `POST /v1/reveal` → 后端 `open -R`
   （`app.py` 里本来就有 `reveal_in_folder()`，直接复用），按钮文字按用户要求写作
   「路径源」；右键菜单里那两条同名动作仍叫「在访达中显示」（给不熟悉这个词的人看）。
   浏览器里打开同一个页面也一样能用，只是浏览器自己也能下载，看个人习惯。
3. **麦克风在 app 里可能用不了，而且不是代码问题。** 症状是点麦克风弹
   `无法访问麦克风: undefined is not an object (evaluating 'navigator.mediaDevices.getUserMedia')`
   —— 注意是 `navigator.mediaDevices` **整个不存在**。实测对照（同一个 .app、
   同一份代码，只换启动方式）：

   | 启动方式 | `typeof navigator.mediaDevices` |
   | --- | --- |
   | 终端里直接跑（含 `open` 之外的一切方式） | `object`，`getUserMedia` 是 function |
   | **双击 / 访达 / 程序坞 / `open`（即 LaunchServices）** | `undefined` |

   试过且**无效**的：给 Info.plist 加 `NSMicrophoneUsageDescription`、
   加 `DTSDKName`/`DTPlatformVersion`、给 app ad-hoc 签名并带上
   `com.apple.security.device.audio-input` 权限、把它做成子进程启动、
   延后 3 秒再建窗、`WKPreferences` 的 `mediaDevicesEnabled`/`mediaStreamEnabled`。
   也就是说：**这个系统版本不给「从访达启动的应用」开放话筒**，应用自己改不了。
   前端现在会先说人话（「当前系统版本下应用内录音不可用…可以把音频文件拖进来搜索」），
   不再抛那句英文；Info.plist 里的用途说明也先加好了，哪天系统放开就能直接生效。
   真要现在就能录，只能绕开 WebKit —— 见下面那节，已经做了。

### 桌面版的原生录音（recorder.py）

上面第 3 条的结论是「WebKit 这条路在访达启动的 app 里堵死了」，所以桌面版改成
**在 Python 侧用 AVFoundation 录音**，前端行为跟浏览器录音完全一致：

- `recorder.py`：`status()`（0 未决定 / 1 受限 / 2 拒绝 / 3 已授权）、`request_access()`
  （只在「未决定」时弹系统授权框）、`start(dst_dir)`、`stop()`、`cancel()`。
  录音用 `AVAudioRecorder` 写成 `mic-<时间戳>.m4a`（AAC / 44100 / 单声道 / High），
  `stop()` 读成 `data:audio/mp4;base64,…` 后**把临时文件删掉**——检索要的字节已经在内存里。
  `_state["rec"]` 必须留着 recorder 的引用，不然会被 GC 掉、录到一半停。
- 路由器：`app.py` 的 `elif u.path.startswith("/v1/mic/")` → `_panel_hook("mic_" + 动作)`；
  钩子在 `launcher.py` 的 `_install_panel_hooks()` 里注册（`mic_status/mic_request/mic_start/mic_stop/mic_cancel`），
  录音目录 `<data_dir>/mic`。没装桌面版时这些口子返回「只在桌面版里可用」。
- 前端：`startRecording()` 发现 `navigator.mediaDevices` 不在就 `startNativeRecording()`，
  走 `micApi('start'|'stop'|'cancel')`；停下来把 base64 塞进 `_pendingAudio`，
  于是 `/v1/voice-search` 那条链路一个字都不用改（它本来就认 `data:audio/mp4`）。
  原生录音没有 `AnalyserNode`，波形用 `startFakeWave()` 画一条会呼吸的假波形。
- 权限：第一次点麦克风，`/v1/mic/start` 看到状态是 0 就顺手弹系统授权框，并回一句
  「正在请求麦克风权限，请在系统弹窗里点「允许」后重试」；用户点允许后再点一次即可。
  打包版实测：LaunchServices 启动时 `status=0`（未决定）→ 弹框标题是
  「"FXseek"想要访问麦克风」，副标题就是 `NSMicrophoneUsageDescription` 里那句话。
  依赖 `pyobjc-framework-AVFoundation`（已进 venv 与打包白名单）。

### 菜单栏那个图标（tray_helper.py）

菜单栏上的 `✦ FXseek` 是一个独立的 NSStatusItem 进程，长这样（从上到下就是要求的顺序）：

```
服务器：运行中（端口 8233）      ← 绿色，只是状态，点不动
──────────────────────────
打开 Web 服务端
停止服务器  /  启动服务器         ← 同一个位置，随状态换字
──────────────────────────
MCP 状态  ▸                      ← 子菜单
──────────────────────────
打开服务面板
──────────────────────────
设置…            ⌘,
关于 FXseek
──────────────────────────
退出 FXseek      ⌘Q
```

四个分组各占一段：状态、打开/停止服务、MCP 状态、面板与设置 —— 每段之间都有分割线，
所以「MCP 状态」和「打开服务面板」各有一条线压在上面（照着 oMLX 那份排的）。

- **中英双语**：`tray_helper.TXT` 里两套文案键名一一对应，`_t()` 缺词条时回落中文。
  语言来源是**用户数据目录的 `settings.json` 里的 `lang`**（走文件不走 HTTP ——
  服务被我们自己停掉时菜单还得画得出来），每次开菜单时 `_paint()` 重设一遍标题，
  所以在设置页切完语言，下次点开菜单就是新的一套。
- **状态行是现读的**：`MenuDelegate.menuNeedsUpdate_` 里每次菜单打开都去问一遍
  `/v1/server/state` 和 `/v1/mcp/status`。读不到就沿用上一次的记忆 ——
  否则刚点完「停止服务器」、下一帧菜单自己刷新一遍，又会被写回「运行中」。
- **停止/启动服务**走 `app.py` 的 `server_stop()` / `server_start()`：
  `stop()` 会**延 0.4 秒再关**，因为「点菜单」这个请求本身正跑在要被关掉的那个服务上，
  当场 `shutdown()` 会让响应写不回去；关掉的只是监听 socket，模型、索引、数据都不动。
- **两条下发通道**（`tray_helper._cmd()`）：服务活着就直接打 HTTP；
  服务已经被停掉时 HTTP 必然失败，于是原子写一份 `<data_dir>/tray_cmd.json`，
  主程序里 `_tray_cmd_watch()` 每 0.7 秒比一次 mtime，读到 `{"cmd":"server_start"}` 就执行。
  这条通道是「服务停了还能把它叫起来」的唯一办法。
- `tray_helper._watch()` 里那句 `if not STATE["running"]: continue` 不能省：
  主程序探活失败 3 次会连带退掉图标，这是我们自己把服务停掉时最不想看到的。
- 菜单项验证**只能靠截图 + 直接打 HTTP/命令文件**：System Events 拿不到这个
  NSStatusItem 的菜单（`click menu item … of menu bar item 1` 报 `-1719 无效的索引`，
  枚举出来的是别的 app 的系统菜单栏）。

#### 「MCP 状态」子菜单：颜色写对了，却是灰的

子菜单长这样：

```
MCP 服务：已开启
已接入 2 个 agent（已装 6 个）
配套技能：已装 6 个
──────────────────────────
  DSH：已接入
  opencode：已接入
  workbuddy：未接入            ← 装了但没接：次要灰
  hermes：未接入
  codex：未接入                ← 没装：最淡灰
──────────────────────────
打开 MCP 设置…
```

**★ 坑：AppKit 会把所有「禁用」菜单项整体压暗，显式写进 attributed title 的
`labelColor` 也盖不过去。** 这是这一块最耗时间的一处 —— 之前把「已接入」那几个
写成 `_title_item(text, labelColor, bold=True)`，颜色完全没生效，一直显示灰色，
看上去像是改错地方了。实测四组对照（真菜单截图逐像素看）：

| 组合 | 渲染结果 |
|---|---|
| 禁用 + 无颜色 | 灰 |
| 禁用 + `labelColor` + 粗体 | **还是灰**（粗体生效了，被吃掉的只有颜色） |
| 启用 + `labelColor` + 粗体 | 纯黑 |
| 禁用 + **自定义视图** | **颜色如实显示** |

也就是说 `setEnabled_(False)` 这一条决定了整行会被压暗，跟颜色怎么给无关。

**解法是自定义视图**：`_strong_item()` 造一个禁用的 `NSMenuItem`，把 title 留空，
再 `setView_()` 一个不可编辑、不画背景的 `NSTextField`。它不参与菜单那套压暗绘制，
所以颜色终于说了算，同时仍然是**点不动、悬停不泛蓝**的状态行。

也试过「`setEnabled_(True)` + `setAutoenablesItems_(False)`」那条路：颜色同样能正常
显示，但整行会变得像**能点的按钮**（悬停泛蓝），状态行不该有这种暗示，所以没用。

**两个尺寸/宽度上的细节**：

- `boldSystemFontOfSize_(0)` 返回 **13 pt**，而 `menuFontOfSize_(0)` 是 **14 pt**。
  直接写 `boldSystemFontOfSize_(0)` 会让这一行比邻居**小一号**。正确做法是先取
  `menuFontOfSize_(0)`，再用它自己的 `pointSize()` 去要对应字号的粗体。
- 每次改文字都要重新 `sizeToFit()` 再重设 frame 宽度，否则
  「运行中（端口 8231）」切成更长的「已停止（点下面那项即可启动）」会被截断。
  这也是 `_set_strong()` 存在的理由 —— `_set_title()` 走的是 attributed title，
  跟自定义视图是两条路，改了字看不到效果。

顶部那条 **「服务器：运行中」原本是 `systemGreenColor()`，同样被压成灰色** ——
文件注释写着「绿色高亮，点不动」，实际一直没绿过。它现在也走 `_strong_item`，
`_paint()` 里用 `_set_strong()` 在线绿 / 停橙之间切换。

**用户最终定的视觉**：汇总三行与「已接入」的行都用**正文粗细**（`bold=False`），
只有颜色区分；加粗版实测太压眼。层次仍然靠灰阶保留（已接入 = 正文色、
装了没接 = 次要灰、没装 = 最淡灰）。

**但「加粗」这事被用户提了两次 —— 第二次才找到真凶（1.0.7）**：那两行字重**早就是
正文粗细了**，看着粗的是**颜色**。菜单里别的项都是禁用态，AppKit 会把它们统一压暗成
灰色；而 `_strong_item` 是自定义视图，**不参与那套压暗**，于是它顶着一身纯黑
（`labelColor()`）跟一片灰邻居并排，**视觉上就粗了一圈**。

所以最终改的是颜色而不是字重：
- MCP 汇总三行 → `AppKit.NSColor.secondaryLabelColor()`
- 顶部状态行 → 新增 `_dim(color, alpha=0.66)`（`colorWithAlphaComponent_`）把
  `systemGreenColor()` / `systemOrangeColor()` 压淡一档 —— **保留色相**（一眼还能
  分出运行中/已停止），只降分量。直接换次要灰会把这个色相信号丢掉。
- 「已接入」的 agent 行**保持正文色不动**（用户只圈了汇总三行）。

★ 教训：**在「禁用压暗」的容器里，颜色才是重量。** 只要一个项绕开了压暗，就算字重
和别人完全一样，也会显得比别人重 —— 调这类视觉问题先比色值，别急着改字重。

**怎么验证这类菜单改动**（可复用的做法）：从 `tray_helper.py` 里用
`re.search(r"\n    def <name>\(.*?(?=\n    def )", src, re.S)` 把**真实函数源码**
抠出来 `exec` 进一个临时类，渲染后 `screencapture -x -R` 抓图 —— 测的就是会上线的
那份代码，不是抄一份容易跑偏的副本。**坑**：`popUpMenuPositioningItem_…` 会阻塞在
菜单跟踪循环里，菜单弹出后跑在 `NSEventTrackingRunLoopMode`，默认模式的 `NSTimer`
**不会触发**，截图回调永远不执行、脚本挂死；必须
`NSRunLoop.currentRunLoop().addTimer_forMode_(timer, AppKit.NSEventTrackingRunLoopMode)`
（默认模式也挂一份）。另外菜单是从锚点**向上**生长，抓图区域要往锚点上方留够高度。


### 模型不进包，首次启动现下

`model/` 有 **1.9 GB**，塞进 dmg 会让安装包涨到 1.5 GB 以上，用户下不动。

- `model_dl.py` 负责下载，**双源**：`mirror` = 国内镜像（`hf-mirror.com`，默认）/ `hugging` = HuggingFace 官方。
  实测直连 `huggingface.co` 在国内不通（TLS 握手超时），所以默认走镜像。
- 下载落点是 **用户数据目录** `<data_dir>/model/`，不是 `.app` 内部 ——
  `.app` 装在 `/Applications` 是只读的，而且升级替换时会连模型一起冲掉。
- 定位顺序（`model_dl.find_model()`）：`FXSEEK_MODEL_DIR` 环境变量 → `<data_dir>/model` → 程序目录 `model/`。
  开发机上程序目录里有 `model/`，会立刻命中、完全不联网。
- 下载必须能重试：镜像会偶发抽风（实测有 25 秒超时的），`_http_get()` 带 3 次重试 + 退避。
- **第一版踩的三个坑（已修）**：
  - `requests.get(verify=...)` 只吃 **CA 证书路径或布尔值**，不吃 `SSLContext`；
    传 context 会报 `TypeError: stat: path should be string, ... not SSLContext`。改用 `certifi.where()` 的路径。
  - 镜像**不支持 Range 续传**：发 `Range: bytes=N-` 它照样回 **HTTP 200 + 完整 body**。
    旧代码见到 200 也当成功，就把完整文件追加到半截文件后面，体积直接翻倍
    （实测 400 + 1171 = 1571，而正确是 1171）。现在检测到 `have and status == 200` 就
    删掉 `.part` 从头下。
  - 镜像会在**文本文件末尾多发一个换行**：`hf-mirror.com` 的 `config.json` 是 **73465** 字节，
    官方仓库是 **73464**。严格按大小校验会让用户卡在
    「下载 config.json 大小不对：得到 73465，应为 73464」，**首次启动直接失败**。
    现在 `_size_ok(path, fn, want)` 对 `_TEXT_TAIL_FILES` 里的文本文件容忍
    「多出来的 ≤8 字节且全是空白」；权重类（`model.safetensors`、`tokenizer.json`）
    仍然严格，且大文件额外跑首尾各 8MB 的采样哈希。
    **注意**：判定只放宽「尾部空白」，多出任何非空白字节一律当坏文件重下。

### 打包纪律：两样东西绝不能进包

1. **`data/`** —— 那是数据目录。`paths.py` 会把「程序目录里存在 `data/`」当成老位置迁移源，
   启动时把它整个搬进 `~/Library/Application Support/FXseek`。结果就是
   **新用户打开看到的是打包机的库，还带着 API Key**。
   `build_app.sh` 第一步就会检查，发现 `data/` 直接报错退出。
2. **`model/`** —— 见上，1.9 GB。脚本按白名单拷贝，本来就不含它。

**别忘了 `seed/`**：开箱即用的示例素材和预置库都在这个目录里（约 7.4MB，含
`assets/` 9 个索引素材 + `tryme/` 2 个体验素材），漏掉的话新用户启动看到的是空库。
详见上一节「首次启动的示例素材」。`build_app.sh` 已把它和 `bin/`、`vendor/`、`assets/` 一起拷进去。

### 分发注意

- **没做公证（notarization）**。用户第一次打开会被 Gatekeeper 拦下，需要
  右键 →「打开」，或去「系统设置 → 隐私与安全性」点「仍要打开」。
  要免掉这一步得买 Apple 开发者账号做签名 + 公证。
- 图标：脚本会优先用 `assets/AppIcon.icns`；没有就用 `assets/icon.png` 现做一份；
  两个都没有就用系统默认（当前仓库是最后一种）。
- 用户数据目录不变，还是 `~/Library/Application Support/FXseek`，
  所以升级替换 `.app` 不会丢库。

数据目录已经和程序目录分开（见「数据放在哪、怎么清理」），所以放进 `/Applications`
之后：能正常写索引、升级替换 `.app` 不会丢用户的向量库、也不会因为往 bundle 写文件
而破坏代码签名。想看当前用的是哪个目录，打开设置页「数据与安全 → 数据存储位置」，
或 `curl -s http://127.0.0.1:8231/v1/paths | python3 -m json.tool`。

## 技术要点

- 模型是混合精度（FP8 护注意力 + INT4 压权重）的 WeMM-Embedding-2B，架构 `qwen3_5`。
- 多模态 embedding 路径：文本 + 图像过 vision_tower 得 `inputs_embeds`，
  进 `language_model` 后取 last-non-padding token 隐状态并 L2 归一。
- 检索场景务必带 task instruction（`QUERY_INSTRUCTION` / `DOC_INSTRUCTION`），
  裸文本会显著降低语义区分度。
- 服务为纯标准库实现，无 fastapi/uvicorn 依赖，便于打包。
